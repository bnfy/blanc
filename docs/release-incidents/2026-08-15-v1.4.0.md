# v1.4.0 release incident — 2026-08-15

## Outcome

Blanc v1.4.0 was published from source commit
`c73008ac4a4885c3691c026abd184c23788f20e0`. The release is the latest stable
release and contains all 14 expected macOS, Windows, Linux, updater, SBOM,
checksum, Windows-signature, and Sigstore assets. The immutable macOS ZIP was
independently accepted by Gatekeeper as a Notarized Developer ID build, its
stapled ticket validated, and the Sigstore bundle verified against
`anthony@bnfy.me` / `https://github.com/login/oauth`. Post-release changelog and
baseline commit `25d82e0741697be227bf83305fd4e8d7e0438fb0` was pushed and the
production site was deployed.

## What went wrong

### 1. The release was initially launched from the agent PTY

The 1Password CLI repeatedly attempted to authorize ChatGPT/Codex rather than
Terminal.app and could not connect reliably to desktop integration. Additional
`op signin` and account-preflight attempts did not address the process identity
problem and only added confusion.

**Fix:** reproduce the previously successful shell-history command directly in
an interactive native Terminal.app window. Its normal `op run` authorization
named Terminal and electron-builder began immediately. `release.sh` now refuses
non-Terminal/non-interactive macOS launches and the runbook forbids separate
`op signin` detours.

### 2. Release validation found two real window-teardown crashes

The first crash called `currentChromeLayout()` after its BrowserWindow had
closed, through a queued `mouseMove` listener. The second force-destroyed a
still-visible profile window, allowing Electron 43's late
`BrowserWindow.visibilityChanged` listener to touch a destroyed native object.

**Fixes in `c73008a`:** `watchCursorFor` now checks `hasLiveWindow()` before any
layout/offset callback; profile deletion hides a visible window and waits for
the visibility transition before destroying it. Regression tests were added,
the focused suites passed, and the complete gates finished at 752 unit tests
plus 104 desktop scenarios / 639 steps.

### 3. Sigstore authorization opened in Blanc and never returned

Blanc was the system default browser. Cosign opened its GitHub OIDC flow there,
the user completed the page, but the local callback never reached the waiting
Cosign listener. Waiting and reopening the now-stale authorization URL made the
recovery longer. The same fresh fixed-port request completed when opened in
Safari.

**Fix:** the release now passes an explicit IPv4 callback
`http://127.0.0.1:${BLANC_COSIGN_REDIRECT_PORT:-49197}/auth/callback` and
prepends `scripts/release-bin` to Cosign's `PATH`; that directory's `open` shim
routes Cosign's browser request to Safari. The page must be completed while it
is fresh.

### 4. The first manual finalization preflight used the wrong phase check

The preserved recovery directory already contained `SHA256SUMS` but did not
yet contain its Sigstore bundle. `verify-release-manifest.mjs` correctly
reported the missing bundle, because a directory with a checksum manifest is
defined as the final phase.

**Fix:** validate the intermediate directory with
`shasum -a 256 -c SHA256SUMS`, then sign, then run the complete manifest
validator. Do not weaken the validator; the ordering was the error.

### 5. Full process inspection exposed the notarization credential

`notarytool` receives the Apple app-specific password in its argv. A full
`ps -ef` inspection copied that value into an agent tool result. It was not
committed or written into a helper script, but it must be treated as exposed.

**Fix:** rotate that app-specific password in the 1Password `Apple
Notarization` item before the next release. Monitor notarization by process name
only and never capture full command arguments.

### 6. Post-publication checks initially looked at mutable local state

The unpacked `dist/mac-arm64/Blanc.app` no longer passed a late signature check
after packaged test execution, while a fresh extraction of the immutable
release ZIP was valid, Gatekeeper-accepted, and notarized.

**Fix:** use the archived ZIP/DMG and published hashes as release evidence.
Do not infer the state of an already-created release artifact from a mutable
unpacked test bundle.

## Proven sequence for the next release

1. Prepare, commit, and push the release inputs; confirm `HEAD == origin/main`.
2. Open/unlock 1Password and confirm `gh auth status` in native Terminal.app.
3. Run the exact command in `docs/release-verification.md` directly there.
4. Approve the Terminal-named 1Password prompt at `op run`.
5. Let all source, packaged, migration, and native CI gates finish.
6. Complete the fresh Safari Sigstore page immediately.
7. Confirm bundle verification before the draft becomes public.
8. Verify the public tag SHA, release flags, exact asset inventory, logged-out
   downloads, immutable macOS archive signature/notarization, and Sigstore
   bundle.
9. Commit the generated changelog and new public/migration baseline, deploy the
   site, and verify the canonical production URLs.

## Follow-up

Blanc's failure to return the localhost Sigstore callback is a separate browser
compatibility issue worth reproducing with a harmless local OAuth fixture. It
must not be investigated during another live release; Safari is the approved
release-operator browser until that behavior has isolated regression coverage.
