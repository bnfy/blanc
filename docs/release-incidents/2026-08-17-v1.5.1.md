# v1.5.1 release lessons — 2026-08-17

## Outcome

Blanc v1.5.1 was published from source commit
`f356dc30e4ed98d4993887e3c0157c0aff0418a5`. The release contains 13 verified
macOS Apple Silicon, signed Windows, Linux, updater, SBOM, checksum,
Windows-signature, and Sigstore assets. Packaged migration from public v1.4.0,
both 25-site favicon matrices, packaged blocker-byte verification, macOS
signing/notarization, Windows Authenticode, Electron fuses, native provenance,
the complete release manifest, and logged-out download smoke all passed.

Post-release changelog PR #156 passed all 10 checks and merged as
`58a716ba2f3ab8249fff21b6e66c92a5d6dabacf`. `npm run site:deploy` ran from a
clean checkout at that exact `origin/main` commit with its required
`--branch=main`; the canonical production changelog showed v1.5.1 and the
production Latest link resolved to the v1.5.1 release.

## What went wrong and what is now permanent

### 1. The Windows blocker failure was packaged input corruption

Windows checkouts had converted the pinned EasyList and EasyPrivacy files from
LF to CRLF. The byte-integrity gate correctly rejected those modified inputs,
which is why published v1.3.0, v1.4.0, and v1.5.0 Windows builds displayed
**Blocking could not start**. This was not an inherent Windows limitation.

**Permanent rule:** `.gitattributes`, the pre-build source check, the automatic
electron-builder `afterPack` check, and the explicit finished-`app.asar` checks
on every native workflow are release invariants. Never weaken or skip them.

### 2. A direct installer launch was mistaken for an updater-handoff test

The private Actions artifact correctly contained the signed installer,
blockmap, signature record, and `latest.yml`. The affected-machine install
proved the blocker fix, and the user confirmed the banner was gone. Later,
launching the candidate EXE directly with `/S` while v1.5.0 was running waited
indefinitely. That route does not reproduce `electron-updater`: the old app did
not discover metadata, download the artifact, emit `update-downloaded`, or call
`quitAndInstall`.

**Permanent rule:** distinguish install validation from updater validation. A
real handoff test begins inside the old packaged app and uses the exact staged
metadata, installer, and blockmap. If that feed harness is not ready, stop
claiming equivalence and report the missing evidence.

### 3. Publication proceeded with an explicit validation waiver

The exact Windows v1.5.0-to-private-candidate updater handoff remained
unverified. The repository merge safety gate correctly rejected publication
until the owner was told the specific risk. The owner then explicitly approved
shipping v1.5.1 without that final test.

**Permanent rule:** never silently convert an unperformed gate into a pass. An
owner waiver must be informed, explicit, and recorded. The next release must
close this evidence gap by exercising real public Windows updates begun inside
both v1.4.0 and v1.5.0, in addition to the normal v1.5.1-to-next path.

### 4. Agent-mode release support conflicted with the orchestration policy

The checked-in script and runbook support an explicitly approved, out-of-
sandbox Codex PTY. The surrounding safety layer rejected that immutable publish
twice, including after the user repeated the exact approval. Retrying only
cost time. After a separate approval, Codex launched the complete command in a
visible native Terminal tab; the release succeeded without asking the user to
copy or type anything.

**Permanent rule:** try agent mode at most once. If policy rejects it, explain
the constraint once and move to an automatically launched, foreground native
Terminal session after approval. Do not spoof `TERM_PROGRAM`, use a background
wrapper, or keep asking the user to reconstruct commands.

### 5. The checked-in 1Password path worked exactly as intended

The native Terminal run executed the release script's exact preflight
`OP_BIOMETRIC_UNLOCK_ENABLED=true op signin`, then reused forced desktop-app
integration for `op run`. Authentication succeeded immediately. No manual
account addition, pasted secret, standalone alternative sign-in sequence, or
`gh auth login` was needed; the existing GitHub keyring session also worked
outside the sandbox.

**Permanent rule:** let `release.sh` own both 1Password boundaries. Cancel if
`op` offers manual account addition. Check GitHub authentication outside the
sandbox before declaring the cached session expired, and use the connected
GitHub app or working Git credential before involving the user.

### 6. Changelog generation is not production deployment

`release.sh` correctly generated `site/src/data/releases.json` after the
release became public and then stopped. The generated file was committed in a
focused PR, merged after CI, and deployed from the exact new `origin/main`
commit. The production script's `--branch=main` was essential; omitting it from
a detached worktree would create a `HEAD` preview and leave
`blancbrowser.com` stale.

**Permanent rule:** release completion is: publish and smoke-check the GitHub
release; generate the changelog; commit/merge the focused changelog PR; detach
at the resulting `origin/main`; run `npm run site:deploy`; verify the canonical
domain with a no-cache request; and confirm GitHub `releases/latest` resolves
to the new tag. A Cloudflare preview URL is not production evidence.

## Proven sequence for the next release

1. Finish every product change before creating the exact signed candidate.
2. Use the private Windows validation workflow for affected-machine package
   checks; retain its complete updater metadata beside the installer.
3. Exercise real updater-driven Windows paths and record observed versions,
   responsiveness, blocking state, and relaunch result.
4. Merge only after required checks pass, unless an informed owner explicitly
   waives and records a remaining evidence gap.
5. Release from a clean checkout at exact `origin/main`. Use agent mode once;
   on orchestration-policy rejection, obtain approval and automatically launch
   the terminal-mode command in visible native Terminal.
6. Let `release.sh` perform its own 1Password preflight and `op run`; never add
   an account manually and never ask for `gh auth login` before exhausting the
   existing keyring/app/git paths.
7. Once the tag or draft exists, follow immutable recovery rules—never rerun
   the full release or overwrite native assets.
8. After publication, merge the generated changelog and deploy the exact new
   `origin/main` commit to Cloudflare branch `main`; verify the canonical site
   and Latest release target.
