# Bangs Page Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `blanc.day/bangs` explains bangs, lets visitors try one, and lists all 10,624, with a Features board tile and a homepage card, built from candidate data now and swapped to the release tag before it goes live.

**Architecture:** A generator pins the app's bang catalog and `bangs.js` at one git ref into `site/src/data/bangs.json` plus a byte copy of the module; the Astro page renders the directory server-side from that JSON and lazy-loads the same JSON (hashed asset) for the try-it box and search. Two small pure modules (directory matcher, try-it model) carry the logic and are unit-tested; browser suites check the built page. Every sentence is recorded in a candidate claims record pinned to `081c965b`, converted to the release ledger after the release.

**Tech Stack:** Astro (site/), vanilla JS modules, `node --test` (test/unit, test/site with Playwright against `npm run preview`), the existing OG card renderer.

**Spec:** `docs/superpowers/specs/2026-10-17-bangs-page-design.md`

## Global Constraints

- Branch `claude/bangs-page`; the PR stays **unmerged** until the release that ships bangs is public (spec decision 1–2). Tasks 1–8 run now; Task 9 runs only after that release.
- Candidate ref: `081c965b` (the bangs merge commit). Nothing is ever read from main's working tree for bang data.
- Counts, version and engine tags come from data, never typed by hand.
- The try-it box never navigates, opens a window, or makes a request other than loading the page's own JSON asset; no Return handler.
- Copy lines the spec fixes are verbatim: H1 **Search the site. Skip the engine.**; *Find a bang ›*; the try-it caption; the two try-it messages; the credit line; the homepage sentence and `tool-limit`; the Features tile and pop line.
- No header or footer link; no change to the app or to `bangs/`; Blubird files never committed; `build.format: 'file'` (the page is `dist/bangs.html`).
- US spelling. Commit messages end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. Pasted or very long text in the try-it box (tabs, newlines, 10,000 characters): it must not hang or overflow; the input is capped at 200 characters and multi-line paste collapses to one line. Test in Task 2 (`describeTryIt` with tab/newline input) and Task 4 (browser: paste 5,000 chars, page stays responsive, field holds 200).
2. Directory search with characters that mean something in a regex or URL (`c++`, `!yt`, `youtube.com`, `(`): matched literally, a leading `!` ignored. Test in Task 2.
3. Narrow phones (360px): no horizontal page scroll; directory rows wrap rather than overflow. Test in Task 4 (browser at 360px: `scrollWidth <= innerWidth`).
4. JavaScript on but the JSON asset fails to load: the directory still works from its HTML rows and the try-it box keeps its static prefilled state with no error shown. Test in Task 4 (route the asset to 404).
5. Searching, then *Show more*, then clearing the search: the visible count and the "showing N of M" line stay truthful. Test in Task 4.

### Task 2: Directory matcher and try-it model

**Files:**
- Create: `site/src/scripts/bangs-directory.mjs`, `site/src/scripts/bangs-tryit.mjs`
- Test: `test/unit/site-bangs-logic.test.js`

**Interfaces:**
- Consumes: `bangs.json` entry tuples (Task 1); the `Bangs` API of the byte-copied `bangs.js` (`parseBang`, `resolveBang`, `matchBangs`, `findBang`).
- Produces: `directoryRows(data) → Array<{ code, aliases, name, host, via }>` (host = `new URL(template.replace('%s','x')).host`, sorted by `name` with `localeCompare(…, 'en', { sensitivity: 'base' })`, ties by code).
- Produces: `filterBangs(rows, query: string) → rows` — query trimmed, lowercased, one leading `!` dropped, compared with `startsWith`/`includes` only (no regex). Empty → `rows` unchanged. Otherwise: rows whose code or any alias starts with the query, ordered by the shortest matching code length then code; then remaining rows whose name or host contains the query, in `rows` order.
- Produces: `describeTryIt(text: string, Bangs, entries, popular) → { kind: 'empty' } | { kind: 'bang', hint: { code, title, url }, sections } | { kind: 'picker', sections } | { kind: 'unknown-code' } | { kind: 'other' }`, where `sections` is `Array<{ section: 'popular'|'all', count, rows: Array<{ code, name, domain }> }>` built from `Bangs.matchBangs(prefix, entries, [], [], popular)` exactly as the app's `bangResults` does (no recents, no custom bangs); `title` is `` `Search ${name} for “${query}”` `` or `` `Open ${name}` ``. Input is `text.replace(/\s+/g, ' ').slice(0, 200)` before parsing.

- [ ] **Step 1: Write the failing tests**

With the real `bangs.json` and `site/src/scripts/bangs.js` loaded in a `vm` context (it publishes `window.Bangs`):
- `describeTryIt('!yt lofi', …)` → `kind 'bang'`, `hint.code 'yt'`, `hint.title 'Search YouTube for “lofi”'`, `hint.url 'https://www.youtube.com/results?search_query=lofi'`, `sections []`.
- `'!w golden retriever'` → `hint.code 'wikipedia'`; `'lofi !yt'` → same URL as `!yt lofi`; `'!yt'` → `title 'Open YouTube'`, `url 'https://www.youtube.com/'`, a section `all` listing `ytm` among its rows.
