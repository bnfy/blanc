# AppImage desktop sandbox fix and static runtime investigation

The AppImage desktop entry generated by Blanc's locked electron-builder
26.15.3 defaults to `Exec=AppRun --no-sandbox %U`. Menu integrations that retain
those arguments disable Chromium's process sandbox, even though Blanc sets
`sandbox: true` on its web contents. Electron documents that the command-line
flag overrides process sandboxing; the preference still disables the renderer's
Node environment, which is a separate protection.

The source fix explicitly sets `build.appImage.executableArgs` to `[]`. The
installed builder now generates `Exec=AppRun %U`. The packaged desktop-entry
verifier rejects sandbox-disabling flags in the main command and desktop action
commands, including single-dash forms and switches disabling the seccomp,
zygote, or WebNN compiler sandbox. It matches complete switch names with
optional values and requires a nonempty main command. The existing Linux native
workflow already runs this verifier against the extracted AppImage before
uploading release or validation artifacts.

This fix removes the unconditional desktop argument. It does **not** establish
that every Linux launch runs with Chromium's sandbox enabled.

## Launcher behavior verified locally

Both `buildLegacyFuse2AppImage` and `buildStaticRuntimeAppImage` in the installed
26.15.3 builder call the same `writeAppLauncherAndRelatedFiles` function. Its
generated `AppRun` runs `unshare -Ur true`; if that probe fails or `unshare` is
missing, it adds `--no-sandbox` before launching Electron. There is no prompt.
This also affects direct AppImage launches, so the claim that double-clicking
always preserves the sandbox needs this qualification.

A local experiment executed that generated launcher with a stub executable and
stub namespace probe; it did not launch Electron or change the system's
namespace policy:

| Probe exit | No incoming arguments | Incoming URL |
| --- | --- | --- |
| 0 | No added argument | URL forwarded unchanged |
| 1 | `--no-sandbox` added | Flag added before URL |
| 127 | `--no-sandbox` added | Flag added before URL |

These results establish launcher argument behavior, not actual Linux sandbox
status. Blanc's main process currently does not reject that fallback flag.

## Newer AppImage runtime

The locked builder already supports `build.toolsets.appimage: "1.0.3"`; no
Electron upgrade or custom runtime is needed. The v26 documentation labels it
beta and describes a static AppImage runtime that removes the host `libfuse2`
dependency. That applies to the AppImage mounting runtime, not all of Electron's
system-library requirements.

The installed builder pins the 1.0.3 toolset archive SHA-256 to
`84021a78ee214ae6fd33a2d62a92ba25542dd10bc86bf117a9b2d0bba44e7665`.
It uses zstd compression by default instead of the legacy default gzip, and
retains embedded blockmap generation. The launcher namespace fallback described
above is shared by both toolsets; migrating alone does not remove it.

The September 29 candidate kept the runtime setting unchanged while its compatibility was investigated.
Before adopting 1.0.3, build a separate Linux validation candidate and verify:

- Direct and integrated-menu launches on a host without `libfuse2`, including
  first-run setup, URL handoff, blocker startup, and close/relaunch.
- Actual renderer sandbox status with working namespaces, plus behavior on a
  host where the namespace probe fails. A successful launch alone is insufficient.
- Extracted desktop commands, packaged payloads, fuses, updater metadata, and
  an in-app AppImage update/restart from the preceding public version.

A browser policy for the existing silent unsandboxed fallback needs separate
review. Removing it can prevent Blanc from launching on restricted hosts; a
FUSE dependency change should not silently decide that policy.

Ubuntu 24.04 restricts unprivileged user namespaces through AppArmor; its
release notes describe application profiles permitting their use. Whether
Blanc's launcher probe succeeds must be observed on the affected host, rather
than inferred solely from the distribution version. Scope process inspection
to the launched Blanc process tree: an unrestricted `pgrep -f -- --type=renderer`
can select another browser's renderers. `Seccomp: 2` establishes that a process
has a seccomp filter; it does not alone establish Chromium's full namespace
and syscall sandbox. Record the renderer command lines, namespace state, and
seccomp state together.

## October 1: candidate for the reported direct-launch failure

An OMG! Ubuntu reader reported that direct AppImage launch failed even after
installing a FUSE package, while extracting the image and running `AppRun`
worked. The report does not include the terminal error or Ubuntu version.
Missing FUSE 2 is a plausible cause, not a confirmed diagnosis; the extracted
launcher also has the namespace fallback described above.

The next private candidate explicitly selects
`build.toolsets.appimage: "1.0.3"`, using the static mounting runtime supported
and hash-pinned by the locked official electron-builder release. Electron
itself remains official and unmodified. The explicit empty desktop arguments
remain in place, and the generated `AppRun` namespace fallback remains unchanged.

The Linux workflow now removes preinstalled `libfuse2` / `libfuse2t64` for
static-runtime candidates and rejects an environment that still advertises
`libfuse.so.2`. It then checks the actual AppImage's SHA-512, version, file size,
and readable embedded differential blockmap against `latest-linux.yml`, runs
two direct launch smokes, and runs the existing packaged media and installed
URL-protocol checks. Immutable release tags using the legacy runtime still
install their FUSE 2 dependency.

The candidate includes current `origin/main` through `15319a95`, including
the dependency-audit fixes from PR #444. Local validation passed 1,970 unit
tests, the 14 focused Linux/default-browser packaging tests, `npm run lint`,
`npm run substrate:check`, and the workflow's YAML/shell/inline Node syntax
checks.

The first static-runtime candidate, `ed891c06`, passed private Linux validation
[run 36871216402](https://github.com/bnfy/blanc/actions/runs/36871216402).
The runner's FUSE 2 absence gate passed, both direct AppImage launches exposed
Blanc chrome/new-tab targets and the `v1.23.0` version marker, and updater
metadata/blockmap, packaged media, installed `blanc-import`, payload, and fuse
checks passed. Release upload and provenance steps were skipped.

That run's separate required PR security check found newly indexed
`brace-expansion` advisories. The follow-up updates only that transitive
dependency within existing ranges in the desktop and tab-import-companion
lockfiles (`1.1.21`, `2.1.7`, `5.0.12`) and regenerates the root lock SBOM.
`npm run security:dependencies` passes all four workspaces with the existing
VEX accounting intact. The final native candidate will be rebuilt from those
patched inputs; its evidence is recorded below when complete.

Actual Linux
desktop-menu behavior, renderer sandbox observations, an in-app Linux updater
handoff, and confirmation on the affected machine remain pending before merge
or release. A successful no-FUSE-2 hosted launch would establish that dependency
is removed for the tested environment, not that Michael's machine is fixed.

The candidate retains version `1.23.0` solely for private validation. It is
not a public replacement for v1.23.0 and must not overwrite its immutable
release assets. Testing should use a fresh directory and a separate profile.
