# Blanc for Android: Google Play Console

How Blanc for Android is set up on Google Play, and the contract the release
script follows (`docs/superpowers/plans/2026-11-03-android-port.md`, A7 and A8;
`docs/android/release.md` runs it).

## Set up (November 15, 2026)

- **App:** "Blanc: Web Browser", package `me.bnfy.blanc`, App, Free, in the
  personal developer account. Only the account owner's Google account can create
  apps there. The Developer Program Policies and US export laws declarations are
  accepted. Play's automatic protection (an installer check Play adds to the
  app's code) is off, at the owner's request, so the bundle Play serves is the
  one the release record checksums.
- **Testers:** only people confirmed on the Android beta signup list
  (`cloudflare/newsletter-worker`, `/android-beta/members`). Their Play email list
  is attached to the closed test (Closed testing - Alpha) and nowhere else;
  internal testing has none. Nobody is invited until a release is published on
  that track. Compare the export with the Play list before each round and remove
  anyone who left.
- **Upload key:** 1Password vault Dev, Document "Blanc Android upload key"
  (file `upload.p12`, PKCS12, alias `blanc-upload`, RSA 4096,
  valid to 2054) and the item "Blanc Android upload key password". The certificate's
  SHA-256 is pinned in `chromium/android/release/upload-cert.json`. It was made on the
  owner's Mac straight into 1Password, with the password generated by 1Password:

  ```sh
  d=$(mktemp -d) && chmod 700 "$d" \
    && op item create --vault Dev --category password --title "Blanc Android upload key password" --generate-password='letters,digits,40' \
    && export BLANC_ANDROID_UPLOAD_PASSWORD="$(op read 'op://Dev/Blanc Android upload key password/password')" \
    && keytool -genkeypair -keystore "$d/upload.p12" -storetype PKCS12 -alias blanc-upload -keyalg RSA -keysize 4096 \
         -validity 10000 -dname "CN=Blanc Android upload" -storepass:env BLANC_ANDROID_UPLOAD_PASSWORD \
    && op document create "$d/upload.p12" --vault Dev --title "Blanc Android upload key" --file-name upload.p12
  rm -rf "$d"; unset BLANC_ANDROID_UPLOAD_PASSWORD
  op item edit "Blanc Android upload key" --vault Dev 'alias[text]=blanc-upload'
  ```

  The last line adds the `alias` field the release script reads (`docs/android/release.md`).

- **Play Developer API:** Google Cloud project `blanc-play-publishing`, with the
  Google Play Android Developer API enabled. Service account
  `blanc-play-upload@blanc-play-publishing.iam.gserviceaccount.com` has no Cloud
  roles; in Play it has Blanc only, with "Release apps to testing tracks" and
  read-only app information (no production rights until A9). Its JSON key is the
  1Password Document "Blanc Play API" (file `blanc-play-upload.json`), made with
  `gcloud iam service-accounts keys create` so it never sat in a downloads folder.

## Account

- **Existing account (owner, November 4, 2026):** Blanc's owner already has a
  **personal** Play Console account, created in 2023 or later. Bananify
  Creative also already has a **D-U-N-S number** (kept out of this
  repository).
- **Testing rule:** a personal account created after November 13, 2023 must
  run a **closed test with at least 12 testers opted in continuously for 14
  days** before it can apply for production
  (support.google.com/googleplay/android-developer/answer/14151465). Testers who
  leave before day 14 don't count. Unless the account turns out to predate
  that cutoff, the A8 closed beta doubles as this test: invite 15 to 20 people
  so a few dropping out doesn't restart the clock.
- **Listing name:** a personal account shows the owner's legal name and
  country, as the individual Apple enrollment does. To show Bananify Creative
  instead, Blanc would need an **organization** account (with the D-U-N-S
  number). Google's help describes no way to convert an existing personal
  account; ask Play Console support before choosing, and decide **before A7
  uploads the first build**, because the app can't move accounts easily after
  that.
- **Decision (owner, November 4, 2026): keep the personal account.** Blanc is
  published from it, and the listing shows the owner's name. No organization
  account is opened; the D-U-N-S number stays unused for now.

## App

- **Application ID:** `me.bnfy.blanc` (release). Debug builds are
  `me.bnfy.blanc.dev`, so both install side by side. Neither can change after
  the first upload.
- **Display name:** Blanc.
- **Architectures:** arm64-v8a (devices) and x86_64 (emulators). No 32-bit ARM.

## Signing

- **Play App Signing:** Google holds the app signing key. Blanc keeps only
  the **upload key**.
- **Upload key and Play API credential:** in 1Password (vault Dev). They
  never reach the build server or the repository.
- **Release-script contract (A7):** the server builds an unsigned AAB from a
  tagged commit; the owner's Mac verifies it, signs it with the upload key and
  uploads it through `op run`, with an SBOM and Sigstore record like desktop
  releases.

## Tracks

Internal (A7) → closed testing → open beta (A8) → production with staged
rollout (A9). Each promotion is the owner's explicit approval.

Once a stable version is on production, betas keep going to a testing track ahead of it: closed
testing until production access, then open testing. [`channels.md`](channels.md) has the rules and
the schedule. Production uploads need the service account's **Release to production** right for
Blanc, which the owner grants when the first stable is ready. Until then it has only "Release apps
to testing tracks" and the rights listed above.
