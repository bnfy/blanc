# macOS startup restoration scheduling

The retained intermittent failure waits in `SessionRestoreImpl::Restore` below `ChromeBrowserMainParts::PreMainMessageLoopRunImpl`. That entry starts AppKit's first application loop while native startup and the browser quit closure are still being initialized. Original signed and instrumented signed repetitions did not reproduce the failure consistently; their passes alone do not dispose of it. A separate ad-hoc diagnostic waits in Keychain authorization and is not the original failure. The original acceptance run also overlapped stapling; that overlap is not established as its cause.

For Blanc macOS process startup only, dispatch synchronous restoration as a non-nestable task, allowing native startup to unwind into the browser main loop first. The retained failure's pre-main-loop entry is removed. Keep process and profile alive until dispatch completes. Copy command line, startup tabs and first-run inputs; hold a weak profile reference and recheck shutdown/creation permission. Reconstruct a short-lived creator only for the existing RestoreOrCreateBrowser helper. Never capture the original stack-owned creator.

The same native helper retains encryption readiness, the existing recovery screen and Quit contract, session restoration, empty/error fallback and app restoration. The completion callback preserves shared-group/update notices. No empty session is invented at a timeout and no concurrent retry read is introduced. New profiles, private windows and explicit non-restore startup choices retain their prior path. Other platforms and ordinary Chromium retain synchronous startup behavior.

Acceptance requires final signed frozen-bundle normal/private/preferences, malformed-record/restart, encrypted recovery, failed-write retry, cancellation, Split View and profile/owner teardown checks. Inspect a restored start's call stack to verify it originates from the main-loop task rather than PreMainMessageLoopRunImpl. Retain original failures and initial test/setup failures. Remove temporary diagnostics, restore the normal binary incrementally and verify a zero-action guard before packaging/signing. Close L6 only after this qualification and an explicit mapping of unchanged owner-approved UI evidence. Google baseline remains separate; latency and Electron remain pending.
