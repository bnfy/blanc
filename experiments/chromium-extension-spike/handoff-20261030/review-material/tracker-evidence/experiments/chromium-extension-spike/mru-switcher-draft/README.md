# Recent-tab switcher draft — 2026-10-30

Reference: published Blanc v1.45.1, source `85883b1afa11375e1300130914d6f40c5388af21`, verified against the latest release API. Shipping `src/main/tab-switcher.js` and `main.js` implement a window-local Ctrl+Tab session: holding Control steps over candidates, release activates the chosen tab, Escape cancels, splits are one candidate and quiet tabs are not woken by preview. The shipping platform gate offers recent order on Linux and Windows, with macOS using list order pending native key-release proof. List order also remains available via Ctrl+PageDown/PageUp.

Chromium 158 already has `kCtrlTabMru` and Settings' `browser.ctrl_tab_mru` preference; its `CycleToMruTab` immediately activates the single most recently focused inactive tab on each command, for both directions. That is useful native groundwork but is not the released held-key session, card, close-pick interaction or release-to-land behavior. A simple rebrand/default change would not achieve the contract. The native option may still serve as a building block; avoid enabling it as a parity claim.

`shipping-tab-switcher.cjs` is the exact pure shipping implementation, SHA-256 `1d96b4e0c51c3b5905b0958ef4bd992de1c9fc0cd4ff9cc3523550e5c73605e8`. `snapshot-controller.cjs` (SHA `feddf067c9ea0e4a92f134ace16369fed020453343a2543f6834e410641ae518`) adapts complete native-style snapshots to per-window ephemeral history and the shipping state machine. It invalidates malformed snapshots, drops moved/closed IDs, and cancels a pending choice after an external activation or split topology change. `node --test .../snapshot-controller.test.cjs` passes seven focused model tests, SHA `080478c7b74fc17366f181eab607ba19c1c227c43f53a6e20e2dfac22dc4829e`. No build, native source, running app or profile changed.

This is a draft with synthetic snapshots only, not integrated, packaged, or a user-visible feature. Its CommonJS code needs a deliberate browser/native integration. Snapshot ordering and complete, timely delivery need real native lifecycle and split focus proof; a native final activation must independently revalidate the target, originating window, profile and private context, including races between snapshot and action. Native key down/up routing, repeat, modifier release, cancel on blur, close-pick, click-to-land, card timing/visual/accessibility, Settings persistence/defaults, restored tabs, quiet/Glance/group behavior and real keyboard checks on each desktop platform remain open. macOS must continue to match shipping's platform gate unless the owner changes the target. No feature or parity acceptance is asserted.


## Shipping-style card and browser composition

`switcher-card.js` (SHA `be7c643761032f941c5bacdc7c92327f237f6e526403f472f0df0f24bfe77df8`) renders the shipping listbox, selection, title/host, live announcement, click and focus-preservation behavior with shipping-derived CSS `switcher-card.css` (SHA `8817974badaff8c4947e63fcb7dcdaba5e331109d10dfa4a5f148d903cae9702`). It uses text nodes for site-controlled titles, fails closed for a missing selected tab, and ignores clicks from replaced card generations. Favicon and translation are injected by the eventual host; full shipping visual/accessibility parity remains untested.

`bundle-controller.cjs` deterministically wraps the exact shipping model and current adapter into `snapshot-controller.browser.js` SHA `b51809b2e8eb24a5014de0aa527a50c6797baa4ffd9a174f6c88392863dfa937`; `--check` verifies it. The adapter now copies session data before handing it to views so a view cannot mutate selection. Seven unit tests pass. `switcher-card-composition-v2-result.json` records the actual isolated headless Chromium DOM fixture: focus retained, selected option and announcements, reduced motion, stale click, text escaping, missing selection, and simulated controller-to-card release/click selection passed. The fixture injects tab state and actions; it is not actual key routing, real native tab activation, a visual comparison, screen-reader proof, or product/cross-platform acceptance. It launched the existing 158 binary headlessly in a disposable Playwright context; the open development profile was not used.

Native source inspection shows tab web contents forward `PreHandleKeyboardEvent` through `BrowserWebContentsDelegate` and `BrowserView`, while the Island's separate delegate handles unhandled key events. Shipping requires Control release from every owned surface; Chromium's native event path and command handling must be measured for key-down/up delivery and double dispatch before choosing an interception point. Do not wire or enable this UI until native owned-window/profile validation, release detection and safe cancellation are proven.

## Input-path probe and card timing — 2026-10-30

`synthetic-key-probe-v3-result.json` records a headless, isolated Mac Chromium run on framework `237242c7e2ddfab4d8fa49528b98a130c1e11dff9f80ffa1db39c0cdc8c06fa1`, with v11 assets. CDP synthesized Control+A as a control, then Control+Tab on a local page and on the Island host. Both surfaces received the generated Control key-up, but the active tab did not change in either case. This establishes only the behavior of the synthetic path; it does **not** prove native accelerator execution or physical modifier release, and is not Linux/Windows evidence. The earlier `synthetic-key-probe-result.json` failure came from evaluating the host before initialization; its exited profile and log remain. V2 and V3 exited 0 and their own successful profiles were removed. The running development app and profile were untouched.

`card-scheduler.js` SHA `5c39dbd63fd828f474e82c8544d715adfe5a7f82a4daa643e7af282731fd54eb` implements the shipping 150 ms first-step delay, immediate display on a second step, busy-Island suppression, per-window state and cancellation. Six synthetic timer tests pass, including rapid cancellation, stale callbacks and independent windows. A host integration must ensure show/update/hide affect only a still-owned switcher surface. The scheduler remains unintegrated and has not been observed with real keyboard input or a native overlay.

## Trusted-input routing draft — 2026-10-30

The Chromium source includes a window-scoped Aura pre-target event handler pattern (`WindowHelpBubbleEventRelayAura`), a possible Windows/Linux input point. Whether that hook sees real key-down and Control-release events from every relevant web or native surface, and how it interacts with Chromium's accelerator processing, remains unmeasured. macOS uses a different path and shipping keeps recent-order disabled there. No hook is installed by this draft.

`input-router.js` SHA `5f7fe414a90db101a77edb78b9176d53fd1960334a33936747b17a097c283231` implements semantics for **already trusted, window-owned native events**: Ctrl+Tab and reverse/repeats, release-to-land, Escape/blur cancellation, platform gating and a close-picked intent. It does not itself consume OS keys or authorize actions. For an asynchronous close, it defers release until an authoritative new snapshot confirms the selected tab disappeared; a token prevents an old close acknowledgement from affecting a later session, and an unconfirmed close cancels. This defensive deferred-close behavior needs validation against shipping behavior and native quit vetoes. Seven focused tests in `input-router.test.cjs` pass. The future native owner must independently validate source surface, window, profile/private ownership and target immediately before any close or activation; never accept equivalent events from arbitrary page script.

The isolated `switcher-card-composition-v3-result.json` passes a browser DOM composition using **simulated trusted-event calls**, the scheduler, shipping model, card and test activation callback: a quick tap lands without a card and a held two-step shows the card then lands. It is not native key, OS accelerator, real browser-tab activation, screenshot parity, screen-reader or platform evidence. No runtime integration, native source build or dev promotion occurred.
