# Shipping search-provider resolver candidate

GitHub's latest-release API on October 29 identified Blanc `v1.45.0`, target commit `6f1bc523d2f0d432d5c4119b9f7ec22a324dbd2d`; the locally available commit was inspected. The release's default is DuckDuckGo and its five built-in choices are DuckDuckGo, Google, Bing, Brave and Kagi. In contrast the active Chromium host currently constructs Google URLs for both its typed-search fallback and explicit search; it does not consult Chromium Settings. A blanket hardcoded switch would overwrite the user's effective choice and would not address settings or policy.

This **unregistered draft** composes the existing selected-custom validator with exact Chromium 158 stock provider identities and full literal patterns. The five explicit user-selected stock providers resolve to the release's metadata-free endpoints with shipping's `encodeURIComponent` encoding, rather than expanding Chromium's Google attribution substitutions. Effective mandatory/recommended policy and user-created custom addresses go through the existing literal validator. Extension-controlled or unsupported providers, changed snapshots, altered stock patterns, post requests, and invalid/oversized input fail without a URL. A Chromium `FROM_FALLBACK` value returns `kNeedsInitialization`: this value can reflect region or configured overrides, and cannot by itself establish a genuinely new Blanc profile or authorize overwriting a pre-existing choice. The UI-thread adapter reads the actual regular-profile service, maps primary private sessions to that regular selection, distinguishes an unloaded service, and rechecks before returning a ready URL. It does not call navigation.

`generate-shipping-vectors.cjs` derives 75 synthetic query/URL vectors from the exact release's real `SEARCH_ENGINES` table. `run4` passes 105 synthetic checks using recompiled draft sources and existing 158 cached libraries, including those vectors, altered identities, policy and custom addresses, extension takeover, changed snapshots and invalid input. The actual `Profile`/`TemplateURLService` adapter passes a 158-header syntax check; it has not been linked or exercised in a browser. Commands, hashes, logs and public latest-release metadata are in `Chromium Preview/evidence/search-shipping-provider-20261029/`. A first parser inspection using strict Python JSON failed on Chromium's commented definitions file; the later source inspection used its literal definitions. No user query, profile, network request, native build or live app was used by the resolver checks.

Do not expose this resolver to the current renderer bridge as-is. It does not establish trusted input, distinguish typed URL intent from query, provide native confirmation for ambiguous private paths, bind to the actual host frame/tab/document/gesture or observe navigation completion. The same-origin host-child boundary still needs review and adversarial tests. The route's existing observer and capability drafts must be composed with the actual browser owner, and provider readiness failures need visible, localized retry behavior without replaying a stale query. An initialization path must prove a genuinely fresh profile and preserve existing selections, enterprise policy, extension control, regional constraints and restart behavior before setting DuckDuckGo; `FROM_FALLBACK` alone is insufficient. Actual Settings selection, profile restart, private routing, built-in and literal-provider policy changes, lifecycle/ABA races, migration, Sync and cross-platform behavior all require isolated browser verification. No full search or shipping-parity acceptance is claimed.
