# Start Page v5 layout and clock candidate — isolated

The v4 assets and manifest were verified before copying to `Chromium Preview/evidence/start-page-layout-clock-20261028/assets-v5`. Only the HTML, page JS, adapter JS and prototype CSS differ; the manifest and receipt bind their hashes. GitHub latest release was verified during this same parity work as v1.44.1, source `3b0c000b569ee33a1548dd1b9a60817fae9288a6`.

Layout selection now waits for the native write acknowledgement before showing the choice. While a write is outstanding the controls remain keyboard-focusable, use `aria-disabled` and are visually dimmed; further clicks are ignored. A failed or timed-out request presents a visible polite status without asserting the write did not happen. Each completion triggers a read of the shared setting, including changes in other windows. Layout and clock reads use epochs to avoid older in-flight reads overwriting a newer local control write. An invalid layout acknowledgement is rejected. The native acknowledgement is not proof of a completed disk flush.

A failed background clock read no longer replaces a known value with defaults or publishes the fallback. It shows a polite status, clears it on a successful read or confirmed clock write, and leaves the previous value intact. No stored clock preference is changed by the read failure.

Nine focused VM tests passed against extracted actual handlers/read/write functions, including concurrent clicks, write failure and subsequent retry, status visibility, stale layout and clock read rejection, failed clock read preserving a prior value, a confirmed clock write invalidating an older read, and structural accessible status checks. Results and exact byte hashes are in `test-final.log` and `receipt.json`. Both scripts passed `node --check`. The tests use fake asynchronous native calls and DOM; they do not prove native IPC ordering, actual rendering, physical keyboard/VoiceOver behavior, cross-window behavior, or persisted writes.

Limitations: the two new status messages are English-only, so localization is unfinished. Other pages and windows can change shared settings independently, and delayed native writes/timeouts require real-browser race coverage; the observer reconciliation is best effort. Other v4 recovery limitations persist. No native source, output, live assets or permanent profiles were changed. The candidate remains isolated and is not release or feature parity acceptance.

## Focused real-browser follow-up

`v5-browser1.json` passed in a fresh synthetic regular profile using exact v5 assets and framework `30877fc2...`. A test-only wrapper delayed and rejected a layout write: while outstanding, the visible layout stayed Billboard, all controls had `aria-disabled`, and a second programmatic click did not dispatch another write. After rejection, the status appeared and controls were available; restoring the real adapter allowed a native Shelf write and subsequent native readback. To exercise the clock failure, a test-only `chrome.send` wrapper returned a failure to the first `clockRead` instead of issuing it. The status appeared, and a later real read returned the unchanged Flex setting and cleared the status. The browser exited normally. These are injected renderer/IPC failures, not real service failures, disk-flush proof, cross-window ordering or physical accessibility.

V5's private-copy styling is unchanged from v4: the only addition to `newtab-prototype.css` is `.layout-preview[aria-disabled="true"]` styling; the v4 private text check is not claimed as a v5 runtime test. `browser-receipt.json` records the v5 manifest, framework, script and result hashes. No native output, live browser/profile or Google baseline was touched.
