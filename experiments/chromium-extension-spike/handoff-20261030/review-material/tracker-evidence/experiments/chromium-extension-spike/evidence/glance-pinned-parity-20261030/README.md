# Glance Keep as Split: pin and group parity

Shipping source: Blanc v1.45.1 commit `85883b1afa11375e1300130914d6f40c5388af21`. `main.js` `keepGlanceAsSplit` creates a 50/50 split led by the active tab; `createSplitFromTabs` assigns the initiator group to both and calls `splitPinned` before `markPinned` on each member. `markPinned` initializes each newly pinned tab's pinned home. The exact released pure model and its dependency are saved under `shipping/`; `shipping-pin-matrix.json` executes the actual `splitPinned` on all four inputs and records an OR truth table. This is model evidence, not browser behavior.

The staged Glance v15 currently rejects **either pinned tab** before conversion. Separately, the inspected Chromium 158 `TabStripModel::AddToNewSplit` and `AddToSplitImpl` use the first (main) tab as the group and pin pivot. Removing the rejection alone would therefore unpin an already pinned reference when the main tab is unpinned, contrary to shipping. The current source `tab_strip_model.cc` SHA-256 is `45ea41d8d2bb2dbc468ab15001dd4a42b26aeed1507abb2b2534f89770e86e82`; the staged Island source SHA-256 is `624bca254f039ea19b09a0590096d6f34e0d6e54b3c67a498e46977e28bd3b2a`.

The active build contains a whole-pair pin repair that has not yet passed its affected checks. Its `SetSplitPinnedImpl` passes `std::nullopt` for group when moving a split; a simple post-conversion pin may therefore drop the main group, and any implementation must also preserve pinned-home behavior. Do not remove the guard or claim parity based only on the pin matrix. After the approved build and its existing affected checks pass, implement and exercise all four combinations, both main/reference orderings, existing versus newly created pinned homes, and main-group/reference-group cases in regular and private windows. Verify that no extra tab changes, that the correct group survives where shipping permits it, and that cancellation/failure cannot leave a partially moved pair. Windows/Linux remain open.
