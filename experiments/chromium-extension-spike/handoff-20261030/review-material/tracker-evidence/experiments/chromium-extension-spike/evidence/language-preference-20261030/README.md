# Shared interface-language preference: source implementation

## Explicit retry for an unconfirmed choice — 2026-10-30

After a failed disk write the native preference can retain the newly selected value in memory. Re-selecting that same option may not emit a change event, so the prior Settings UI could display “Try again” without an actionable retry. The staged UI now shows an explicit retry button while the value is unconfirmed, disables it during a write, hides relaunch until confirmation, and clears the uncertainty when a later confirmed write succeeds. The button uses the existing released `ws.editor.retry` translation, present in all six supported catalogs. Four focused synthetic Settings tests pass, including failure that retains the selected value followed by a same-value retry; `Chromium Preview/evidence/glance-language-assets-v2-20261030/retry-test-result.json` SHA `9c6e5559b3412367c0020931ac392801eb58cbab9a8b1424d95cb5a3ff51352d`.

The mocked tests do not establish real native write failure, actual UI accessibility, browser lifecycle or restart behavior. The combined native build remains stopped at the live-scope guard while the owner decision is pending.

## Rejected disk-check task — 2026-10-30

The unbuilt language handler now checks the return from Chromium's `ThreadPool::PostTaskAndReplyWithResult`. If the disk-readback task is rejected during shutdown, it clears the pending flag, keeps the write unconfirmed and reports a retryable error to a still-live Settings document. It rechecks the weak handler after notifications before replying in both the rejection and normal completion paths. This avoids a permanently pending process state when posting is rejected; it does not claim the write reached disk.

## Write-confirmation correction

Source inspection of Chromium 158 `JsonPrefStore::CommitPendingWrite` showed its reply callback only orders work after queued disk operations and carries no write-success result. The previous source reply therefore could not establish the shipping contract's durable write. Native source now serializes language writes, marks them unconfirmed, and after that barrier reads the bounded Local State file on a worker, accepting only the expected persisted string plus a matching current preference. Missing, malformed or mismatched data is unconfirmed; retry forces a new write. The UI reports uncertainty and suppresses relaunch while a write is pending or unconfirmed. An explicit relaunch rechecks the selected preference after the write queue drains. If an initiating Settings document closes before verification, other supported Settings documents poll for the final state without rebuilding unchanged options. The staged 158 preference hook now refuses an existing differently defined registration rather than adding a duplicate.

Four preference/hook tests and three synthetic UI tests pass. Scripted actual Settings DOM checks with a **simulated** bridge pass unconfirmed-write/relaunch suppression in regular and private contexts, and simulated other-window completion is picked up without rebuilding options in a separate regular fixture. Both unconfirmed-write fixtures and the poll fixture exited zero and their passed profiles were removed. Exact fixture manifests and current source hashes are recorded in `write-confirmation-result.json`; raw evidence is under `Chromium Preview/evidence/language-write-confirmation-ui-fixture-20261030` and `language-poll-ui-fixture-20261030`.

The native path remains unbuilt: these tests do not prove disk-readback, failure handling, OS-level races, actual cross-window or quit-veto behavior. An unconfirmed write is not automatically rolled back to the old preference; later filesystem replacement and task shutdown behavior remain unqualified. Full Settings routing, localized uncertainty text, explicit OS language/region, accessibility, Windows/Linux and promotion remain open. No real profile, output, development session or signed artifact was changed.
