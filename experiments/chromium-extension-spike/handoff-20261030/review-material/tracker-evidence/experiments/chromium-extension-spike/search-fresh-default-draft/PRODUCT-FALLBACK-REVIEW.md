# Chromium product-level search fallback review — 2026-10-29

Current published release was reverified as Blanc v1.45.0, tag commit `6f1bc523d2f0d432d5c4119b9f7ec22a324dbd2d`; shipping `src/main/settings.js` sets `searchEngine: 'duckduckgo'`, and that setting is included in shipping Sync. The retained Chromium selected-provider candidate honors the currently effective native provider but does not initialize the shipping default.

## Native source points

- `components/search_engines/template_url_prepopulate_data.cc:357` implements `GetPrepopulatedFallbackSearch` by calling `FindPrepopulatedEngineInternal` with `google.id` and `use_first_as_fallback=true`. That helper selects Google from the supplied list or its first element. `GetPrepopulatedEngines` first uses `kSearchProviderOverrides` when present, then the native regional list. Consequently, changing `google.id` to DuckDuckGo is **not merely a first-run setting** and can also change the fallback selected from a provider override list.
- `components/search_engines/template_url_prepopulate_data_resolver.cc:GetFallbackSearch` supplies that result to `DefaultSearchManager::LoadPrepopulatedFallbackSearch`. `DefaultSearchManager::GetDefaultSearchEngine` gives precedence to mandatory policy, recommended policy, extension, user preference, then `FROM_FALLBACK`. A pure built-in fallback change ordinarily leaves higher-priority effective providers selected, but changes every existing profile still using the old native fallback. An existing profile's unchanged Google fallback is still an existing provider even though it was not explicitly selected. The requested preservation rule therefore rules out an unconditional global substitution.
- `TemplateURLService::ApplyDefaultSearchChange` handles `FROM_FALLBACK` by finding/updating or adding a prepopulated provider in the search model; it does not invoke `SetUserSelectedDefaultSearchProvider` in that branch. The `FROM_USER` branch reconciles a user-pref provider and writes its GUID. Do not infer that all prepopulated database or Sync behavior is unchanged: reconciliation and account synchronization require real tests. A product-wide fallback might avoid explicitly writing a user choice but still changes the effective search and model behavior for existing users.
- `SearchEngineChoiceService::EvaluateSearchProviderChoice` around line 1215 treats a non-Google prepopulated provider as an existing choice when `should_preserve_non_google_dse` is enabled; dynamic eligibility maps that to `kHasNonGoogleSearchEngine` rather than `kEligible`. Changing fallback can therefore change whether an eligible person sees a choice screen. Region, policy, restore and configuration paths must remain intact; an OS-configured locale is not proof of physical location.
- The 158 DuckDuckGo catalog entry (`third_party/search_engines_data/resources/definitions/prepopulated_engines.json`, id 92) uses the correct released search template, but also includes native suggestion and New Tab URLs. Verify that shipping Island suggestions, private-mode request behavior and Blanc Start Page remain correct; adopting the native entry is not by itself parity. Some regional lists or provider overrides may omit or alter it. Do not silently add a third-party endpoint or use a different provider.
- `chrome/browser/search_engines/template_url_service_factory.cc` redirects regular off-the-record and Guest contexts to their original profile. A shared fallback modification can affect regular, private and Guest behavior; the shipping/private privacy contract is not established merely by choosing the same provider.

## Configuration alternatives and limits

1. **Product-wide native fallback:** technically small, shared by macOS, Windows and Linux, and retains native precedence for explicit user, extension and policy selections. It fails the requirement to preserve an existing `FROM_FALLBACK` provider, may disturb overridden lists and choice-screen eligibility, and has unqualified model/Sync/suggestions effects. It is not a safe direct solution under the current request.
2. **Registered default search dictionary:** changing `DefaultSearchManager::RegisterProfilePrefs` alters the registered default for existing profiles as well as new ones. `LoadDefaultSearchEngineFromPrefs` treats a valid nonempty dictionary as `prefs_default_search_`; it can take user-source semantics rather than remaining an ordinary fallback. It still needs choice/Sync analysis and does not identify genuinely fresh profiles.
3. **Distribution `initial_preferences`:** `ChromeBrowserMainParts::ApplyFirstRunPrefs` / `first_run::ProcessInitialPreferences` can seed the default profile before normal profile initialization on desktop, but `first_run.h:143` explicitly says that path overwrites existing Preferences and is only meant for first run. `ProfilePrefStoreManager::InitializePrefsFromMasterPrefs` creates the profile directory and serializes a combined Preferences file; it is not a non-destructive fresh-profile detector. It seeds the default profile rather than every later secondary profile and may act as an explicit user preference with native choice/Sync implications. Packaging and installer behavior differ by OS; no bundle or installer is changed here. It is not an acceptable automatic replacement for existing-profile protection without an independently verified non-overwrite/creation contract.
4. **Product fallback selected by a trustworthy per-profile cohort:** potentially avoids persisting an automatic choice and can share a native implementation across platforms. To preserve all existing effective fallbacks, however, the cohort must reliably distinguish newly created profiles from existing, imported, restored, damaged, or copied profiles and remain correct across crashes/restarts. A registered default, `Profile::IsNewProfile()`, a missing Preferences file, first-run sentinel, or untrusted marker alone cannot establish that. A provenance signal or non-destructive first-run creation contract is still needed, even if the final provider is injected through the native fallback resolver rather than mutating a user pref. There is no verified source hook providing that signal in this checkout yet. This is the preferred direction to explore after the provenance boundary is resolved; it is a design candidate, not implemented or proven.

The memory-only exclusive-directory proof experiment in `PROFILE-LIFECYCLE.md` is one possible signal, with explicit same-user race, blocking-I/O, restart and Windows limitations; it should not be staged or assumed to solve the cohort. Its current `SetUserSelectedDefaultSearchProvider` adapter is an alternative, **not** the same as a pure fallback configuration, and could make a user-source choice eligible for synchronization. Neither path currently meets full shipping parity.

## Focused acceptance needed before any build or promotion

Use native service/unit tests plus independently isolated browser checks for: new initial and secondary regular profiles; an existing Google `FROM_FALLBACK` profile and existing explicit Google/other/custom users; no-file/corrupt/restored/copied profiles; mandatory/recommended policy, extension and user changes during initialization; overridden engine lists and regions with and without the exact DDG entry; eligible/ineligible/unknown native choice-screen state; restart, crash and migration; local/account Sync bootstrap and later sign-in without overriding a prior remote choice; regular/private/Guest behavior; actual Settings selection and visible result; first query before initialization and cancellation; suggestions/private network requests and Blanc Start Page. Include macOS, Windows and Linux where shipped. Use synthetic queries, preserve raw failures, and distinguish a constrained exploratory loopback check from independently enforced outbound isolation.

No fallback source, build graph, preferences, installer, profile or app was modified, and no browser or build ran during this review. Latest source identity is recorded in `release-verification.json`; the local Git tag itself is absent but GitHub's tag ref resolves to the cached commit. Electron remains paused, Google baseline separate and latency deferred.
