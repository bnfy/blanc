## Native extraction guard draft — 2026-10-30

This is **not a compiled or integrated feature**. No runtime test establishes that navigation, document replacement, frame lifecycle, source movement, window/profile destruction, visibility, private contexts, timeouts or malicious result shapes are correctly handled. Reserving the world in the real source also requires review of the extension world range and synchronized Android enum. Its conservative eligibility and byte limits may differ from shipping and need review. ## Address preflight and mapped-address gap — 2026-10-30

`shipping/dark-websites.js` is the exact v1.45.1 source used by the shipping Reader address decision (SHA-256 `b64412ed9fd67422c1b055f4a4700b1a73d43e83530bb37f73feb0ac6fe58385`). Chromium 158 documents `net::IPAddress::IsPubliclyRoutable` as treating IPv4-mapped IPv6 as publicly routable; it cannot alone enforce shipping's rejection of private mapped addresses. A resolution check also cannot substitute for pinning the actual socket to an approved resolved address.

`native/reader_address_policy.h` and `.cc` are a standalone binary-address preflight implementing shipping's blocked IPv4 and IPv6 ranges and requiring every resolved address to pass. They conservatively reject all IPv4-mapped IPv6 values, including public mappings that shipping accepts when written in dotted notation; this is an explicit, unresolved compatibility difference. Invalid and empty answer sets fail closed. The isolated executable exercises reserved ranges, boundaries and mixed answer sets; `native/reader-address-policy-result.json` records compilation and execution. `native/reader-address-oracle-result.json` compares 10,024 non-mapped addresses with the exact shipping JS, with zero mismatches, and separately records the intentional mapped difference. The pinned linker warned about missing libLTO but returned success.

These are synthetic, standalone checks, not proof of Chromium's resolver representation, source-profile proxy and blocker decisions, redirects, DNS-rebinding resistance, socket pinning, certificate validation, cookies or lifecycle security. No browser request uses this draft. Integrate only with a source-bound, policy-revalidated transport that pins a validated address while preserving hostname-based TLS validation; use the real decoder and all remaining protections recorded above.

Chromium 158 source review identifies a possible transport path: `NetworkContext::CreateTCPConnectedSocket` accepts an explicit `AddressList` and returns the connected peer; `TCPConnectedSocket::UpgradeToTLS` takes a separate `HostPortPair`. `tls_client_socket.cc` passes that pair to `CreateSSLClientSocket`, and `TLSClientSocketOptions.unsafely_skip_cert_verification` defaults false. `LookUpProxyForURL` and `ResolveHost` accept the frame's network anonymization key. This is a candidate, not a tested implementation or a security proof: the source-context policy, selected peer validation, TLS hostname and certificate behavior, redirects, HTTP framing, content limits, cancellation and actual browser tests still need verification. In particular a raw socket would require a safe HTTP implementation, so compare it with other native options before choosing.


## Concurrent image pixel reservations — 2026-10-30

The v5 image budget supersedes v3: header SHA-256 `072ab0f3567e0a6dd693a5909957ffbd89867e758b62e6ec68f520c38eeb7b66`, implementation SHA-256 `7e2b8763be250a6c9a64ef0acd6d09b7482e964e61a82f09a6fd5aaf8b2d4fbe`. Earlier code checked only committed pixels during preflight, so concurrent jobs could all begin decoding even if their combined declared dimensions exceeded the 32 Mi-pixel total. It now reserves validated header pixels before admitting each decode, keeps other in-flight reservations when committing actual dimensions, and releases reservations on rejection, expiry and close. A trusted sandboxed decoder must independently enforce dimensions before allocating, since a header preflight alone cannot bound a decoder that ignores or misinterprets the header.

`native/reader-image-budget-test-v5-result.json` records a passing standalone build and focused execution, including concurrent admission, released reservations, competing commits and timeout/close cleanup. The v4 test failed because its test incorrectly expected rejection at exactly the allowed total; v4 inputs and log remain preserved, and the corrected v5 test covers a true over-limit case. The linker emitted the existing missing libLTO warning. This remains an isolated accounting draft: no actual decoder, network, scheduler, real cancellation or browser is tested.


## Candidate bounded decoder path — 2026-10-30

Chromium 158's `ImageDecoderImpl::DecodeImage` calls `WebImage::FromData` before `ResizeImage` applies `max_size_in_bytes`. That parameter therefore bounds the returned bitmap after decode; it is not proof of a pre-allocation pixel cap. The normal Blink `ImageDecoder` `max_decoded_bytes` path also cannot be assumed to enforce a hard first-frame bound on every platform: its explicit decoded-size rejection is conditional on Fuchsia, and other code uses it for cache purging.

`native/bounded-decoder-patch/candidate.patch` (SHA-256 `88fd816badb20e7ebec8e88986a20998485683123c49b99a793e150624bb6c1b`) proposes a separate data-decoder method and Blink entry point: bound encoded input and the caller-supplied limit, check the same decoder's reported original, decoded and first-frame dimensions before requesting the first raster frame, and recheck the resulting bitmap. It retains orientation handling. The patch does not change the existing generic decode API. Its preimages, candidate files and generator are retained; `patch-check.json` records clean application to a copy, candidate hashes and unchanged active-source hashes. The initial candidate used a nonexistent `BigBuffer.empty()` method; its patch and generator are retained in `v1/`, and the current patch uses `size()`. Generator AST parsing passed; `py_compile` failed because the sandbox denied the system Python cache directory, as recorded in `generator-check.json`.

This is a proposed change, not compiled or run. Dimension parsing, frame metadata, animation, codec edge cases, orientation allocations, resource-process isolation, IPC serialization, cancellation, real security tests and Windows/Linux behavior remain unverified. It does not establish a strict total-process memory bound; malicious decoder behavior and metadata allocation need separate analysis. Do not connect it until the full blocker, DNS/pinning, proxy and ownership path and decoder tests are ready.

## Budget-to-decoder limit contract — 2026-10-30
