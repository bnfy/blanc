# Isolated native cohort fallback candidate — 2026-10-29

This is a review candidate only. No Chromium source was staged, no build or browser test was run, and no profile was modified. Shipping reference: latest published v1.45.0, tag source 6f1bc523d2f0d432d5c4119b9f7ec22a324dbd2d; shipped setting defaults to DuckDuckGo and is synced. Latest release was rechecked via GitHub on this date. `source-hashes.json` identifies exact live 158 inputs and generated candidate copies; `make_candidate.py` refuses unexpected source shapes. It does not install them.

`default_search_manager.cc/.h` adds an ordinary, non-syncable, profile-local integer preference, default zero (legacy), and refreshes the native fallback on cohort change. `template_url_prepopulate_data_resolver.cc` proposes DDG only when marker 1 is user-controlled, the provider-override pref is untouched, both native and valid OS country indicate outside choice regions, and the regional list contains exactly one id 92 with the expected GET template and no POST parameters. Otherwise it returns the unchanged native fallback. DefaultSearchManager's existing policy, recommended policy, extension and user priority is not altered. Settings, explicit choices, and the existing synced default preference remain independent of the cohort. No custom signing, keys, anti-rollback service, or device anchor is proposed.

**Enrollment draft, not wired:** `enrollment_candidate.{h,cc}` sketches a one-shot writer requiring the earlier exclusive-directory proof, a fully initialized writable *new* regular (not OTR) pref store, untouched cohort/default/GUID/override prefs, and an `ImportResolution` capability bound to the same live profile. Its constructor is private to a future importer owner; no actual code can mint a reviewed resolution yet. It never calls `SetUserSelectedDefaultSearchProvider`; it sets only the local cohort pref, returning “set in memory, not durable.” Observer reentrancy may destroy the profile, so it does not touch profile/prefs after the write. No product hook, coordinator, retry or import-completion integration exists. The filesystem proof only covers POSIX and requires validated parent/coordinated creation, is not trustworthy against adversarial same-user replacement in its mkdir/open gap, and is untested across the real creation path. Do not call from an invented boolean or `IsNewProfile()` check.

`Profile::CreateProfile` precedes PrefService construction; `ProfileImpl::OnSyncToSigninMigrationMaybeCompleted` runs `InitProfileUserPrefs` and then `CreateBrowserContextServices`, while `OnPrefsLoaded` precedes `OnLocaleReady` and migration. An exclusive-create proof would have to enter the constructor before synchronous `OnPrefsLoaded`. First-run native `ImportFromSourceProfile` can invoke a blocking importer after a profile already exists, and `ProfileWriter::AddKeywords` merges search engines rather than proving no import. No existing `no import is planned or in flight` lifecycle boundary was found; identity/Sync and user decisions can also arrive asynchronously. Enrollment must be single-sequence, canceled on profile shutdown, and decided before user navigation or else UI must explicitly handle any default change. Deferred imports can invalidate an earlier decision. These facts prevent calling the writer today. Existing profiles (including installer-precreated directories), ambiguous/failed creation and imports without a committed cohort remain legacy. A committed cohort copied with its whole profile retains its cohort; a copy or restore from before its commit cannot reliably be distinguished from legacy. Never infer freshness solely from missing Preferences.

Preference writes are asynchronous and the completion callback is not proof against power loss. A crash before durable persistence may revert the marker to legacy and yield the native fallback after restart. No automatic re-enrollment is safe without independently proven provenance; avoid claiming crash-proof DDG default or sending a first search to an unexpected provider. A complete product integration must decide how to present or hold searches when such ambiguity exists. Pending Sync may later supply a higher-priority user default; test startup races and effective routing, including before Sync settles. Preference is not itself synced, unlike shipping's synced setting. A normal fresh install may therefore differ across devices until explicit native Sync resolution. The conditions above are only conservative gates: OS locale is not proof of physical location, regional service initialization/changes, choice-screen handling, existing locale overrides and Sync lifecycle remain unverified.

**Deleted or edited engine — unresolved blocker:** after the model loads, the draft withholds a newly introduced DDG fallback when id 92 is missing or its matching row is not safe for autoreplace. Before model load it also withholds that fallback, then rechecks the current effective source on model completion. This is not a complete deletion fix: `GetSearchProvidersUsingKeywordResult` performs built-in engine reconciliation before `ChangeToLoadedState`; when country/data version changes or decryption fails, reconciliation may add a previously absent id-92 row to WebData before this draft sees it. The candidate can therefore still recreate a deleted engine and mistakenly treat the recreated row as safe. No staging or parity claim until raw persisted-row provenance and that merge side effect are resolved and tested. A truly fresh profile also starts with no row, so simply rejecting every absent raw row would withhold DDG for fresh installs unless a trusted first-setup path is established. On model-load failure, pre-load transitions, later reloads, and null-default consumers, behavior is unverified. Outside an introduced DDG fallback the original native behavior is retained. The cohort marker has no anti-tamper protection; same-user manipulation is outside the normal preservation goal.
