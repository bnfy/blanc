# Native search-engine deletion provenance — 158 source review

No native persisted per-engine deletion tombstone was found. This is a read-only source assessment, not a browser, WebData, crash or Sync test. The candidate remains isolated and unstaged.

* `template_url_service.cc:875-963`: `Remove()` removes a non-default engine from memory and schedules `web_data_service_->RemoveKeyword(id)`; `keyword_table.cc:819-826` implements this as SQL `DELETE FROM keywords WHERE id = ?`. User default engine removal is explicitly forbidden, although a previously non-default id-92 engine can be deleted.
* `template_url_service.cc:2234-2240,2300-2305` uses `pre_sync_deletes_` to suppress a known GUID in the current process and clears it after successful Sync. It is not a persisted record identifying prepopulate ID 92 after restart. Sync server tombstones are account/synchronization protocol state, not evidence available for every local-only profile or before Sync.
* `keyword_web_data_service.h:46-76` metadata stores last built-in-data version, country and migration set, plus starter-pack version: these describe bundle reconciliation, not first creation, presence or user deletion. `keyword_table.cc:381-399` returns 0/invalid when metadata is absent or unreadable; `keyword_web_data_service.cc:27-48` always engages the country optional even for that invalid value, so `HasBuiltinKeywordData()` is not a reliable fresh-database test. Existing, restored, damaged or partially initialized data can present the same values as first setup. `GetKeywords` also deletes some invalid rows and its decryption-failure flags cover only certain failure types.
* `template_url_service.cc:1874-1899` passes the raw result to `GetSearchProvidersUsingKeywordResult` before `SetTemplateURLs` and `ChangeToLoadedState`. `util.cc:1045-1082,1091-1120` may call `MergeEnginesFromPrepopulateData` when data/country version changes or prepopulated decryption fails. Thus the current post-merge model guard cannot prove an absent row was never added or recreated.

The minimal credible source of *positive* first-setup evidence is a same-profile, single-use in-memory creation/import-completion capability carried from exclusive regular-profile creation through initial PrefService and WebData setup, paired with a successful raw WebData result showing no existing id 92 and a suitably uninitialized metadata state with no known read/decryption error. That capability can justify **one initial population in that session**. The native metadata alone cannot supply this proof; a user with missing metadata can otherwise be mistaken for a new install. If that capability is lost on a crash, the ordinary preference's prior non-sync cohort value does not prove whether setup or deletion occurred; conservatively preserve existing behavior and require explicit product handling instead of automatically reseeding. A closed copied profile with a committed cohort is not proof of initial creation in the new installation.

Before allowing the native pre-merge operation to add missing id 92 for a cohort fallback, the caller would need to pass the capability into a narrowly scoped initial-load path and keep unrelated engines/explicit provider/policy/extension behavior intact. Without a capability, safely *preserving deletion* through the native generic merge would still require either a scoped omission of this engine during that merge or a persistent, correctly synchronized deletion signal; neither is presently implemented. Suppressing or changing generic reconciliation wholesale is not acceptable. A false-negative gate will leave a new user on Chromium's original fallback or temporarily without a default; it must not silently claim shipping DDG parity. Also verify that native pre-load/default-provider consumers tolerate an unavailable provider and that a later explicit selection, Sync or policy update restores behavior.

An implementation must test real fresh WebData creation, same-session and post-restart deletions, restored/copied/partially initialized data, stale/missing/corrupt metadata, row decryption failure, version/country reconciliation, live explicit user selection and policy/extension/Sync, and failure/crash between PrefService and WebData writes. No test above has run, and no blanket modification of native reconciliation is proposed. Existing exact source SHA-256 values remain in `source-hashes.json`.
