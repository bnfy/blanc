# Conservative fresh-profile search-default draft — not integrated

GitHub's latest release and tag were reverified on October 29, 2026: shipping v1.45.0, exact commit `6f1bc523d2f0d432d5c4119b9f7ec22a324dbd2d`. Its released `src/main/settings.js` defaults to DuckDuckGo (`release-verification.json`). The separate selected-provider Chromium draft routes the effective provider but leaves its fresh-profile fallback unchanged; that is a real parity gap.

`fresh_default_adapter.cc` is a real Chromium 158-header-compatible, synchronous one-attempt draft, with policy decisions factored into `fresh_default_policy.h`. It proposes selecting only one exact built-in DuckDuckGo engine from a freshly created **regular** profile when a trusted caller has independently proved that the profile directory itself was new before profile files were created, its writable Preferences store is newly created, the search-data and default-GUID prefs and provider overrides are untouched, identity tokens are loaded with no known account, the search service is loaded and still uses the unoverridden fallback, the native choice service says outside its choice-screen scope, the OS-reported region is valid and outside all configured native choice regions, and exactly one unchanged built-in DuckDuckGo engine can be selected. It rechecks the selection, region, account, prefs and candidate immediately before setting the native default. Unknown, managed, recommended, extension-controlled, duplicate, configured, signed-in, existing, guest/private and unproven cases preserve the current provider. An incomplete model or identity returns an explicit wait without retaining a query. The adapter records only that the in-memory native user preference and selected provider were observed after mutation; that does not prove disk persistence.

This is **not product-integrated or shippable**. The move-only `FreshProfileProof` is a limited draft: a missing Preferences file alone is not proof of a new directory. It requires the caller to validate and control the parent and records an exclusive directory creation plus a pinned directory handle, but it does not establish isolation from a hostile same-user replacement between directory creation and opening the handle. A false proof could overwrite a restored user's search choice. The caller must own one attempt per profile, capture proof at the actual creation boundary before files are created, tie its lifetime safely to the profile, register and cancel identity/model callbacks without losing events, serialize user/policy/extension/Sync changes, and ensure no query routes through a fallback before initialization settles. On crash before selection, an existing directory will fail the fresh check next launch; durable initialization/recovery needs design without resetting existing choices. Changing a native user-selected pref can affect Sync and native choice-screen interpretation; compare those semantics with shipping before use. The OS country API reports a configured region, not physical location; neither it nor native eligibility alone is a legal determination. Regions with unknown or eligible choice conditions deliberately remain unchanged. Full Settings, multi-profile, choice-screen, account, import, restart/crash, browser and private behavior are untested. No backend, 157 fallback, source checkout, app or build cache was staged or modified.

`fresh-default-policy-test.log` records 30 standalone policy and duplicate-engine checks using the pinned 158 compiler/SDK and cached objects. These tests exercise the pure decision and uniqueness rules, not the real Profile/TemplateURLService or callback races. `strict-syntax.json`/`.log` record a `-fsyntax-only` pass with actual 158 compiler flags and the unsafe-buffers plugin; this is not a native link or build. Earlier isolated failures are retained: a missing SDK include in the first syntax attempt, a raw-pointer iteration type error fixed in the draft, and a standalone C++ invocation without configured include paths. The local Git tag was absent; the GitHub tag reference independently resolved to the already available commit whose settings blob was read by exact SHA. No browser tests or production builds were run.

Before promotion: independently review trust and privacy assumptions; locate a durable authenticated profile-creation provenance and cancellable model/identity lifetime; preserve external changes/choice screen and Synced settings; bind the initialization to the existing host routing without holding or transmitting stale user input; then derive exact staged source/BUILD dependencies, obtain a guarded incremental dry-run scope and run focused fresh/existing/restart/managed/extension/choice/Sync regular-private browser checks under an appropriate independent network boundary. Preserve existing candidates, user profiles and failures. Electron remains paused, Google baseline separate, latency deferred.
