# Per-profile fallback cohort and restart provenance — isolated draft

Shipping v1.45.0 / `6f1bc523d2f0d432d5c4119b9f7ec22a324dbd2d` defaults to DuckDuckGo. A global native fallback substitution would change existing fallback users and can alter native search-choice eligibility; `PRODUCT-FALLBACK-REVIEW.md` records those source paths and constraints. The preferable shape is a per-profile, product-fallback cohort below existing native user, policy, extension and choice decisions, without writing an automatic `FROM_USER` selection or sending/retaining a user query while prerequisites are unresolved.

## Isolated work delivered

`restart_safe_cohort.h` implements a pure, fail-closed decision model with absent, pending, committed, retired and corrupt records; current exclusive creation versus a verified restart; known import/restore status; regular-only scope; exact model/identity/provider/override/choice checks; and explicit wait, pending, commit, retire, preserve or DuckDuckGo-fallback actions. On a later account sign-in, a committed cohort waits until Sync reconciliation is known, then continues using its fallback only if no explicit provider, policy, extension or override took precedence. It never selects a custom or duplicate prepopulated provider; `CandidateSet` accepts exactly one normal id-92 DuckDuckGo record with the released template, no extension and no POST parameters. This is a policy model only, not a native resolver or a storage backend. `restart-safe-cohort-test.log` records 39 synthetic state/engine assertions, including interrupted phases, stale/corrupt/unverified/copied evidence, imports, choice, user/policy/extension changes, post-sign-in Sync and duplicate/malformed engine data.

`restart_record_auth.{h,cc}` is an isolated Chromium `crypto::hmac::SignSha256`/`VerifySha256` integrity component. It MACs fixed-width installation, profile and filesystem identities, generation and phase under a domain-separated encoding. Verification requires an independently supplied trusted anchor with matching identities, generation **and phase**, rejecting prior pending/committed phase replay and tampering. `restart-record-auth-test.log` records 17 synthetic checks, including an independently generated HMAC-SHA256 vector, wrong key, changed binding/phase/tag and generation replay. The test key and values are fabricated; no credential is stored. Real key generation, OS secure storage, secure key lifetime/erasure and rollback-resistant anchor are **not implemented**. A valid MAC is not proof a directory was originally fresh or that both the record and anchor have not been rolled back together. Never pass an ordinary marker or caller-provided boolean as `kVerifiedRestart` or `verified_record_binding`.

The pure model and MAC component are not yet connected to each other or to the 158 resolver, profile lifecycle, browser UI, Sync or network. The test logic assumes trustworthy evidence supplied by a future verifier; it does not establish that evidence. No user profile, native source, checkout, app or product build was changed. The 158 Clang syntax checks use the cached toolchain, including its unsafe-buffers plugin; isolated link failures from an unsupported thin archive and missing cached SHA assembly objects were retained before the corrected cached-object link. No cache was cleaned or toolchain changed.

## Required real integration contract

1. Establish a genuinely new regular profile directory before user data is written, using a reviewed platform-specific exclusive-create/identity mechanism. The `fresh_profile_proof` experiment offers a macOS/Linux in-memory claim only; it has an identified create-to-open race, blocking-I/O and Windows gaps. Unknown, preexisting, restored, copied, externally seeded, ambiguous or failed evidence must preserve the prior effective provider.
2. Create a cryptographically random installation key and installation/profile identifiers using established Chromium OS-backed APIs with explicit unavailable/locked/error handling, no secret in Git or logs, and a stable cross-platform directory identity captured by reviewed OS-specific APIs. Bind record authentication to an independently protected per-installation anchor including exact phase and strictly increasing generation. A standalone profile marker, path, timestamp, inode, UUID or MAC using a key copied alongside the record is insufficient. No portable, rollback-resistant secure-anchor implementation has been verified in this checkout. If the platform cannot supply this guarantee, the only currently safe recovery is to preserve the existing provider and leave the cohort unresolved.
3. Persist pending then committed states with a reviewed atomic/durability protocol, no concurrent writers, and independent anchor/readback verification. Crashes between the two stores must fail closed; no query may use a pending/unverified cohort. `base::ImportantFileWriter::WriteFileAtomically` explicitly does **not** guarantee integrity across system crash, so it alone is not a demonstrated durable or anti-rollback solution. Full machine backup/restore of both stores may also roll back a valid record and anchor together; this must be detected by an actual trusted monotonic mechanism or treated as unverified. Never delete or replace another profile's files to recover.
4. On each async transition re-read native source, user-pref/GUID, provider override, identity, Sync/import and region/choice eligibility on the correct sequence. Register model and identity callbacks before starting loads and recheck synchronous completion; use cancellable weak lifetimes. Native `DefaultSearchManager` precedence must remain policy/recommended policy, extension, user and only then fallback. Route fresh pending/unknown requests to a visible retry/hold state without storing or automatically transmitting stale query text. Never infer legal or physical location from an OS locale.
5. On a verified committed cohort, inject the exact unmodified DuckDuckGo prepopulation entry only into the native fallback path; do not override a selected user/custom/extension/mandatory or recommended policy provider, a provider override, an eligible/unknown choice screen or a restored/imported profile. Recheck actual behavior if the user signs in, Sync data arrives, the region changes or an explicit choice is later cleared. Shipping Settings must report the actual provider, and private suggestions/Start Page behavior must remain protected.

A full test matrix must include power loss at every journal/anchor step, both-store rollback, copied/imported profile and installation combinations, metadata/identity reuse, corrupted or locked credentials, multi-process races, first search while loading, user/policy/extension/Sync/choice changes mid-commit, retries without stale input, restart and real regular/private browser behavior, on macOS/Windows/Linux. Match the exact reviewed source and product app, preserve failures, and require an independently enforced network boundary for acceptance. No native build is authorized by this draft.
