# Conditional manager sequence guarantee — not resolved

This v2 candidate is **not generally atomic** and must not be staged. Its new registration method rejects callers off UI, but the existing `Shutdown()` remains unchanged. If any shutdown can execute concurrently off UI, `shutdown_needed_` and Chromium's unchecked observer list can race and the candidate can miss `ManagerGoingDown` or access invalid state. `NotFatalUntil::M159` on some BrowserContext UI checks reinforces that violations cannot simply be dismissed; user-facing behavior must not be made more crash-prone to hide them. `BrowserContext` documents UI confinement and normal Chrome source paths use it, but that is not yet an audited guarantee across embedders, test doubles and every direct shutdown call.

Do not treat a successful v2 registration as proof of a safe lifecycle until the exact manager implementation and all its shutdown pathways have a verified same-sequence invariant. Reject unproved managers in the future service. The v2 draft `service/` does **not yet implement an enforceable provenance proof**, and therefore cannot be exposed or used to project private rows. Synthetic model and syntax passes do not demonstrate the invariant.

A lock around only `shutdown_needed_` and registration could serialize their state transition but is insufficient: legacy `AddObserver`/`RemoveObserver`, the unchecked ObserverList, callback iteration, raw manager lifetime and an observer's UI-only profile/WeakPtr state would still race if Shutdown runs elsewhere. Holding a non-reentrant lock while invoking observers would deadlock self-removal, nested shutdown, or other callbacks; releasing the lock before callbacks still requires an independently safe observer/removal/manager-lifetime protocol. Retrofitting a thread-safe observer list or posting shutdown notifications changes notification timing and must guarantee that a worker-side shutdown synchronously revokes all sensitive UI operations before any item/manager can be destroyed; delayed UI invalidation is not sufficient. A dedicated shared atomic liveness latch also does not make access to a destroyed manager safe by itself. Such a redesign would be materially broader than this candidate and requires concrete lifetime proof, cross-platform review and concurrency tests.

Other viable directions include a carefully reviewed manager-owned sequence assertion/provenance capability supported by every implementation, or a creation-time broker with an explicit, enforceable UI-only shutdown contract. Neither has been implemented or proven. Test direct off-UI shutdown with deterministic task barriers under a safe synthetic configuration, reentrancy and self-removal, multiple observers, private context teardown and recreation, manager pointer lifetime, immediate rejection of pending private replies, and caller violations. Do not infer these from an off-UI registration test alone.
