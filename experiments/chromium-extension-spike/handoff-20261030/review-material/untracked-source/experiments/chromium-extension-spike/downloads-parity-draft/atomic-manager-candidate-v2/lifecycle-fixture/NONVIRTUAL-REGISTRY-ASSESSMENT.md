# Nonvirtual manager lifecycle broker — feasibility review

This is a design assessment, not an implementation or proof. The v2 patch inserts a virtual `DownloadManager` method before existing methods; an ad-hoc executable cannot safely mix its rebuilt manager with cached objects compiled against the previous vtable layout. A nonvirtual content helper/registry could avoid changing the existing public `DownloadManager` class and therefore avoid that specific ABI hazard and public-header rebuild fan-out. It does **not** prove a tiny standalone link is complete or safe: `DownloadManagerImpl.cc`, any helper/service and test sources still need to be rebuilt, and missing test infrastructure/transitive dependencies remain unresolved.

## Candidate boundary

Within `//content`, a browser-process-only registry could track concrete `DownloadManagerImpl` instances by a fresh per-manager unguessable generation and its owning `BrowserContext::UniqueToken`; neither token or any raw pointer is renderer-supplied. Registration must occur only after construction has safely reached its publication point; `DownloadManagerImpl` passes `this` to other initialization code, so an arbitrary mid-constructor hook or an assumption of no reentrancy is not enough. Shutdown retires the instance *before* any `ManagerGoingDown` callbacks and destructor cleanup removes any remaining entry. A helper exposed through a narrow new `content/public/browser` interface could accept only browser-owned expected context/manager generations and an observer, fail closed for unknown/mocked/unsupported managers and avoid adding a virtual to `DownloadManager`. On the supported UI sequence, it may look up a registry-held `DownloadManagerImpl` and perform a known non-reentrant concrete observer addition before returning. Exact class/lifetime proof, content export and dependency-layer rules must be established; never static-cast an arbitrary `DownloadManager*` or dereference a raw pointer solely because its address matches a map key.

Use distinct manager-instance generations, not manager pointer or context identity alone: address reuse can create ABA, and private-profile teardown/recreation must invalidate its previous generation. A manager can be constructed before a previously active test manager is shut down (`SetDownloadManagerForTesting` receives an already-created replacement); two manager instances can briefly share one BrowserContext. The registry must not overwrite a single context slot or label a newly constructed replacement active prematurely. Track each concrete instance separately and obtain the *currently published* manager identity from a trusted BrowserContext lifecycle handshake, or fail closed while ambiguous. Neither the existing public manager getter nor a renderer-supplied GUID supplies such proof. Final private/regular grouped replies must revalidate both context and manager generations and current trusted document immediately before delivery.

## Thread and lifecycle limits

A helper that only checks UI before registration inherits the same conditional assumption as v2: `Shutdown` must happen on UI. Registry deletion before callbacks provides correct late-registration and reentrant-observer ordering *only for conforming same-sequence execution*. It does not harden an off-UI early embedder Shutdown; a global map with an unchecked observer list would race. A lock over registry membership is also insufficient if `DownloadManagerImpl` may concurrently destroy items, invoke a UI-only observer or use its unchecked `ObserverList`; holding a lock through callbacks can deadlock self-removal or reentrant shutdown. A thread-safe/lifetime-pinning redesign would require a more invasive manager ownership and observer protocol, not merely a hash map or atomic flag. The helper must therefore reject all use without a proven supported-sequence provenance guarantee; no such enforceable capability exists yet.

Lifecycle observer callbacks, manager replacement, reentrant delegate setup, Profile::ShutdownStarted, manager-down before profile-down, pending item read, self-removal and delayed UI delivery all require proof and synthetic-browser tests. Preserve warning raw values and keep all capabilities disabled until a separate native security/action design is integrated. Never persist or log private rows, URLs, file paths or tokens.

## Build impact and next step

This route may reduce header fan-out relative to v2, but exact actions are unknown. It requires an isolated helper API/implementation and registration/retirement hooks, at least one new or altered native build target, service and test code, and possibly a content/public export. A guarded candidate-aware dry run is still required before compilation; GN generation, toolchain changes or a cold build are not authorized here. Review the registry's exact creation/publication point, supported-sequence guarantee and layered API with an independent reviewer before writing or staging it. Current fixture and service stay unregistered; no native code/output or user profile has been touched by this assessment.
