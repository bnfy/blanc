# Browser-owned Downloads integration: Chromium 158 source review

Shipping reference rechecked October 29: v1.45.0 tag `6f1bc523d2f0d432d5c4119b9f7ec22a324dbd2d`. The released `src/main/downloads.js` uses one active local profile family, combines that family's normal and private session records in its sheet, persists at most 200 finished normal records, keeps private finished metadata in memory, puts active rows first, and deletes finished records without deleting saved files. A private item's metadata lasts for the Electron process/session, whereas Chromium primary-OTR lifetime may end sooner. This and retry/session behavior are unqualified product differences. The shipping sheet is owned/trusted and is not ordinary web content.

## Owner and lookup

Chromium `content/public/browser/download_manager.h:5-24,60-61` specifies one manager per browser context and History-backed regular records. `chrome/browser/profiles/profile.h:247-276,394-425` identifies regular, incognito, guest, system and enterprise-isolated contexts and `GetPrimaryOTRProfile(false)`. Chromium's Downloads page `chrome/browser/ui/webui/downloads/downloads_ui.cc:300-313` initializes history and binds its manager. Its tracker `downloads_list_tracker.cc:560-579` merges an OTR manager and the original manager; that is intentional native UI behavior, not proof that another caller may inspect either profile.

A Blanc **browser-owned profile-family service**, not a document, should own registry, manager observers, row handles and capability decisions. Establish the regular owner from a trusted window/browser object and require `IsRegularProfile() && !IsOffTheRecord()`; reject Guest, system, enterprise isolated, secondary OTR and unknown contexts. Only after proving the owner, read the current `owner->GetPrimaryOTRProfile(/*create_if_needed=*/false)` and verify its exact parent, primary identity and accepted incognito type. Never create a private profile just to populate the sheet. Any original/private combination must be limited to the same user-authorized family. Confirm whether the sheet's invocation from a private tab is meant to show both, using actual shipping behavior, before enabling the flow; do not imply private data is hidden in a normal-window-owned sheet if shipping combines it.

Allocate an unguessable, ephemeral browser-owned row handle bound to `{family lifetime, context epoch, manager, item GUID}`. No renderer supplies a profile ID, epoch or filesystem path. Resolve the handle only within that service after validating the calling primary document, frame, current committed and visible URL, pending navigation, exact window and profile. Recheck ownership and epoch on each request. Resolve the current item by `manager->GetDownloadByGuid(guid)` (`components/download/public/common/simple_download_manager.h:61-68`), never a family-wide first-match search or deprecated numeric ID (`content/public/browser/download_manager.h:203-209`). If duplicate GUIDs appear within a projection, either map distinct opaque handles to known manager epochs or fail closed. Enumerate only authorized managers and wait for their actual initialization/history load; `GetDownloadByGuid` can find in-progress entries not returned by uninitialized `GetAllDownloads` (`content/browser/download/download_manager_impl.cc:1546-1568`). No partial enumeration may be represented as a complete empty history.

Observe each manager's going-down notification and each item's update/removal/destruction; erase/revoke handles before their context or item disappears. Never cache a raw item pointer across a posted task, user dialog, renderer reply, manager teardown or profile destruction. A restored item can lack associated initiating WebContents. Chromium 158 `DownloadManagerImpl::CreateDownloadItem` attaches its own BrowserContext before publishing a history-created item (download_manager_impl.cc:1403–1408), and `ImportInProgressDownloads` does the same before its restored item is published (:1475–1490). `DownloadItemUtils::GetBrowserContext` reads that attached data (download_item_utils.cc:94–100). These source paths support retaining the strict matching-context check for ordinary restored items even when WebContents is null. Other item producers, teardown races and real regular/private browser behavior remain unverified; missing context must still fail closed. Do not use original profile's manager as fallback after a private handle fails. Private epoch destruction must remove private rows and private operation visibility; it must not accidentally recreate OTR or export URLs to regular profile storage, logs or telemetry. Avoid storing GUID/URL/path in a persistent registry for private operations.

## Command preconditions and operation outcomes

For each real dispatch: authenticate current document/window and interaction, re-resolve handle and exact manager, re-evaluate current item state, `DownloadItemModel::ShouldShowInUi`, unsafe/insecure/scanning/enterprise state and applicable policy. Build a local `DownloadItemModel` and `DownloadCommands` on UI sequence; the model must outlive the command object (`chrome/browser/download/download_commands.h:55-69`). Current presentation capabilities are hints only. `DownloadCommands::IsCommandEnabled/IsCommandVisible` do not authorize the command and `ExecuteCommand` does not recheck them (`download_commands.cc:149-171`). Base `DownloadUIModel::IsCommandEnabled` returns true for KEEP, DISCARD, deep-scan bypass and RETRY (`download_ui_model.cc:637-678`); these security-sensitive actions must not be exposed by the current draft. `IsDangerous()` alone does not classify every scan/policy state: `DownloadItemImpl::IsDangerous` returns false for `ASYNC_SCANNING`, `ASYNC_LOCAL_PASSWORD_SCANNING`, and `DEEP_SCANNED_FAILED` (`components/download/internal/common/download_item_impl.cc:1123-1151`). Explicitly inspect `GetDangerType`, `GetInsecureDownloadStatus`, model warning/policy state and only permit a reviewed allowlist of positively established safe states. When not established, keep item non-actionable and route users to Chromium's existing security warning surface through a separately reviewed flow.

- **Cancel / resume:** recheck current state, `CanResume`, visibility, current security/policy, and `DownloadCommands` eligibility; use the actual item only after registering observers. `Cancel(true)` and `Resume(true)` are void (`components/download/public/common/download_item.h:198-210`); dispatch is not proof of completion. A later state transition is observable but may have been caused by a different actor. Establish a documented, race-aware confirmation criterion before returning `true` or terminal registry outcome.
- **Open:** require a completed item, recent *trusted user interaction* like `DownloadsDOMHandler::OpenFileRequiringGesture` (`downloads_dom_handler.cc:261-281`), current safe/policy state and model `OPEN_WHEN_COMPLETE` enabled. `CanOpenDownload()` may be true for in-progress items (`download_item_impl.cc:1234-1240`), where `OpenDownload` toggles future auto-open rather than opening now. No open action on in-progress/interrupted items. `OnDownloadOpened` records Chromium's event, not successful external-app launch; `OpenDownload` returns void (`:768-800`), so no OS-success claim.
- **Show:** require appropriately completed safe current item, model `SHOW_IN_FOLDER` enabled and reviewed trusted interaction. `ShowDownloadInShell()` returns void (`download_item_impl.cc:804-812`); it cannot confirm OS presentation. Registry must distinguish **issued** from verified action success; the present `kSucceeded`/`kConfirmedFailure` interface has no such terminal value. Until the product contract and reconciliation are defined, do not falsely resolve or re-enable ambiguous retries, and do not ship the current sticky state as a complete recovery UI.
- **Retry:** Chromium generic model returns no-op for RETRY (`download_ui_model.cc:787-790`), even though enablement can be true. Native Downloads WebUI creates a new request with original initiator through `downloads_dom_handler.cc:420-463`. This does not automatically match shipping's replacement row, owner session and selected save-path reuse. Leave retry disabled until provenance, HTTP(S) admission, owner/partition, user-gesture and save-path behavior are implemented and browser-tested.
- **Clear finished:** check `prefs::kAllowDeletingBrowserHistory` at dispatch (`downloads_dom_handler.cc:841-845`) and again before each asynchronous continuation; snapshot eligible authorized handles, reserve a registry clear against the exact epoch/keys, and re-resolve each. Do **not** use Chromium `ClearAll` (`:543-596`): it removes dangerous/insecure/scanning downloads, including potentially active ones. `DownloadItem::Remove` deletes intermediate files if in-progress or interrupted (`download_item.h:210-215`); a conservative first candidate may remove only verified COMPLETE, safe, currently shown records, after explicit user request. Its omission of finished interrupted/cancelled records is a shipping-parity gap, not full clear acceptance. Do not remove a file via `DeleteFile`. A later design must reconcile all shipping finished states without deleting intermediate files or silencing security warnings.

Before any possibly reentrant command, reserve an operation, install the observer and mark it dispatched. `DownloadItemImpl::Remove()` synchronously notifies then removes/deletes the object (`download_item_impl.cc:757-765`); callback may run during the call. Never dereference the item, `DownloadItemModel` or owner after dispatch without separate lifetime proof. `OnDownloadRemoved` can establish that the observed item was removed, whereas `OnDownloadDestroyed` also occurs during manager teardown (`download_item.h:133-142`) and cannot by itself mean successful removal. An item update can originate externally, so its interpretation needs precise state and operation checks. Registry terminal results must be authoritative; loss/teardown, partial batches and callback timeouts stay unresolved, with scoped cleanup on private epoch teardown. Any observer's reentrancy and weak-owner lifetime must be tested.

## Required integration and narrow tests

This document is a source-bound design, **not** a compiled handler and not a product/parity claim. Implement a scoped service + trusted WebUI registration only after source/lifetime/security review and a guarded incremental build plan. Current registry remains an isolated single-sequence model, has no manager linkage, no restart journal and no reliable OS-completion signal.

Before exposure, use only fresh disposable regular and primary-incognito profiles and local test downloads. Verify manager initialization and delayed history, family ownership and forbidden contexts, duplicate/stale handles and primary-OTR destruction/recreation, private metadata non-persistence, externally changed warning/policy between list and action, missing paths, unknown progress and name normalization, every command's security policy, reentrant removal/observer teardown, asynchronous and timeout outcomes including recreated documents, clear while state changes and partial results, actual saved file/intermediate-file preservation, restarted regular state, dangerous/insecure/scan warning handling, OS actions, keyboard/VoiceOver and six locales. Test eventual late callback and browser exit/restart before claiming exactly-once semantics. Run only affected checks against exact built candidate; never use a real profile or the separate Google baseline. Electron remains paused and latency deferred.
