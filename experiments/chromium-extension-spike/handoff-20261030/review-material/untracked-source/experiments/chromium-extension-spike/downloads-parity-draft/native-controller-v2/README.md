# Browser-owned Downloads controller v2 — isolated draft

Shipping reference: GitHub latest release and tag verified 2026-10-29 as Blanc v1.45.0, commit `6f1bc523d2f0d432d5c4119b9f7ec22a324dbd2d`. This is not registered, built into the product, or released.

Independent review found that the previous candidate could reuse an old handle when a removed `DownloadItem` was replaced with the same GUID. V2 attaches an observer to each issued item and rejects its handle after `OnDownloadRemoved` or `OnDownloadDestroyed`, including when a new object occupies the same address. A new item needs a new handle. It also checks UI-thread membership in release before map access; destruction requires the UI thread. Controller, item observer and browser context remain UI-sequence-owned.

`item-lifetime-test.cc` exercises the *same* lifetime template used by the candidate against a fake item: normal scoped removal, removed item, destruction, and same-address replacement. `xcrun clang++ -std=c++20 -Wall -Wextra -Werror item-lifetime-test.cc -o item-lifetime-test` and the executable exited 0 with assertions enabled. This is not an actual Chromium DownloadItem, manager shutdown or reentrancy test. The real v2 controller passed the recorded Chromium 158 cached-clang syntax-only command in `syntax-command.json`; no linked product binary or full test ran. The original frozen candidate and its evidence remain in `native-controller-candidate/`.

Still not safe to expose or count as product parity: the caller must authenticate the current primary document, window, gesture and family; issuance and cancellation do not independently enforce current native visibility, security warnings or enterprise policy. The API does not have the required observation/outcome reconciliation, so `kIssued` cannot mean success. Items with missing attached contexts are rejected, omitting some history rows. Exact manager/item destruction and removal during lookup/state getters, observer-list reentrancy, profile shutdown, private teardown/recreation and real UI ordering require native tests. The visible download sheet, current live policy gate and every action besides cancel remain unimplemented. Do not wire this candidate into a renderer or production app before these gaps and independent review are resolved.
