# DownloadManagerImpl shutdown caller and sequence audit — Chromium 158

Source audited: Chromium 158 checkout HEAD `681cd621e82e606d7536eae8ea2576afb3c7d65c`; the source files listed below were unmodified at audit time. The common source paths apply to macOS, Windows and Linux: there is no platform conditional around the relevant calls or manager shutdown implementation. `audited-source-sha256.txt` records current audited source hashes. No runtime instrumentation, build, production staging or personal-profile access was performed.

`Profile::MaybeSendDestroyedNotification` (`chrome/browser/profiles/profile.cc:490-506`) first invokes `NotifyWillBeDestroyed`, then profile observers. The profile's `ShutdownStarted()` is therefore a useful early denial, and the independent epoch service candidate checks it; it does **not** detect a separately initiated manager shutdown. `DownloadManagerImpl::Shutdown` (`content/browser/download/download_manager_impl.cc:725-749`) marks `shutdown_needed_` false before notifying `ManagerGoingDown`, but does not assert a sequence. `content/public/browser/download_manager.h:73-78` explicitly allows the embedder to call Shutdown early and does not state a manager-specific UI-thread rule there. Under documented/conforming BrowserContext use, normal desktop construction, normal/OTR keyed-service cleanup and destruction are intended to occur on UI. That is evidence for the conditional protocol, not a guarantee that every possible direct or future embedder call observes it, especially while the 158 release checks are transitional.

A repository-wide `rg -U` search of `*.cc`/`*.h` excluding only `out/` for `GetDownloadManager(...)`, `download_manager`, `download_manager_`, or `download_mgr` followed by `->Shutdown()` found the two `BrowserContextImpl` calls, `DownloadCoreServiceImpl` call, and the two direct implementation unit-test calls above. A second search for Shutdown calls in files containing `DownloadManager*` found no additional obvious production DownloadManager calls. This lexical scan does not prove absence of type aliases, indirect calls, generated code, code in excluded outputs, dynamic behavior, or third-party downstream embedder calls. The public early-shutdown API is itself an explicit limit.

## Decision and next implementation step

For the reviewed repository's normal desktop profile paths, the existing UI confinement contract explains why the v2 registration would work when respected, and the normal and private flows share that sequence. **Do not promote v2 as generally atomic or hardened:** it has no enforcement for a public direct Shutdown from another sequence, and a nonfatal upstream check means erroneous execution can continue into data races. It also lacks an implemented, trusted document/profile provenance service and safe item lifetime. The audit does not justify adding an unconditional fatal Shutdown check or assuming private-data safety.

The smallest concrete next step is an isolated native test/instrumented candidate, not a product toggle: observe actual browser UI sequence and callback ordering for fresh regular and primary-private profile creation/manager initialization, early keyed-service shutdown, final BrowserContext teardown and old private lease rejection; record exact profile/manager identities and check no late private result. Test separate registered-observer self-removal, multiple observers, callback reentry and late registration. Restrict all fixtures to synthetic profiles. Source contract and successful tests can justify using v2 only within a documented supported-sequence boundary; they cannot establish safety under hypothetical off-sequence shutdown. If strict tolerance of such a violation is a requirement, a separate manager/observer lifetime redesign is required, as explained in `SEQUENCE-RISK.md`; a flag-only lock is not enough. Perform a guarded dry run and assess public-header fan-out before any native test build. This audit does not approve staging, building, release, waiver or use of a real profile.

## Independent review

An independent source review agreed that documented BrowserContext UI confinement and the audited normal/primary-private desktop paths justify *evaluating* v2 as a narrowly guarded Chromium 158 prototype, without an unconditional fatal Shutdown assertion. That conclusion covers conforming supported-sequence paths only. It does not establish general atomicity, protect an off-UI early embedder Shutdown, or qualify the lifecycle service and private snapshots. The reviewer requested real synthetic regular and primary-private Profile/manager lifecycle checks, early and final shutdown, manager replacement/late registration, observer callback reentry/self-removal/multiple-observer behavior, stale OTR epochs and delayed replies, teardown and unsupported mock behavior. The proposed off-UI registration unit test is unrun and does not exercise concurrent off-UI Shutdown or actual profile lifetime. No build, staging, runtime test or real-profile operation occurred in this review.
