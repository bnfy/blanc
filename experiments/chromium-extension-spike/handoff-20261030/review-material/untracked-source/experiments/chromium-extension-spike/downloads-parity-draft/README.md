# Downloads parity draft — isolated, not integrated

Reference: published Blanc v1.45.0, commit `6f1bc523d2f0d432d5c4119b9f7ec22a324dbd2d`, verified from GitHub release and tag on October 29. `shipping/` contains exact released Downloads HTML, renderer and row model. Current Chromium prototype instead routes Downloads to `chrome://downloads/` in a tab; it does not provide the shipping transient sheet or the full shipping API.

## Implementation direction

Use Chromium's profile-owned `DownloadManager`/`DownloadItem` and existing `DownloadItemModel`/`DownloadCommands` policy instead of rebuilding download networking. Keep Blanc's released sheet, action order, progress and accessibility behavior. Finished regular metadata must remain profile-scoped, private metadata must not persist beyond its private session, in-flight rows precede finished rows, and the shipping 200-record finished limits and profile deletion behavior must be reconciled with Chromium history. Only the current profile and its primary private context may contribute; Guest, secondary off-the-record contexts, stale profiles and ambiguous IDs require explicit policy, never implicit merging.

`downloads-adapter.cjs` is a presentation-only draft for a future trusted native endpoint. It validates the schema, rejects duplicate IDs and path-shaped filenames, exposes only basename and an origin-only HTTP(S) source, and intersects released row actions with native capabilities. `downloads-renderer-candidate.js` is the released renderer with two changes: it uses the capability intersection and clamps progressbar width/ARIA value to 0–100. The origin-only tooltip and blank non-web source intentionally differ from shipping's full URL tooltip, reducing exposure of credentials, query tokens and local paths; this difference is not silently counted as parity and needs product review. On review, a malformed `http:broken` string was found to normalize into a URL; explicit `http://` or `https://` is now required.

The adapter never establishes authorization: native code must bind each call to the exact trusted primary document, derive the current owner and profile, re-resolve the GUID and context at execution, and recheck the current download state and Chromium's danger, insecure-download and enterprise policy. `KEEP`, `DISCARD`, bypass and similar security-sensitive commands are not exposed by this draft. Do not rely on a stale client capability or display row to authorize an action. A stale or changed item must fail explicitly. The action path must preserve Chromium Safe Browsing and review flows, active-download lifecycle and file contents; clearing finished history must never delete downloaded files. Chromium's generic `DownloadCommands::RETRY` path is not itself an implementation of Blanc's retry/save-path/session behavior, so it must not be presented as working until mapped and tested.

Sixteen isolated Node tests passed on October 29: released action order and capability intersection, denied/non-web retry, malformed records and duplicate IDs, fixed dispatch and native errors, no extra path field, URL/path redaction, an actual renderer-with-fake-DOM progress overrun, cross-platform path-shaped filename rejection, removal/recovery of stale rows on a failed refresh, slow polling/focus recovery, a deferred mutation invalidating an in-flight read, bounded unresponsive/false native replies, a late-completing mutation that cannot be retried from the still-open sheet, and security-unknown/review rows with accessible distinct statuses and no unsafe actions, with Cancel available only if native permits it. The first run of the new redaction test failed on WHATWG URL normalization; the rule was corrected and the suite passed. The DOM test is not a real browser, a native download, or physical accessibility evidence. The five new keys (`downloads.loadError`, `downloads.updating`, `downloads.actionUnconfirmed`, `downloads.securityReview`, `downloads.securityUnknown`) have isolated proposed messages for all seven shipping locales in `downloads-locales.json`. Two focused tests verify that the exact released translator resolves each key, preserves every released message and refuses collisions. `generated-locales-v3/` contains isolated generated scripts bound to exact released-input hashes and generator/merge hashes; its deterministic check and a released-translator integration test pass. Earlier v2 assets are retained. They are not merged into live assets, and human translation, rendered layout and accessibility review remain open. Native adapter, trusted bridge, live UI, safe in-flight ownership and cancellation/retry semantics, warning presentation, persistence cap, migration, private teardown, no user-visible stale data, and cross-platform tests are all **unimplemented or unverified**. No production native code, user profiles, output, or live development assets were changed by this draft.

The draft client timeout is an observation deadline, not cancellation of a dispatched native action. A timed-out mutation reports an unconfirmed outcome, and the future backend needs explicit late-completion, idempotency and refresh semantics; it must not claim the operation failed or safely retry destructive actions based only on a client timeout. A native success response must mean a checked operation actually completed, not merely that a request was queued.

An ambiguous mutation leaves the draft sheet in a sticky unconfirmed state and suppresses automatic polling and further actions. It has no cross-document operation identity or recovery mechanism; closing or recreating a sheet could otherwise permit a duplicate while an old operation is still running. A browser-owned operation registry and explicit terminal resolution across document/profile lifecycle are required before this UI can be integrated. The sticky state is deliberate protection during this draft, not a completed user-facing recovery design.

`download_operation_registry.h` is an isolated, single-sequence native-state model. It assigns native tokens, keeps an item locked until an authoritative terminal outcome is acknowledged, scopes item keys by browser-owned profile-family and context-epoch identities, permits unrelated item operations, and makes Clear Finished conflict with a validated snapshot of affected items. A newly created trusted sheet can list outstanding operations, and internal code can inspect the affected clear snapshot. The standalone C++ test passed for same-item conflicts, distinct context keys, snapshot conflicts, pre-dispatch denial versus terminal observation, late events and acknowledgement. Context ownership is an external invariant; those tests do not prove real profile isolation. This model is not connected to DownloadManager, and its input keys, snapshot eligibility, caller trust and terminal signals still require native enforcement. In particular Chromium's open/show/cancel/resume interfaces can return before an OS or download outcome is known; dispatch is not terminal confirmation. It does not journal regular operations across process restart, promise recovery of private actions after OTR teardown, handle external native UI operations, or prove at-most-once behavior across browser crashes. The registry and its test provide no product parity or production security guarantee.

A reserved operation can be denied before dispatch; once marked dispatched, timeout, observer loss and partial batch completion stay unresolved and locked. Only a genuinely authoritative terminal observation can unblock it after acknowledgment. Registry integration must enforce real family/context-epoch ownership and visibility to prevent a recreated sheet seeing stale or private operations, and it must reconcile partially completed clears without deleting files. `List` and `ClearItems` are internal model APIs, not an authorization boundary.

The source-bound [native integration review](NATIVE-INTEGRATION-REVIEW.md) documents exact manager/epoch ownership and unsafe-state checks. In particular `IsDangerous()` alone misses some scanning states, native Open/Show do not report OS success, and Chromium Clear All can remove unsafe or active items. The registry's current terminal model therefore must not be wired as if those void calls confirmed success. Shipping-compatible retry and complete Clear Finished remain unresolved.

Presentation now requires an explicit `safe`, `needs-review`, or `unknown` classification; non-safe records show distinct statuses and suppress open/show/retry/resume, while allowing a native-authorized Cancel where the released row supports it. This does not classify Chromium danger enums or authorize commands. A separate native mapping must use a reviewed positive safe-state allowlist, handle future/unknown values as untrusted, retain meaningful warning/scan UI and recheck at dispatch. The existing raw native projection is not directly compatible and must not be wired to this presentation without that mapping.
