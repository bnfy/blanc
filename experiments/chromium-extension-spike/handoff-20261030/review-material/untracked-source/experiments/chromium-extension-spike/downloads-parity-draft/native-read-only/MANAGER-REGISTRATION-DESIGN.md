# Manager shutdown observation: proposed registration handshake

The unregistered epoch service must not adopt a manager merely because its pointer is non-null, its profile is live, its context matches or `IsManagerInitialized()` is true. `DownloadManagerImpl::Shutdown` (`content/browser/download/download_manager_impl.cc:725-749`) flips private `shutdown_needed_` to false, notifies `ManagerGoingDown` once, clears state and observers, and the object can remain addressable afterward. A late observer receives no replay. `Profile::ShutdownStarted()` closes a distinct profile teardown window but does not prove the manager has not independently shut down. The current `Adopt` draft assumes a future trusted caller has solved this handshake; no current caller supplies proof, so it remains unregistered.

Two designs merit review; neither is implemented or approved here:

1. **Atomic observe-if-running API:** add a UI-sequence-confined method to `DownloadManager` and the implementation that, in one non-reentrant operation, checks a manager-owned shutdown state and registers the observer before any shutdown can begin. It returns an explicit failure if shutdown already started. Define precisely whether a manager is observable before or after initialization and separate that from History readiness. The proposed method must cover the transition when shutdown first becomes irreversible and guarantee observer lifetime/removal through `ManagerGoingDown`; a separate `IsShuttingDown()` followed by `AddObserver()` is insufficient without a proven no-reentry invariant. The method is a native API change needing source, security, cross-platform and test review; existing `AddObserver()` provides no such acknowledgment.
2. **Creation-time lifecycle broker:** install a browser-context-owned broker and register its manager observer at the manager construction boundary (`content/browser/browser_context_impl.cc:288-307`), after the unique manager is allocated but before the delegate can reenter or any other code can obtain it. It rotates an unguessable manager generation on shutdown and supplies only scoped leases to the profile-family service; if an existing manager predates the broker and lacks this proof, report unavailable rather than attach retroactively. This crosses the content/chrome layering boundary and needs a reviewed callback/injection mechanism. `DownloadCoreServiceImpl::GetDownloadManagerDelegate` is invoked from the manager creation path and performs other setup, but is not by itself proof that no early/independent shutdown occurred. `MultiProfileDownloadNotifier::AddProfile` calls lazy `GetDownloadManager()` and then attaches a notifier; it does not expose an atomic no-shutdown registration guarantee and must not be treated as that proof.

For either design, the service tracks owner/profile generation as well as manager generation; invalidates lease and private rows on `ManagerGoingDown`, profile shutdown start and service shutdown; and revalidates weak owner, context, manager, document and generation immediately before and after any reentrant operation and immediately before reply. Observe callbacks cannot turn `OnDownloadDestroyed` into successful command completion. Grouped regular/private responses require both leases current at delivery. A browser-owned untrusted-renderer bridge never supplies or forges a lifecycle proof. Lifetime remains unresolved until a real browser implementation proves registration ordering, partial observation rollback, reentrant shutdown and late delivery.

Focused synthetic browser tests should invoke manager shutdown while its profile remains alive, attempt registration before and after shutdown, destroy the profile in each registration phase, start private teardown and recreate the same-profile manager, reenter creation/delegate callbacks, test duplicate registration and replacement, invalidate both grouped snapshots before delivery, and verify no stale notification is interpreted as successful action. No real user profile or Google baseline should be used. These tests and a guarded incremental build are not performed by this design.
