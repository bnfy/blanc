# Synthetic Downloads lifecycle fixture: build and safety plan

**Not compiled or run.** `synthetic-profile-lifecycle-unittest.cc` is an isolated candidate using Chromium `TestingProfile`, its actual context-owned `DownloadManagerImpl`, and the unregistered epoch service. It proposes early regular manager Shutdown, late registration, two self-removing observers and reentry during `ManagerGoingDown`; a test-manager replacement and stale old lease; synthetic primary-OTR destruction/recreation and refusal of delayed old-epoch delivery; and owner destruction followed by final manager shutdown. This is a candidate, not proof: `TestingProfile::GetDownloadManagerDelegate()` returns null (`chrome/test/base/testing_profile.cc:846-848`), and the manually constructed replacement does not follow the production getter/delegate initialization. It does not exercise a real `ProfileImpl`, real DownloadCoreService keyed shutdown, history, actual WebUI/document, download warnings, off-UI Shutdown, action outcomes or actual IPC delivery. The separate manager implementation test in `../candidate.patch` covers atomic-registration ordering only for the supported UI sequence and has not run.

## Profile isolation and cleanup

An independent review identified two fixture hazards, both corrected: every test now creates an owned `base::ScopedTempDir`, sets and verifies `chrome::DIR_USER_DATA` to that root before profile creation, supplies an explicit child path to `TestingProfile::Builder`, and unregisters a late observer if a broken candidate unexpectedly accepts it. The prior source is retained as `synthetic-profile-before-review.cc`. A follow-up review caught fixture member destruction order: `BrowserTaskEnvironment` is now declared last so it is destroyed first, while the user-data override and root still exist; `synthetic-profile-before-teardown-fix.cc` preserves the pre-fix source. The reviewer confirmed this specific order correction but has not established whether the task-environment constructor accesses global profile data before `SetUp`. A future runner must create and validate a separate disposable user-data root **before the test process starts**, pass it via the test launcher's supported user-data override, and ensure all global test setup uses it. The per-test ScopedPathOverride alone cannot prove that earlier process initialization was isolated. Stop before profile creation if the process-level root cannot be proven disposable; never use a production profile, Google baseline, or the running development browser. Verify any temp profile path remains beneath the owned root; leave failure artifacts only in explicitly owned disposable test paths and copy non-sensitive logs durably. Do not record paths, URLs or data from user profiles.

## Cache and scope findings

At inspection, the existing 158 output contains production `obj/content/browser/browser/download_manager_impl.o` and `obj/content/public/browser/browser_sources/download_manager.o`, but they predate the candidate. `testing_profile.o`, `testing_profile_key.o`, `fake_profile_manager.o`, `testing_profile_manager.o`, `browser_task_environment.o`, `test_browser_context.o`, mock-manager/test objects, and the `content_unittests`, `unit_tests`, and `browser_tests` executables are absent. The `testing_profile_impl` GN source set contains all four named profile-related objects; a hand-linked subset may omit unused members but its link closure is unproven. An inventory of the 38 archives in a previous unrelated standalone link found none with member names matching TestingProfile, TestBrowserContext, browser task environment, mock manager, gtest or DownloadManagerImpl; this does not prove symbols are absent under other names or establish a complete dependency closure. See `cache-inventory.json` and the preserved earlier inventory. The test harness also requires correctly initialized `TestingBrowserProcess`/Chrome test infrastructure and gtest; running a direct standalone main without equivalent setup is invalid.

**Do not link the two existing production objects or other stale consumers against the v2 patch.** It adds a virtual method in the middle of `DownloadManager`, shifting existing vtable slots. Old objects calling later virtual methods can dispatch incorrectly when mixed with a rebuilt implementation; a tiny ad-hoc cached-object link would not establish ABI safety. Recompile every affected consumer in a coherent isolated output or use a separately reviewed nonvirtual design. Moving a virtual to the end is not, by itself, proof that old derived-class vtables or embedders are safe. The entire dependency closure, compiler/linker flags and framework exports must be established before any standalone experiment; the former simple parser link receipt is not an adequate substitute.

For perspective only, even a hypothetical manual link would at least need fresh candidate `download_manager.cc` and `download_manager_impl.cc`, `epoch-service.cc`, this fixture, `testing_profile.cc`, `testing_profile_key.cc`, and `browser_task_environment.cc` (seven translation units), plus an appropriate test runner/gtest and whatever missing transitive objects the link requires. This is a lower bound, not a measured action count, complete build plan or assurance that linking any particular mix is safe. A GN build of the `testing_profile_impl` source set has four listed objects, not just the two needed by that rough estimate. The `content_unittests` target owns the real manager unittest; a Chrome test target must own the separate Profile fixture and epoch service. Neither runner is currently built. Adding a new focused GN test executable or modifying an existing test source set requires an isolated candidate GN change and review; do not run hooks, alter GN args/toolchain, or regenerate the shared checkout casually.
