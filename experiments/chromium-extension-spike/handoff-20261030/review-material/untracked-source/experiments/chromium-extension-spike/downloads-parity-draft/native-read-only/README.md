# Native Downloads read-only projection — isolated draft

Follow-up: [security classification draft and focused evidence](SECURITY-CLASSIFICATION-20261029.md) supplies a conservative native warning mapping and internal-row adapter. It is not registered or wired, and it deliberately leaves ordinary `NOT_DANGEROUS` rows unknown pending native policy and shipping-behavior review.

The October 29 GitHub latest release remains v1.45.0 at `6f1bc523d2f0d432d5c4119b9f7ec22a324dbd2d`. Shipping keeps active first, followed by private finished and regular persisted rows for a single local profile family, and its saved-files and retry behavior is described in `../NATIVE-INTEGRATION-REVIEW.md`.

`projection.{h,cc}` is unregistered, synchronous internal draft code using actual Chromium 158 APIs. Given a browser-owned regular profile and nonempty matching epoch pair supplied by its eventual service, it selects either that profile or its *existing* primary Incognito profile without creating one. It rejects other kinds, absent/mismatching epoch, wrong manager/context, duplicate or empty GUID and attached foreign browser context; uninitialized manager or unverified regular history returns pending. It copies the state, raw danger type, insecure status, native warning pattern and booleans, while granting no actions. Only a basename and HTTP(S) origin are copied; no path or full URL is emitted. GUIDs and timestamps are internal-only, not renderer identifiers. The code does not mutate download items, persist rows, or dispatch download commands. **Correction:** it is not side-effect-free: `GetDownloadManager()` may lazily create a manager and call into its delegate, and `DownloadItemModel` registers and removes an item observer. The former inline claim of no side effects has been corrected; this candidate is blocked from use.

**Not an authorization boundary:** The draft has no browser-owned service, registered lifecycle/epoch source, manager shutdown observer, trusted caller/document/window checks, raw-pointer lifetime proof across future IPC, item handles, cross-document operation registry, or bridge. Epochs and `regular_history_ready` are currently caller inputs; no code establishes or rotates these values, so matching them cannot yet prevent an ABA or stale-profile problem. Calls must be on the owner UI sequence; this has not been proven by runtime checks. Even a null attached context is accepted for history items based on manager ownership; this requires a synthetic real-browser test. The current draft has no display filtering for trusted extension, temporary, transient, hidden or missing-path downloads. It may include rows the native Downloads UI intentionally excludes; conversely an empty or path-shaped filename currently invalidates the entire projection, including early items whose filename is not yet available. It does not sort active/finished, implement shipping's 200-item limit, or provide browser-ready renderer rows. Bidirectional control characters, filename normalization, size overflow/unknown bytes and locale/display rules still need review. Origin-only display differs from shipping tooltip and needs product review. Warning fields are **not** a safe-state decision; in particular the native pattern alone can be normal for policy/scan states and cannot substitute for a reviewed allowlist.

A standalone `scope_test` compiled with Apple `xcrun clang++ -std=c++20 -Wall -Wextra -Werror` and exited 0, covering synthetic scope decisions, missing/wrong epochs, unknown scope, pending readiness and obvious filename forms. It does not instantiate a Profile, DownloadManager or DownloadItem. `check-syntax.py` invokes the cached Chromium 158 clang and build flags with `-fsyntax-only`; `syntax.log` passed with zero diagnostics on the previous source hash; a subsequent comment-only correction was not rechecked. The initial syntax attempt failed because `DownloadVector` holds `raw_ptr` elements rather than raw pointers; the failing log and command are retained as `syntax-initial*`. Syntax alone is not a link, build or runtime check. No Chromium production build, source staging, app launch, real profile or Google fixture was touched.

Before integration, implement the owner/epoch lifecycle and trusted document bridge, determine full history readiness, filter only appropriate records while retaining warning UI, create opaque document/family handles, and independently review reentrancy and serialization. Use disposable synthetic regular and primary-private profiles for native browser tests: primary teardown and recreation, duplicate GUIDs, guest/system/enterprise/foreign contexts, delayed history, all warning/scan states, unusual filename/size/URL values, item destruction and shutdown, private persistence/exposure, and unauthorized frames. Actions, clear, retry, file and registry outcome handling require their separate reviews. The existing adapter requires string states and drops warning fields: do not feed it these raw numeric state/danger/pattern values or naïvely map them to “safe.” The returned value does not bind a family or epoch and can carry private data beyond teardown if sent asynchronously. See `OWNER-AND-PRESENTATION-DESIGN.md` for the required lifecycle and fail-closed presentation contract. This is not product parity or an accepted gate; Electron remains paused and latency deferred.

## Lifecycle-only candidate, independently reviewed

`epoch-service.{h,cc}` is an unregistered `KeyedService`/profile and DownloadManager observer draft. It derives family and context generation tokens in native code, accepts only a trusted caller's existing regular or exact current primary-incognito manager (does not call `GetDownloadManager` or create OTR), issues internal scoped leases, and invalidates them when observed manager or profile teardown occurs. It does not invoke `projection.cc`, validate a WebUI or document, initialize history, observe items, send replies, create row handles, or change warning states. The `Adopt` API assumes its caller supplies native pointers whose manager has not begun shutdown and proves observation is registered before shutdown can begin. A live pointer or matching BrowserContext is not proof; there is no implemented caller or handshake. Weak and observer checks inside this draft do not by themselves prove reentrant safety, partial-adoption cleanup, or absence of stale manager callbacks. No profile, manager, object lifetime, or real browser test has run, and this is not a deployable service.

Chromium 158 syntax-only check `epoch-syntax.log` exited 0; `epoch-syntax-command.json` records exact compiler flags and source hashes. Ten `epoch-model.test.cjs` cases passed (`epoch-model-v2.log`) for the *separate synthetic JavaScript model*: independent epochs, old private lease after recreation, shutdown, teardown during adoption, wrong/duplicate scope, delayed delivery and profile shutdown beginning before observer notification. They do not invoke or test the C++ service. The independent reviewer confirmed the profile-shutdown checks but identified the unresolved manager-adoption prerequisite; preserve this isolated candidate and do not expose it until real synthetic-profile, manager-teardown, reentrant observation and document-delivery tests pass.

Independent review identified the interval between `BrowserContext::NotifyWillBeDestroyed` and `ProfileObserver::OnProfileWillBeDestroyed`. The v2 candidate rejects owner or private `ShutdownStarted()` before and after adoption and on lease capture; its initial syntax command and seven-case model log remain preserved. This is a source-level repair and synthetic model evidence, not a real teardown proof. A manager can remain addressable after its `ManagerGoingDown` callback has already fired: a trusted future owner must prove pre-shutdown manager lifecycle, beyond checking a live profile or pointer.
