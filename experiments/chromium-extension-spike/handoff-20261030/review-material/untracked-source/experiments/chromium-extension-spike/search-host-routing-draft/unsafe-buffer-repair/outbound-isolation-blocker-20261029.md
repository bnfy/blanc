# Search fixture outbound isolation blocker — 2026-10-29

The retained `browser-search1.json` and `browser-search1.log` show that the fixture's outer outbound-denying `sandbox-exec` preflight ran, but Chromium's own renderer and network-service sandbox initialization repeatedly failed with `Operation not permitted`; the CDP target crashed before the product checks. The isolated browser process exited normally. No selected-provider browser check passed in this run. This is evidence of incompatibility in this launch environment, not proof that all macOS sandbox nesting or every alternative is impossible.

Do not disable Chromium's sandbox, drop the outbound-denial requirement, depend on per-target CDP interception, alter system firewall/routing/DNS, or touch user profiles. CDP events can miss network traffic from other processes or targets; interception alone is not an independent boundary. Proxy flags and host resolver rules also do not prevent all outbound connections.

A possible independent boundary is a **new dedicated offline macOS guest** with no externally connected guest network interface, isolated non-user profile and a loopback fixture server inside the guest, running the verified 158 candidate with Chromium's normal security sandbox enabled. This option is not yet established as available or tested. Before accepting it, verify guest provenance and isolation, exact candidate/source/assets/receipt hashes, no guest outbound IPv4/IPv6/DNS route with independent positive/negative network probes, working loopback fixture and CDP, actual renderer/network service startup with their normal sandbox, clean browser exit and no personal-profile access. Record failures and guest execution details; do not change the networking or data of any existing VM. Assess guest performance/resource and dependency scope before provisioning, and only proceed within the owner's authorization and platform licensing.

## Lower-assurance local exploration, not acceptance

A separate opt-in exploratory harness could use a fresh disposable profile, the verified executable and assets, a synthetic loopback HTTP server and synthetic searches exclusively. Chromium would launch normally with its own renderer and network sandboxes; no outer `sandbox-exec` or `--no-sandbox`. Use actual Settings controls to add and select a synthetic `http://127.0.0.1:<port>/?q=%s` provider, then observe ordinary typed search, explicit search, selected custom-provider routing, new-tab commit, stale intent rejection and primary-private isolation against that local server. Confirm the added engine is effective before entering any search; abort if Settings, selected-provider initialization or navigation is ambiguous. Test input must be fabricated and contain no user or account data. A private-mode local-server request is not by itself a full proof of absence from persistent History; check the closed disposable profile separately.

An explicitly configured local rejecting HTTP proxy, `--disable-quic`, restrictive Chromium host-resolver rules and target-level CDP `Fetch` interception could reduce accidental remote requests, with separate local proxy and CDP logs. They cannot guarantee that all browser/service processes, direct IP connections, non-HTTP protocols, DNS or every newly created target are intercepted. They are therefore **best-effort mitigations only**, not an operating-system network boundary, privacy guarantee, proof of no outbound traffic, or permission to enter real search queries. Exact settings must be verified before a run. This can provide limited evidence for the loopback custom-provider path only; it does not close the independent outbound-denial prerequisite, the two stock-provider checks, or overall fixture acceptance.
