# Deterministic visible-background investigation (design only)

`sunrise-c` observed a background tab with renderer `document.visibilityState === "visible"` and received a grant on f318. The later v2 foreground check passed with a hidden renderer; `fg-visible-background` was inconclusive because the renderer was hidden. Do not call that a reproduction or a confirmed fix. No additional browser attempt is implied by this document.

## Existing Chromium behavior to investigate

In Chromium 158 `content/browser/web_contents/web_contents_impl.cc`, `UpdateWebContentsVisibility` keeps visibility visible for an opted-in WebUI through its first visually non-empty paint and also documents that `CreateParams::initially_hidden = false` may leave a never-shown WebContents initially visible. Before `did_first_set_visible_` becomes true the implementation ignores a request to hide it. These paths could produce the observed mismatch, but the retained sunrise-c evidence has no browser-side visibility sample, no creation flag, and no first-paint timing, so this is a hypothesis, not the diagnosed cause. `document.visibilityState` is renderer state and is not by itself proof of `WebContents::GetVisibility()` or of the membership seen by the synchronous native grant.

## First line: deterministic composition test, no browser mutation

Use the existing fake TabStripModel test with a control active, background target in the model, no split, and assert the exact `SunriseForegroundMember` helper returns false. Separately compose the existing `LaunchSunriseContentsAttempt`/`LaunchSunriseGate` under `enabled=true`, regular context, all actual visibility inputs true and membership false: deny the claim; on a fresh active contents the same process gate must still grant once within 30 seconds. Exercise active and inactive split membership plus inconsistent state. The helper-only test already covers the membership result; a source-level composition test must explicitly exercise the gate and record precise source hashes. It is fast and deterministic but cannot prove the production call site passes the right values, that Chromium can enter the inconsistent state, or that the released binary behaves correctly. Do not weaken, stub, or substitute the production gate in the claimed test.

## Stronger integration design if the remaining uncertainty warrants a test build

Prepare a dedicated, ephemeral native browser-test binary using the exact v2 source and cached 158 toolchain, with all instrumentation compiled only into that test target, never into the development app or a renderer-facing interface. Before building, dry-run the real target and disclose the action count; the existing broad test target was previously expensive and is not implicitly authorized here.

On the UI sequence, create a fresh disposable regular browser/profile with the setting enabled. Create a `WebContents` with `CreateParams::initially_hidden=false` and arrange it as an inactive tab without first showing it, using supported TabStripModel insertion APIs. Keep another tab selected; assert no active split or Glance, target is inactive, and actual `GetVisibility()==VISIBLE`. Fail as inconclusive if Chromium normalizes visibility before the claim. Load a real trusted Start Page in that WebContents and trigger the normal first `start.data()` request. A native test-only observer at the exact `ClaimSunriseForTrustedStart` decision point records, in one UI-sequence event, active and target identities, native split membership, container/drawn and widget inputs, `WebContents::GetVisibility()`, `foreground`, final visibility predicate, and result. It exposes no WebUI/JS bridge and must not alter any predicate or result. Require native visible + inactive + no split + denial; then require a fresh selected visible tab to get the one still-unspent grant within the 30-second window. Confirm trusted document and private/profile restrictions separately rather than bypassing production validation. Collect exact revision, test-target and artifact hashes, build commands/guard, complete logs and exits.

If naturally constructing the initial-state path proves impractical, an alternate **test-only forced state** may call the existing public `WebContents::WasShown()` on the inactive test tab immediately before the real claim, on the UI sequence, then assert the same native preconditions. This is a deliberate inconsistent-state stress test, not proof that a spontaneous user workflow reproduces sunrise-c; record that distinction prominently. Do not use a JS visibility override, fake native grant, forced renderer property, unsafe bridge, or production hook. Observer callbacks must be removed with the test binary and have no data-exposure path in the shipping build. Exact v2 development output remains unmodified.

Even a successful instrumented test is evidence about the separately built test binary and exact source, not by itself a runtime test of the uninstrumented `ee7517...` app. The prior Settings/private checks remain f318 observations, not v2 acceptance. Real write-failure, managed policy, accessibility, visual and lifecycle coverage remain open. This design does not authorize staging, a build, launching a fixture, replacing the open dev browser, or full parity/release credit.
