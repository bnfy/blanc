# Interrupted diagnostic build: prepared recovery, not executed

This procedure addresses an actual failed/interrupted **diagnostic build** after its recorder captured its own PID, build process group and exact owner/inode/hash identities for both cooperative locks. It does not imply that a diagnostic run has failed or authorize a new build. Preserve all prior source, output, cache and evidence. A missing/ambiguous recorder PID, process-group ID, build log, staged receipt, lock ownership, baseline backups or cached UI object fails closed; the case then requires separate investigation rather than reconstructing ownership or clearing anything. An interrupted pre-build plan, incomplete lock-creation receipt, partial lock release, failed recovery build, unobservable process exit, or altered source requires its own reviewed recovery. PID reuse also stops this procedure.

The diagnostic recorder now records its owner PID and both lock identities before recheck/build. `audit-focus-failed-recovery.py` performs a read-only state audit of the failed receipt, build log, pinned manifest and staged source/preimage; verifies the trusted groups baseline and backed-up app/framework/object; requires the recorded owner and process group to be absent, no Siso/Ninja/autoninja/caffeinate process, and the exact two locks; and snapshots the actual partial app, output framework and UI-object hash. A failed build may have modified those objects: they are retained and recorded, not assumed to equal the old baseline. The audit writes only a fresh durable evidence directory and leaves both locks intact. It cannot prove that a non-cooperating process or an earlier heartbeat is absent; the independent monitor-drain prerequisite remains open.

After inspection and separate review of the audit, the release phase takes its exact SHA-256. It repeats the monitor status, process/group, evidence, source, backup and partial-output checks; verifies the original lock inodes/owner bytes; creates a durable release journal and writes intent before each removal. It removes only the two recorded owner files and empty owned lock directories, rechecking before each removal. A changed owner, reused PID, changed output, incomplete or foreign lock, active build or uncertain monitor stops the operation. An interrupted release may leave one lock and a pending journal; stop and inspect rather than retrying blindly. The script never sends a signal, changes source, deletes a profile, alters output or clears caches.

After monitor drain is independently established and the failed attempt actually exists, run from `Chromium Preview/repo` with fresh lowercase labels and inspect the resulting receipt before any release:

```sh
python3 experiments/chromium-extension-spike/start-page/groups-projection-draft/audit-focus-failed-recovery.py audit STAGE BUILD AUDIT monitor-paused-no-inflight
python3 experiments/chromium-extension-spike/start-page/groups-projection-draft/audit-focus-failed-recovery.py release STAGE BUILD AUDIT monitor-paused-no-inflight REVIEWED_AUDIT_SHA256
```

After verified release, the already-prepared stage transaction can restore only its exact source preimage while advancing timestamps and preserving its journal. `record-focus-failed-restore.py` requires the exact original staged receipt hash, failed receipt/log, reviewed audit and completed lock-release receipt, unchanged audited partial output and the preserved baseline backups. It takes a fresh plan with a bound of one to six dry-run actions and rejects generators; this is a guard, not a forecast of actual scope. Inspect the entire plan and command-multiset digest before any build. A separately invoked build requires the reviewed digest, rechecks all provenance and toolchain data under cooperative locks, and monitors observed starts against the preserved six-target closure. Observation is best effort and may occur after a command starts; it is not a hard pre-execution boundary. The final ordinary zero-action guard and complete app, output-framework and UI-object comparisons must exactly match the groups candidate before it is called restored.

```sh
python3 experiments/chromium-extension-spike/start-page/groups-projection-draft/stage-focus-branch-diagnostic.py restore STAGE monitor-paused-no-inflight
python3 experiments/chromium-extension-spike/start-page/groups-projection-draft/record-focus-failed-restore.py plan RESTORE STAGE BUILD AUDIT monitor-paused-no-inflight
python3 experiments/chromium-extension-spike/start-page/groups-projection-draft/record-focus-failed-restore.py build RESTORE STAGE BUILD AUDIT monitor-paused-no-inflight REVIEWED_RESTORE_PLAN_SHA256
```

The `monitor-paused-no-inflight` argument is operator attestation, not independent proof of scheduler drain. Keep the monitor paused and its diagnostic exclusion active until restoration is verified and separately reviewed. If a recovery or restore stops, preserve its files, journal, cache and retained locks; do not rerun automatically. The prepared scripts have only synthetic checks and remain subject to independent review. No live audit, lock removal, restore, build, signing, profile change or monitor change has been performed.
