## Prepared transaction and restore drafts

`stage-focus-branch-diagnostic.py`, `record-focus-branch-diagnostic.py`, and `record-focus-restore.py` are isolated, review-required drafts; none has been run on the checkout. The stage transaction binds `build-closure1` and its complete app inventory, saves and flushes full app, output-framework, UI object and source preimages before mutation, journals replacement, and revalidates source timestamps and backups. Exception rollback rechecks the monitor and active build immediately before source writes; if either is uncertain, it preserves the journal and both owned locks. The restore step records the original staged-receipt hash before updating the journal. The restore recorder binds that hash to the diagnostic build receipt, checks the exact diagnostic app, output framework, UI object and zero-guard evidence before a plan, and accepts restored output only when the full app, framework and UI object exactly match the pinned candidate backup after a zero-action guard. Only synthetic transaction, provenance, owned-child monitoring and exit-receipt tests have run.

The stage and recorder require the keep-open automation to report `PAUSED` in its saved configuration and require the operator's `monitor-paused-no-inflight` attestation. **Neither proves an earlier heartbeat has drained.** The available automation interface observed during preparation does not expose authoritative in-flight heartbeat execution state. An independent scheduler/run drain check, or an equivalent independently reviewed coordination mechanism that includes already-started runs, remains necessary before staging. The monitor currently prohibits promotion of unverified configurations; a durable diagnostic sentinel honored by an updated monitor could add a further barrier, but cannot retroactively bind a heartbeat already running with the old prompt. No monitor has been paused, updated or marked drained here. A paused monitor or sentinel alone is not sufficient evidence of drain.

After independent review and confirmed coordination, the staged plan phase is intentionally distinct from compilation:

```sh
python3 experiments/chromium-extension-spike/start-page/groups-projection-draft/stage-focus-branch-diagnostic.py stage FRESH_STAGE monitor-paused-no-inflight
python3 experiments/chromium-extension-spike/start-page/groups-projection-draft/record-focus-branch-diagnostic.py plan FRESH_BUILD FRESH_STAGE monitor-paused-no-inflight
```

`FRESH_STAGE` and `FRESH_BUILD` denote fresh lowercase labels using letters, digits and hyphens. The diagnostic recorder refuses a plan count other than one and uses the previously reviewed six-target observed-start closure; provisional Siso totals can be larger. Present the actual full dry-run commands, count and normalized digest to the operator. A separately invoked build requires that exact reviewed digest, and stops if the plan, baseline, environment or observed action starts change:

```sh

```

If a build or restoration is interrupted, if monitor coordination is uncertain, or if the exact original app/framework/object cannot be reproduced, preserve the source, output, cache, journal, logs and owned locks; do not resume the keep-open monitor or claim safe recovery. The prepared restore recorder currently requires a successfully verified diagnostic build receipt; it does not provide an automatic recovery path after a failed diagnostic build. The sentinel/drain prerequisite, independent review and this failed-build recovery limitation remain open.
