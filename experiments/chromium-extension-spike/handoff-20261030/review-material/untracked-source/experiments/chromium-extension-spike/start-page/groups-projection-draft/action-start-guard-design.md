# Observed-action guard: isolated review draft

The failed `groups1` and `resume1` builds emitted one `S CXX` for the intended UI object, followed by `- CXX` cancellation and zero completed actions. Their provisional denominators reached 556 and 972 respectively; these numbers do not, by themselves, establish that that many actions started. The previous successful baseline restore (`stage-sunrise-a/restore-build.log`, SHA-256 `3ca6080080c101c58e2a56b673c45f8a6dda4ee688d0a122e6158987dd27c10b`) planned one CXX command yet logged six `S`/`F` pairs: the UI object compile, framework link, framework bundle-data copy, framework verification, app bundle-data copy and app verification. That recorded closure is evidence for this exact past output, not a guarantee that every future valid build has only those actions.

The installed Siso reports `v1.6.7`; its `version` command printed the CIPD instance but could not look up package Git revision due DNS, so exact source correspondence was not independently established. Chromium's published Siso source at another revision documents `S` as a started step, `F` as finished, `-` as cancelled and `c` as cache hit, while progress totals are calculated from changing total/skipped counts. These descriptions are consistent with the retained non-terminal logs; do not conflate another revision's source with proof of this binary's full behavior. See [Siso builder progress](https://chromium.googlesource.com/build/+/a70a06976a5edb44c35445edaa7b017fc8155690/siso/build/builder.go) and [Siso progress output](https://chromium.googlesource.com/build/+/17244db1152d10a2292fbaab02957e2bb7f39733/siso/build/progress.go).

`action-start-monitor-draft.py` and `action-start-guard-draft.py` are isolated and **not wired into a build runner**. The former verifies the entire preserved successful log hash and extracts exactly six unique permitted action descriptions. It parses non-terminal records and accepts only one `S` followed by one `F` per allowed description. An unknown, duplicate or excessive start; an unmatched finish; cache/retry/fallback/cancel/error marker; malformed progress; or missing/mismatched successful summary is refused. Large changing denominators are recorded, not treated as actual starts. The latter observes an owned new-session process's saved log and signals that process group on an observed violation, requires actual parent/group exit, and requires callers to preserve locks and logs on any uncertainty. It does not invoke Siso, change the existing recorder, modify locks, or start a build.

The saved successful and stopped logs replay correctly, and synthetic tests cover chunked records, large provisional totals, unknown/duplicate starts, unpaired finishes, cache hits, missing output, a successful six-action synthetic child and an unexpected-action owned-group stop. These tests do not prove Siso 1.6.7 will always emit complete non-terminal records or that an action's textual description uniquely identifies its command and dependencies. A different valid incremental closure will stop conservatively. Events are observed after a process starts; polling, buffering and scheduler concurrency can let unreviewed work begin before detection, and unlogged work may be detected only at the final count or not at all. This is a best-effort audit and stop mechanism, not an enforceable pre-execution action limit or a substitute for the exact fresh dry-run command digest, live process inspection, same-guard build/zero guard, artifact inventory or owner scope review. No existing evidence, output, cache, profile, lock or app was changed by preparing this draft.

Review corrections: processing now consumes complete lines before enforcing the 1 MiB bound on the remaining incomplete line, and the guard reads at most 64 KiB per operation, draining buffered output after process exit. A success must include both the pinned candidate UI CXX start and its finish; empty or other-only success is rejected. Large multiline, UTF-8 chunk boundary, truncated/missing event and multi-chunk tests pass. `record-groups-closure-draft.py` now has a separately invoked plan mode; its actual start-event build-stream helper has only been integration-tested with disposable synthetic child processes, including receipt/PID updates and an unexpected-action group stop. It now binds both stopped runs and the completed second owner-checked recovery receipt; plan availability is not build authorization. Its group recorder, locks, current failed-build provenance, real Siso output and action identity need a fresh joint review before any use.

`recover-resume1-locks.py` is the separate, unrun owner/inode-checked recovery draft for the second stop (owner 57362, group 57396); it binds the second receipt/log, first failure and prior completed recovery, staged source and full trusted baseline. The closure recorder rechecks both rounds’ retained plan logs and the same one-action digest, both old process identities, the exact completed recovery2 receipt and exact baseline before plan/build. Synthetic provenance, tamper, owner/inode and actual recorder-helper tests pass. Neither a second lock recovery, a real fresh plan nor a build has run as part of this draft.
