# Navigation identity plumbing for blocker statistics — review-only

The latest published Blanc release was verified as v1.45.0, source `6f1bc523d2f0d432d5c4119b9f7ec22a324dbd2d` (October 29, 2026). Its `src/main/adblock-stats.js` and `src/main/blocking-providers.js` are byte-identical to v1.44.1; the statistics request callback, aggregation and Start Page projection paths were checked in the changed files and retain the earlier observed semantics. Those changed files also contain other product changes; this check is not a complete v1.45.0 product-parity audit. The separate Google extension baseline was not inspected or modified.

## Finding and candidate

Chromium 158 `content/public/browser/content_browser_client.h` documents that the browser's `navigation_id` applies to `kNavigation` factories and equals `NavigationHandle::GetNavigationId()`. The existing Blanc `ContentClientParams::FinalizeBlancFactory` passes context, frame, type and isolation, but discards this ID. In the separate `NavigationURLLoaderImpl::CreateNetworkLoaderFactory` assembly path, the immediately preceding upstream browser-client hook receives `frame_tree_node->navigation_request()->GetNavigationId()`, while the independently constructed Blanc `ContentClientParams` currently supplies no ID.

`prepare.mjs` copies the exact current 158 native sources to the separate durable `Chromium Preview/evidence/blocker-navigation-id-20261029-v2/candidate/` tree and records the original and candidate SHA-256 identities in `manifest.json`. The candidate adds an optional integer to the public Blanc wrapper, propagates it in both ordinary and DevTools-override factory paths, preserves the value through the browser-client call, snapshots the navigation ID before the explicit navigation path invokes browser/DevTools callbacks and uses that same snapshot for both, and stores it in the factory context only for `kNavigation`. Non-navigation factory contexts forcibly receive an empty ID. No URLs, client-provided request IDs or profile identifiers are substituted. The candidate does **not** consume, emit, log or persist the ID, change blocking decisions, count any request, write prefs, or claim complete statistics.

The exact source used is the currently built 158 checkout. Its `chrome/services/blanc_blocker/blocker_proxy.cc` differs from the repository canonical copy at `BindCosmetics`: the built copy uses `base::MakeSelfDeleting` while the repository copy says `new`. Neither copy was changed. This difference must be reconciled by the owner of production source before any staged build; do not overwrite either file as part of this draft.

The first generated candidate is retained under `evidence/blocker-navigation-id-20261029/`. It read the ID again after the DevTools callback; v2 snapshots once, so it does not attribute a replacement navigation to an earlier factory if the callback changes the active navigation. No build outputs were changed.

## Verification and limits

`syntax.py` uses the existing 158 generated Ninja target flags and cached generated headers, a read-only Clang VFS overlay pointing at the isolated candidates, and `-fsyntax-only`. All three actual candidate translation units compiled successfully: `url_loader_factory_utils.cc`, `navigation_url_loader_impl.cc`, and `blocker_proxy.cc`. Commands and logs are retained in `syntax-results.json`, `*-command.json` and `*-syntax.log`. This is compilation/syntax evidence only: no linking, Ninja build, runtime callback, event attribution or behavior acceptance. `verify.mjs` confirms both factory paths, the single snapshot across upstream and Blanc calls, non-navigation filtering, source hashes, and absence of navigation-ID event logging. `verify-initial.log` retains a fixture assertion that mistakenly expected five rather than four variable occurrences; `verify-final.log` passed. Neither check establishes actual request identity.

Before counting, prove in an isolated instrumented Chromium browser that the exact navigation ID is shared by the appropriate loader and NavigationHandle through redirects, DevTools replacement and restart, cached/prefetched response, cancellation, separate regular/private BrowserContexts, and activation. A prerender activation is itself a NavigationRequest and may have a different ID from its earlier prerender load: do not assume those IDs match, and do not merge them without explicit evidence and correct semantics. Check cases where the navigation factory is used for more than one request and worker factories, which do not get this ID. Establish a bounded lifecycle-owned context-scoped deduplication mechanism that cannot use stale entries or infer identity from URLs; ensure all blocked paths and startup/crash/week continuity are covered before exposing a complete count. Guest/private exclusion, device-vs-profile behavior, persistent migration and write failures, timezone rollover, UI rendering, and accessibility remain unqualified. IDs must remain memory-only and absent from logs and persisted data. The original profile, live browser, native checkout/output, 157 fallback and separate Google baseline remain untouched.

The repository's `prepare_final_factory.mjs` and related tests must be updated together if this is taken forward: changing only these generated copies would not survive a fresh source preparation. Check the exact live incremental build scope after any authorized staging; modifying a public content header could have a broad rebuild impact. No cold build or full build was started.
