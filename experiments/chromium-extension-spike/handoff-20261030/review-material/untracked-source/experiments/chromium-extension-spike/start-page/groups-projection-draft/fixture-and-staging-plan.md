# Groups projection: isolated verification and guarded staging plan

`syntax-check.py` compiled the isolated 158 UI candidate with cached Chromium flags, checkout include paths and `-Werror -fsyntax-only`; `syntax-command.json` and `syntax.log` preserve the inputs and output. This is not an object build. `assets-v1` is a separate 78-file copy of the current verified development assets with only the two reviewed Start Page JS files changed; `manifest.json` and `inputs.json` bind source and assets. Existing development, search and Sunrise assets/artifacts were not changed.

`browser-check-groups.mjs` is an unrun, syntax-checked, review-required CDP fixture derived from the owned-process guards used in earlier Sunrise fixtures. It requires an exact verified build/manifest/zero-action receipt, matching native source, assets and blocker inventory, no conflicting build, both coordination locks, loopback-bound proxy/server and a fresh durable disposable profile with DevTools port 0. It exclusively creates a per-label preflight record before validation and records validation failures, binds the complete candidate bundle inventory (including executable, framework and symlinks) to the trusted build receipt, preserves browser logs/results, rejects nonzero process exit and has bounded owned-process/listener cleanup; the proxy does not prove host-wide outbound denial. Regular scenario proposes a local two-tab group, Start Page chips and first-tab activation in all four layouts, group rename refresh and background action refusal. Private scenario constructs a private group, checks the native `groupsRead` response is empty and the Start Page exposes no group action/chips. Fake tests cover failure/retry and keyboard focus only; actual failure injection, minimized/background window, cross-window moves, malicious untrusted frames, lifecycle reentrancy, mouse/keyboard/VoiceOver, real shipping visual comparison and mixed-window difference remain open. The scenario itself needs independent review and a real run before it is evidence.

Before staging, independently review the native observer/lifetime logic, fixture, asset delta and exact source base. Reconcile any concurrent search/Sunrise work instead of overwriting it; preserve their unverified candidate app/assets and receipts, the verified baseline app and 353-entry inventory, profiles and active development process. The automatic reopen monitor must not see an unverified output as eligible. Stage only after a dedicated transaction is prepared with cross-operation guard, fsynced preimages/journal, timestamp-safe replacement and conflict-aware full prevalidation; the Sunrise staging script is not directly reusable because this overlay has a different source manifest. The source update is one native .cc file; copying candidate assets does not authorize promotion.

While holding the shared guard and with no active build, run the prepared recorder’s `plan` phase, which invokes Siso with the same pinned environment and exact offline/eight-worker dry-run flags as `build.mjs`, against that reviewed staged source, saving the whole plan and exact action count to fresh durable evidence. The current draft has not been staged, so no exact candidate scope is available; an earlier two-action plan is not a substitute. Stop before compilation for a cold/unexpectedly broad plan, regeneration or environment drift. Only then may an authorized incremental build proceed, followed by the standard zero-action guard and a receipt binding the exact source, manifest, assets, framework and plan. The recorder binds full app inventory and its hash to the build and zero guard in the same continuously guarded transaction. The separate post-hoc inventory binder is withdrawn; independent review is required before using the recorder receipt for the two focused scenarios. Preserve failures and clean only proven exited owned fixture profiles. Never restart the open development browser solely for this check, overwrite search/Sunrise preserved artifacts, or infer full parity from these focused results. If restoring, use the journaled source preimage and ensure Siso observes its timestamp; rebuild incrementally and verify both the known framework hash and all baseline inventory entries.

Prepared, **not executed**: `stage-groups-transaction.py` adapts the timestamp-safe, intent-journaled Sunrise transaction to the one-file groups overlay. It preserves and rechecks the complete baseline app, separate output framework directory, affected native object, source preimage, search candidate and both retained Sunrise candidate apps/assets. It does not duplicate the entire Chromium output directory or cache. It refuses symlink targets escaping each inventoried tree. `stage-groups-transaction.test.py` passed disposable restoration/timestamp/fault cases; `inventory.test.py` passed internal/escaping symlink cases. Standard fsync is not an established hardware power-loss guarantee.

`record-groups-build.py` is a prepared, **unrun** two-phase recorder. `plan` records the guarded incremental dry run and stops at `planned`; `build` is a distinct invocation requiring the same stage/manifest and an unchanged rechecked action count. Following any separately authorized build and zero guard it captures and hashes the complete app inventory in that same recorder transaction while holding the shared guard, rejecting escaping symlinks, before marking the receipt verified. Locks coordinate only participating processes, and do not prevent non-cooperating writers or a separate automatic monitor from launching an output; inspect actual processes and monitor state. A post-hoc binder cannot prove association with the original guard and has been explicitly withdrawn. None of these files authorizes staging or compilation.

The stage transaction verifies both the live and copied 353-entry app against a hash-pinned trusted baseline receipt before mutation; it also compares the live and copied separate output framework against the corresponding baseline inventory. The isolated plan parser checks normalized full action commands, rejects missing/count-mismatched actions and generated build flags, and passes its disposable tests. None of this has been run on the checkout.

`operation_lock_groups.py` is the prepared owner-checked guard used by the groups transaction and recorder. It never removes an existing lock, preserves and reports an uncertain lock if owner creation fails, and preserves the original error. The disposable owner-write/existing-lock tests passed. The browser fixture has equivalent ownership tracking and creates its result JSON exclusively with fsync; a failed owner write is reported without deleting an uncertain lock. These cooperative locks cannot prevent an unrelated process that ignores them.

The recorder's build phase now observes Siso's advertised live `[completed/total]` and final step totals and, if the observed maximum exceeds the lower of the reviewed planned action count and the 1,000-action incremental cap, sends SIGTERM to the separately created, owned build process group. It retains logs, cached outputs, receipts and locks if the group cannot be proved exited; it does not clean or silently resume. The synthetic monitor tests include a spawned worker in the same process group. Progress is observed by polling: actions can start or finish before detection, totals may be unavailable, and the dry-run count or monitor is **not a hard upper bound**. The user must review actual staged scope and this limitation before any build.

Both recorder and fixture now fsync the evidence-directory ancestor chain, as well as their records; tests exercise the path sequence. This is not a guarantee against every hardware power-loss mode. An unrelated Start Page data refresh can redraw other layout content, but unchanged group sections now retain their rendered nodes and focused group control; a synthetic test exercises the real group render functions across four fake layouts. The copied assets and manifest were regenerated. No checkout staging, build or browser run has occurred.

The live cap is the reviewed plan count when it is below 1,000, not an allowance to expand to 999 actions. Siso totals can initially advertise unpruned work and later shrink (the earlier v2 build showed this), so this conservative policy can stop a build whose eventual work would have been smaller. Any stop needs investigation; do not silently resume or infer a completed build. Polling remains best effort, not an enforceable hard ceiling.

The actual `regular1` run failed before its first group check with `Timed out: visible group in ledger`; the fixture closed its owned browser with exit 0 and preserved the profile and result. Its result contains no native group or DOM snapshots, so it does not establish the product cause. The original fixture requested layout through the head-installed adapter as soon as the function existed, before the renderer's data-ready event and status listener were guaranteed installed; this is a concrete test readiness race, not proof that it caused the timeout.

`browser-check-groups-ready.mjs` is a separate, unrun revision. It installs a marker before navigation, waits for the real `blancStartDataReady` event, then opens the real Customize popover and selects each visible, unobscured layout button using CDP pointer events; group activation also uses a visible pointer target. Failures retain page URL, ready/layout/document visibility, Start Page content geometry, group IDs/text/visibility/retry state, scoped native `groupsRead`, host tab/group snapshot and bounded console events where available. Diagnostics themselves can time out and are recorded as such. `fixture-groups-readiness.test.mjs` passes synthetic event ordering, target visibility/occlusion and diagnostic wiring checks; this does not prove the browser will pass. `regular1`, its logs and receipt remain unchanged. No rerun or product change was made.

`private1` passed its original narrower fixture with a native empty `groupsRead`, no observed chips and exit 0, but that fixture did not wait for the renderer data-ready event and its focus call was rejected in JavaScript using a foreign ID. Treat it as preliminary, not proof that native focus rejects an actual private group. The unrun readiness revision now waits for the private data-ready event, captures the real private group ID, sends that ID directly through the native `blancNewTab` focusGroup message, requires false and an unchanged active tab, and also checks the adapter result and absent chips. The synthetic readiness test exercises the raw native-request fixture wrapper and asserts those gates are present; it is not a native browser result. Existing `private1` evidence remains unchanged.
