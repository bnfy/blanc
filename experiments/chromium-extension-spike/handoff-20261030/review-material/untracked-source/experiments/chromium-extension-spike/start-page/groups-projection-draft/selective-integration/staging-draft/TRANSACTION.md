## Durable backup, crash protocol and rollback

First reserve a fresh unique durable journal directory with exclusive creation; fsync it and its parent. Record current source/GN/modules' type, device, inode, size, mode, nanosecond mtime/ctime and content hash, candidate identity, path and expected action, plus profile/app process and monitor status without URLs or personal data. Capture and fsync verified source and GN preimages, the complete current group app inventory and app copy, output framework and UI object (including symlinks/modes) against the earlier trusted group receipt. A graph-backup design must enumerate the concrete GN/Siso output write set and prove restoration of that set, or use a separately reviewed independent disposable output; metadata identity alone is insufficient. Preserve the live output and caches, do not clean or overwrite them. Independently check the original and backup inventories again; stop if the app/framework/output changed during capture, free space is inadequate, or a running process could mutate them. Avoid copying or changing the user's profile.

Fsync journal files and their directories in the specified order, while recognizing that fsync alone does not guarantee power-loss recovery on every filesystem. Durably write every path and pending action before first mutation. Use guarded path-relative opens and descriptor-based checks to reduce symlink/race exposure, exclusive temp creation in the target directory, write/fsync, atomic rename and directory fsync. Verify current preimage identity again immediately before each replacement; For candidate-created files, use an atomic no-replace operation such as a reviewed macOS exclusive rename; an absence check followed by ordinary rename/replace is racy. Journal success after each replacement. No multi-file atomicity is claimed. A process crash leaves the journal and locks for human inspection: do not delete an ownerless lock without proving its owner/process and all affected file states. Reconcile each target only if it matches the journal's old or transaction-written identity; any third-party change, uncertain inode or unexpected directory content stops rollback and preserves evidence.

Record original timestamps as evidence, but do not restore old mtimes blindly. Stage and rollback replacements with timestamps strictly newer than affected compiled object/dependency metadata and the GN graph as applicable; check clock skew/future timestamps and filesystem resolution, abort if the invariant cannot be established. Restoration replaces preexisting files only if still exact transaction-owned staged bytes; remove newly created modules only if their transaction identity is intact. Remove an empty directory only if the transaction created it and it remains unchanged. After any rollback, explicitly label outputs unverified: restoring source bytes does not restore an already-regenerated graph or linked app. Do not automatically rebuild or replace the running app. A separate reviewed graph restoration and incremental rebuild/guard is required if output changed.
