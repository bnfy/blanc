# Start Page mixed/private group parity — source and design

## Verified reference and current candidate

GitHub's latest release was rechecked on October 29: v1.45.0, commit `6f1bc523d2f0d432d5c4119b9f7ec22a324dbd2d`. The exact release `src/main/main.js` SHA-256 is `a93d43a2ada7a63c4ca993701f2ad97845ebe5655786d168dbd88da1971cf759`; `src/main/pages.js` is `4a800fa2d59f4d324875c068b83cba6439fb5cfc1fc28a057cdb4ee5c55245b1`. This is source inspection, not an observed installed-app interaction.

The trusted Start Page IPC handler runs in the requesting page's owning window runtime, including its local profile. Its group projection traverses that runtime's cluster order, counts members using `!tabs.get(id)?.private`, and excludes groups whose resulting count is zero. Assuming each listed tab ID resolves to its live record, this counts only non-private members; an unresolved ID also passes that JavaScript predicate, so lifecycle behavior is not proven by this source reading. The hook does not independently filter the requesting page's private flag. A private Start Page in a mixed shipping window can therefore receive group names, colors, IDs and non-private counts for that same window. Under the live-record invariant a group containing only private members is omitted. The shared `focusGroup` unfolds the group and activates its **first cluster member without a private filter**; in a mixed group that first member can be private. The projection does not itself reveal private member counts or URLs. Source paths that move tabs into groups do not universally reject private tabs; reachability and precise ordering need real shipping tests.

The isolated combined 158 candidate `e8cd2e37af0aeaf73f55d2afeee5afc10344fbb170dd444d68238aadcd67a76e` has a different window/profile structure. Its Start Page handler denies group reads and focus for every off-the-record profile before resolving the owning browser. Its regular handler reads and activates only groups in the owning Chromium window. The adapter does not poll groups for a private page. Existing `private3` checks support the narrow empty-projection/denial behavior for an isolated private window, not shipping mixed-window parity. Neither prior groups evidence nor source inspection qualifies the unbuilt combined bytes.

## Why a small cross-window lookup is unsafe

The shipping scope is a specific logical window containing tabs from normal and private sessions. A Chromium off-the-record browser window has a separate tab strip and is not shown by this candidate to carry a trusted association to the regular window whose groups a private page should see. Selecting the last active regular window, enumerating same-profile windows, falling back to the original profile, or accepting a renderer-supplied window/group ID can disclose names and membership from a different window and make an action target the wrong one. Even a trusted cross-window association does not reproduce shipping's mixed ordering or first-private-member activation when members occupy separate native tab strips. Removing the off-the-record guard or simply querying an original profile is therefore not a supported fix.

## Required design before implementation

Compare a single logical-window owner that explicitly owns normal and primary-private contents with a paired-window adaptation; the latter is only an approximation unless its presentation and interaction match the shipping window. Any implementation must:

- Bind the requesting exact primary frame and live page to a browser-owned, unambiguous logical-window capability. No global recency fallback, arbitrary cross-profile enumeration, renderer-supplied owner selection or access for guests/other off-the-record contexts.
- Project only that logical window's groups, preserving shipping cluster order and regular-member count. A private-only group is omitted; metadata from private-only groups and private counts must not leak. Re-resolve IDs against the same live owner and invalidate outstanding reads on navigation, close, reparenting or owner destruction.
- Define and validate ordering and action semantics for mixed groups, including the case where the first cluster member is private. A focus action must not silently activate a member from another logical window, and it must revalidate ownership, visibility and lifetime across synchronous observers. Whether foreground activation can safely cross native window boundaries needs direct investigation.
- Keep private group data ephemeral, avoid private URLs, titles and membership in durable state or logs, and enforce equivalent regular-profile and private-profile boundaries. Owner destruction or ambiguity fails closed. Explicitly handle multiple profiles, several regular/private windows, opener closure, private-only windows, reparenting and guest profiles.

Before implementing, inspect Chromium's actual browser/tab-strip ownership and private-window creation paths, and obtain real shipping observations for private-only, mixed and two-window behavior. Then exercise fresh isolated profiles for regular/private requests, mixed first-member ordering, unrelated same-profile windows, cross-profile/guest denial, close/reparent/navigation races, foreground/background authority and no private persistence. UI keyboard, VoiceOver and visual checks remain separate. Do not reuse the existing regular or private3 passes as evidence for changed source.

No safe source patch is proposed by this inspection: the required mixed-owner model and corresponding trust/lifecycle contracts do not yet exist in the candidate. This is an open shipping parity gap, not an owner-approved waiver.
