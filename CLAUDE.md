# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Blanc — a minimal Electron browser shell: custom-drawn "Island" chrome (a single floating command pill replacing the traditional tab strip + toolbar, per the Bowser Design System's Island Chrome handoff) with ad/tracker blocking wired in at the network layer, independent of Chrome's extension store and Manifest V3's `declarativeNetRequest` limits. Plus favorites, history, downloads, settings, slash commands, a Quick Switcher, private tabs, an explicit permission policy, and packaging config.

The app was renamed from "Bowser" to Blanc in July 2026 — its former name was inseparable from Nintendo's Mario villain, which didn't fit a serious indie browser's ambitions. `build.appId` in `package.json` deliberately stayed `me.bnfy.bowser` through the rename (only `name`/`productName` changed) to preserve macOS Gatekeeper/notarization identity and the auto-update chain for existing installs — don't "clean up" that mismatch, it's intentional. The design system's project name ("Bowser Design System", referenced throughout this file) is a separate Claude Design project the user maintains and wasn't renamed alongside the app; leave those references as-is.

## Commands

```
npm install
npm start                       # run in dev (electron .)
npm run dist                    # installable build: macOS dmg/zip, Windows NSIS, Linux AppImage
npm run dist:dir                # quick unpacked build in dist/, no installer
npm run release                 # scripts/release.sh: clean, build, sign, publish to GitHub Releases
```

After a release, `npm run site:deploy` is the production Cloudflare Pages
command. It deliberately includes `--branch=main` because the required clean
release checkout is detached at `origin/main`; without that flag Wrangler
creates a `HEAD` preview and leaves the live site (`blanc.day`) unchanged. A successful
post-release deployment is not complete until `wrangler pages deployment list
--project-name=blancbrowser` shows the expected source SHA as `Production` on
branch `main` and the canonical changelog shows the new version. Since the
October 2026 homepage redesign, `site:deploy` also refuses a build without the
licensed Blubird fonts, which are never committed (the repository is public and
the licence forbids redistribution): a fresh or isolated checkout must first run
`npm run site:fonts -- /path/to/Blubird.zip`. See `site/CLAUDE.md`.

`npm run lint` runs ESLint correctness checks on first-party desktop and Worker JavaScript (the `substrate` CI job runs it, and warnings fail; reviewed exceptions are in `docs/badge-lint-gate.md`). There is no plain `npm test` — the real commands are `npm run test:unit` (node --test over `test/unit/`), `npm run test:acceptance:dry` / `test:acceptance:desktop` (Cucumber scenarios in `spec/acceptance/`, the latter launching the app via Playwright), `npm run test:oauth:desktop`, and `npm run substrate:check` (tokens/settings/copy/adblock generated files match their sources). **CI skips the Electron jobs on website-only PRs.** In `.github/workflows/parity-guards.yml`, a `changes` job lets `oauth-compatibility`, `modified-link-clicks`, `tab-handoff`, `workspace-regressions`, `favorites-import`, `quiet-tabs` and `browser-shortcuts` skip when every changed path is under `site/`, `test/site/` or `docs/`, or is a root `*.md` other than `THIRD-PARTY-NOTICES.md`/`ASSET-LICENSE.md` (both packaged into `app.asar`). The gate is a job-level `if:` rather than a workflow `paths` filter, so the required `oauth-compatibility` check still reports (as skipped) instead of blocking the PR. It fails closed: if `changes` fails, the jobs run. `substrate`, `acceptance-wiring`, the Windows/macOS `unit` jobs and CodeQL always run, because unit tests also guard the website claims ledgers. A new parity-guards job must be classified in `test/unit/ci-website-only-gate.test.js`, and on a website-only PR the skipped jobs appear under their bare names next to a passing `changes`.

UI text on the internal pages and in the Island/overlay chrome, including the Billboard clock, is Instrument Sans (SIL OFL 1.1, committed in `src/renderer/pages/` with its license) at width 98 and +0.01em; counts and key caps stay Inter. The app ships no commercially licensed font. Blubird (Rajesh Rajput) is a website/wordmark face only: never add its files to the app or commit them (`.gitignore` blocks `Blubird*.zip` and `src/renderer/pages/Blubird*`).

`npm run release` bumps nothing itself — bump `version` in `package.json` (and consider the `electron` devDependency, since Chromium can't be swapped out of a running app) *before* running it. It shells out to `scripts/release.sh`, which authenticates via the `gh` CLI's own cached session (no `GH_TOKEN` needed locally), builds unpublished, then uses `gh release create` directly instead of electron-builder's own GitHub publisher — that publisher races its per-artifact upload tasks against each other on first publish for a tag and can leave a release missing `latest-mac.yml` or a blockmap; creating the release once with the complete macOS asset set avoids that. **Released versions are immutable:** the script checks local/remote tags and GitHub releases before building and fails if the version already exists; always bump to a new version, never overwrite assets. It also refuses dirty desktop release sources and wipes `dist/` before building so artifacts correspond to committed code and stale files never linger.

**Notarization:** the build step is wrapped in `op run --env-file=.env.1password --no-masking -- ...`, pulling `APPLE_ID`/`APPLE_APP_SPECIFIC_PASSWORD` from the 1Password item **"Apple Notarization"** (vault Dev, `username`/`password` fields) plus a literal `APPLE_TEAM_ID` — electron-builder's `@electron/notarize` integration auto-detects those three env vars. The hardened runtime keeps only Electron's required JIT/unsigned-executable-memory allowances; library validation stays enforced everywhere except `Blanc Helper (Plugin).app`, whose sole exception loads 1Password's separately signed native bridge (see the password-manager section). `release.sh` requires `op` and fails closed if notarization cannot run — a public release never falls back to an unnotarized build. A signed-but-unnotarized build gets quarantined and blocked by Gatekeeper the moment it is downloaded.

**Release-operator protocol (mandatory):** `release.sh` supports native Terminal (`BLANC_RELEASE_OPERATOR=terminal`) and an explicitly approved out-of-sandbox agent PTY (`BLANC_RELEASE_OPERATOR=agent`). During v1.5.1 the Codex safety layer rejected agent mode even after approval. Do not retry that dead end: after one rejection, explain it once, obtain approval for native Terminal, and launch the complete terminal-mode command there automatically so the user need not type or copy it. Keep it foreground, visible, and interactive. The script itself runs the exact fail-fast command `OP_BIOMETRIC_UNLOCK_ENABLED=true op signin` before build work and later uses forced desktop integration for `op run`; do not invent another sign-in flow, and cancel if `op` offers to add an account manually. A sandboxed `gh auth status` can falsely report an invalid token because it cannot reach the macOS keyring: retry outside the sandbox and use the connected GitHub app or working Git credential before asking the user to reauthenticate; do not send the user through `gh auth login` unless every existing path actually fails. Read `docs/release-verification.md` immediately before every release. Complete the fresh Safari Sigstore page immediately. During notarization inspect process names only, never full arguments, because `notarytool` includes the app-specific password in argv. Never rerun an immutable release after its tag or draft exists. The v1.5.1 lessons are recorded in `docs/release-incidents/2026-08-17-v1.5.1.md`.

**What's New page before every feature release (mandatory after v1.39.0):** a feature release's (X.Y.0) What's New page must be live on blanc.day before `npm run release` starts, because Blanc asks for it once per launch after the update and people update within a minute of publication (v1.39.0's first launches came before its page deployed). After the prep PR merges, draft it with `npm run site:whats-new -- --release X.Y` (it reads the prepared `docs/press/release-notes/vX.Y.0.md` while the release isn't public, turns its bold-named Added bullets into highlights with TODO media and never overwrites a page), take its captures from the merged build, and get the owner's explicit sign-off on its final text and media; or, with the owner's approval, add a `noPage` entry in `site/src/data/whats-new.json`. Merge it in a website-only PR and run `npm run site:deploy`. Until the release appears in `releases.json` the page builds as the one *upcoming* page: no date, `noindex`, left out of the sitemap and of the `/whats-new` redirect. `release.sh` runs `scripts/check-whats-new-page.mjs` before building and again before Sigstore, and refuses a feature release whose `https://blanc.day/whats-new/X.Y` doesn't answer 200 to a redirect-free HEAD (bug-fix releases and pre-releases skip it).

**Release completion and takeover protocol (mandatory after v1.15.0):** Publishing the GitHub release is not the end of the release. Keep `scripts/release.sh` as the single owner of the signed macOS build, immutable tag and draft, native workflow dispatch, complete-manifest generation, fresh Safari Sigstore authorization, publication, logged-out asset checks, and changelog refresh; do not manually duplicate or race those stages. If taking over a live release from another agent, first reconcile the foreground Terminal process, tag SHA, GitHub release state and assets, and the exact native run. If the release is already public and `SHA256SUMS.sigstore.json` exists, the Sigstore authorization already succeeded—do not open another approval or rerun the release. Continue with independent post-publication evidence from a fresh temporary download: run the complete manifest validator, `shasum -a 256 -c SHA256SUMS`, and `cosign verify-blob` against the pinned identity and issuer. For macOS, mount the published DMG read-only, assess the contained `Blanc.app` with Gatekeeper, run strict deep `codesign` verification, confirm the expected Developer ID, and validate the ticket stapled to the app; the documented gate does not require a separate ticket on the DMG container. Then dispatch `.github/workflows/prerelease-smoke.yml` against the exact release tag with `release_version` set and wait for the hosted public-DMG checks (Apple Silicon and Intel, each on its native runner), public AppImage launch, and Linux and Windows DNS jobs to pass. The hosted macOS jobs independently check each published DMG's manifest digest, strict-deep signature, pinned Developer ID certificate, stapled ticket, architecture and native launch; every release ships both Apple Silicon (the default Mac build) and Intel, and `release.sh` refuses one architecture unless `BLANC_MAC_ARCH_WAIVER` records why. These hosted checks complement rather than replace the local Gatekeeper assessment. Only then update the public baselines, dated release incident, `site/src/data/releases.json`, the next release's default `MIGRATION_BASE_VERSION` and its unit-test assertion, the Feature Roadmap (`site/src/data/roadmap.json`: take shipped items off and bump `updated`, which its test requires), and the Bangs page's pin (`npm run site:bangs -- --ref vX.Y.Z --release vX.Y.Z`, whose data test requires the newest tag in `releases.json`) from a clean isolated worktree; run the changelog check and full site/SEO build, commit, and push. Deploy with `npm run site:deploy`, verify Cloudflare reports that exact commit as `Production` on branch `main`, verify the canonical homepage and changelog, append that deployment evidence to the incident, and push the follow-up record. Leave adjacent macOS and Windows updater handoffs explicitly pending until each begins inside the immediately preceding public Blanc, discovers the public metadata, downloads the update, and invokes **Restart Now**; a direct installer launch is never a substitute.

**Provisioning profile (Touch ID passkeys):** the mac build embeds `build/embedded.provisionprofile` (wired via `build.mac.provisioningProfile`) because the WebAuthn `keychain-access-groups` entitlement is *restricted* — even for the app's own `TeamID.BundleID` group, AMFI SIGKILLs an app carrying it without a profile that authorizes it, and helpers can't carry a profile at all (so the inherit entitlements must never list the group). The profile is only honored when it embeds the **exact certificate** the build is signed with; the Apple account has several identically-named Developer ID Application certs, so the signer is made deterministic and verified twice. `build.mac.identity` pins the signing certificate **by SHA-1 fingerprint** (electron-builder substring-matches the qualifier against `security find-identity` lines, so a fingerprint selects exactly one identity — update the pin when the cert rotates). `scripts/preflight-mac-signing.mjs` (npm `predist`/`predist:dir` + `release.sh`) then fails the build early unless *every* certificate electron-builder could select — the pinned identity, a `CSC_LINK` p12 (parsed and validated, never skipped), or unpinned Developer ID identities — is embedded in the profile, and unless the profile is an unexpired, all-devices (`ProvisionsAllDevices`, never `ProvisionedDevices`), `Platform: OSX` Developer ID profile — a device-listed development-type profile would launch only on registered Macs, bricking every other install through auto-update, while end-user devices need nothing installed for the correct profile type (it ships inside the bundle). Finally `scripts/after-sign-verify.js` (`build.afterSign`) checks ground truth on every packaged app: the certificate that *actually* signed `Blanc.app` must be in the bundle's embedded profile (itself byte-identical to the repo's) with the WebAuthn entitlement present, throwing before any dmg/zip exists. Regenerate the profile on the developer portal whenever the signing cert rotates — and note every current Developer ID cert expires 2027-02-01 (G1 CA cap), so cert *and* profile rotation land together before then. `test/unit/webauthn-packaging.test.js` guards the static wiring cross-platform.

**Windows & Linux:** `release.sh` builds macOS locally, then dispatches `.github/workflows/release-windows-linux.yml` and watches it to completion. Native artifacts stay on an unpublished draft until every platform succeeds. Windows signing is fail-closed: complete Azure Trusted Signing configuration is tried first, a complete `CSC_LINK`/`CSC_KEY_PASSWORD` pair is the Authenticode fallback, and missing or partial signing configuration fails the job. The installer and unpacked app must have a valid timestamped signature whose exact subject equals `WINDOWS_EXPECTED_PUBLISHER`; `windows-signature.json` binds that observation to the installer SHA-256. Linux AppImages have no OS-level publisher signature, so the authenticated release manifest is their publisher check. The NSIS installer's `customInstall`/`customUnInstall` macros in `build/installer.nsh` register Blanc under Windows' Default Programs contract (`RegisteredApplications` → `Software\Clients\StartMenuInternet\Blanc\Capabilities` → the `BlancURL` ProgId) so Settings → Default apps lists it as a browser; Electron's `setAsDefaultProtocolClient` alone never gets it listed, and `isDefaultProtocolClient` on Windows merely reads back that same write, so on Windows the Make default button opens `ms-settings:defaultapps` and the status comes from the real HTTP and HTTPS `UserChoice` ProgIds via `src/main/windows-default-browser.js`. The installer deliberately claims no `.htm`/`.html` file associations because `webUrlsFromArgv` accepts only HTTP(S) URLs. The Linux desktop entry advertises `Network` and `WebBrowser` plus the HTTP(S) scheme-handler types electron-builder derives from `build.protocols`; it likewise claims no local HTML MIME types. `test/unit/default-browser-packaging.test.js` guards the source configuration, and the native Linux workflow verifies the generated AppImage desktop entry.

Before a Windows hotfix is released, agents can build a private, signed installer from the candidate branch with `gh workflow run release-windows-linux.yml --ref <candidate-branch> -f mode=validation -f platform=windows`. Validation mode checks the normal signature, timestamp, fuses, and files and uploads the installer, blockmap, signature record, and `latest.yml` only as a three-day Actions artifact. Installing that EXE proves packaged behavior, but launching it directly while Blanc is open does **not** prove the `electron-updater` handoff. That claim requires Blanc itself to discover the staged metadata, download the exact candidate, and invoke **Restart Now**. Obtain explicit affected-machine confirmation before merge/tag/release. If the owner waives a gate, state the missing evidence and risk, obtain written approval, and record the waiver rather than claiming the check passed. Normal releases dispatch with `mode=release`.

The Azure branch requires every tenant/client/account/endpoint/profile/publisher value before it is attempted; partial Azure configuration may use the complete CSC fallback but may never reach unsigned output. AppImages for the runner's default architecture have no `-x86_64` suffix and carry their block map internally. The release gate verifies Electron fuses in every packaged executable, emits a CycloneDX SBOM and `SHA256SUMS`, signs the checksum manifest with Sigstore, and requires exact OIDC identity/issuer verification before publishing. GitHub Actions are commit-SHA pinned; native artifacts receive GitHub provenance attestations.

The desktop ad blocker compiles only the bundled, hash-verified EasyList + EasyPrivacy snapshots in `adblock/sources/`; it makes no live filter-list request at startup and strips remote scriptlet resources. The compiled engine is cached in userData as `adblock-engine.v<N>.bin`; delete it to force a rebuild from the same bundled snapshot. Updating the lists is a reviewed release input: update `pinned.json`, run `npm run adblock:build`, and commit the generated snapshot/hash changes together.

The pinned blocker files are byte-verified, so `.gitattributes` must keep `adblock/sources/*.txt`, `adblock/sources/pinned.json`, and `adblock/generated/*.json` at `eol=lf`. Without that, a Windows checkout converts them to CRLF and every packaged launch correctly fails closed with **Blocking could not start**. The native Windows workflow must run `npm run adblock:check` before electron-builder; never remove or bypass that gate. Every electron-builder package also runs `scripts/verify-packaged-adblock.js` from the cross-platform `afterPack` hook, comparing the actual `app.asar` payload byte-for-byte with the verified release inputs before signing. Release workflows repeat that packaged-payload check explicitly for macOS, Windows, and Linux.

Auto-update (`electron-updater` against GitHub Releases) only runs in packaged builds — `npm start` skips it entirely. Releasing means bumping the `electron` devDependency (it tracks Chromium stable) and `version` in `package.json`, since Chromium itself can't be swapped out of a running app.

## Architecture

**Many `BrowserWindow`s, each with many `WebContentsView`s.** The window's own `webContents` renders `src/renderer/index.html`/`styles.css` through the exact-allowlist `blanc-chrome://` scheme — the chrome **strip**: a slim (68px) band holding the resting island pill (back/forward, the active group's tab dots with a capped overflow, favicon, domain, the Blanc Blocker count, private chip, and a trailing reload/favorite/close-tab/downloads action cluster) and window controls. Permission prompts render in their own small transparent `WebContentsView` (`permission.html`/`permission.js`, the third `blanc-chrome://` document), attached bottom-center over the page only while prompts are pending — the strip only paints the top band, and anything beside the island competes with it. The whole resting pill is scaled up in one place with `zoom` on `#islandPill` (kept in lockstep with the `--strip-h` geometry token); each anonymous tab dot blooms into a disc showing that tab's favicon on hover/focus (`.dot-peek`, reusing the pill's favicon rendering) so you can tell which tab you're switching to before you click. Each tab is a separate `WebContentsView` added as a child of the window's `contentView` at `y = chromeHeight`; on macOS and Windows ordinary inactive tab views are hidden and detached, so switching tabs is remove-one/add-another rather than destroying anything. On Linux, Electron 44 stops drawing a tab view that is removed from its window and added back, so `src/main/tab-view-lifecycle.js` keeps inactive tab views hidden but window-owned; a view arriving from another window (Move Tab to New Window, a space opened elsewhere) draws again only after another child is added to that window, so the module adds a fresh 1×1 transparent `View` beneath it and removes it a tick later. Attach and detach tab views only through that module. The Playwright acceptance suite cannot see this class of bug (Playwright's focus emulation keeps every page drawing), so `npm run test:tab-view-drawing:desktop` launches Electron directly and runs in the quiet-tabs CI job (Linux under xvfb, and Windows). Managed uBO tool views on Windows/Linux stay hidden but attached through background reloads to preserve their native Aura focus root, and are removed after native destruction; Quiet Tabs and closed-tab expiry still control their renderer lifetime — but an *idle background* tab is a separate matter, and its renderer is deliberately discarded (see **Quiet Tabs** below). `src/main/main.js` owns all of this: the `tabs` Map + `tabOrder` array are the single source of truth, and both chrome renderers only ever reflect `tabs:updated` broadcasts.

**Quiet Tabs.** An idle background tab's renderer is deliberately discarded to reclaim its memory (~148 MB/tab measured on Electron 43), and rebuilt when the tab is activated again. Policy is pure and unit-tested in `src/main/tab-sleep.js` (`sleepCandidates`, `trimSnapshot`, `TAB_SLEEP_DELAY_MS`) — no `require('electron')` in that file. View construction and the whole per-tab listener set live in `src/main/tab-view.js` (`createTabView`, `wireTabView`, `initTabView`), which is also the single home of the private-session choice. `main.js` owns `sleepTab`/`wakeTab`, the 30 s sweep, and the wake generation (`tab.wakeGeneration`) that suppresses history and failure handling across every hop of a redirect chain. **`liveContents(tab)` is the only correct liveness check**: after `webContents.close()`, `view.webContents` can read back `undefined`. The main-process-only `sleepSnapshots` Map retains bounded navigation recovery data and must never move onto the tab record or cross IPC, disk persistence, sync, or crash reporting; snapshots may contain page state and POST bodies. During app shutdown, `closeTab` must never select and wake a surviving quiet tab while Electron tears down the native window. The dirty probe protects changed form controls across the frame tree and Chromium's unload objection. It deliberately does **not** treat non-empty `sessionStorage` as user work, because ordinary sites create site-owned keys on load and that blanket rule makes the feature inoperative. Instead, a storage-bearing tab keeps its WebContentsView in the snapshot Map, discards only its provably-exclusive renderer, and reloads that same WebContents so Chromium's browser-process sessionStorage namespace survives; any beforeunload listener or shared/uncertain renderer PID leaves it awake. `session.json` has an optional `meta: [{title, favicon}]` array parallel to `urls`, written into each v2 `windows[]` entry, never the five-key flat rollback mirror; `version` is `2`. Restored tabs are born quiet and only the selected tab loads. Internals say `asleep`/`tabSleep`/`sleepSnapshots`; every user-visible and assistive string says **quiet**, except the fixed `/sleep` command. The device-local delay is Settings → General → Quiet inactive tabs (`off|30m|1h|6h`, default `1h`, deliberately outside `SYNCED_KEYS`); Off stops future quieting and never wakes an existing quiet tab or drops its snapshot.

**Reopen Closed Tab.** Closing a tab records a per-window closed entry with three internal restore tiers: for ~30 s the closed tab's live `WebContentsView` is parked (same view re-attached on ⌘⇧T, no re-fetch, JS and POST state intact), then it degrades to a `trimSnapshot()` restore (back stack, scroll, group, pin, slot), with URL-only as the floor. Never expose tier jargon such as **held** in user-visible copy. Pure policy lives in `src/main/closed-tabs.js` (`holdEligibility`, `sanitizeSnapshot`, `buildTabEntry`/`buildGroupEntry`, `expireHolds`, `expireEntries`, `projectEntries` — no `require('electron')`); `main.js` owns parking (`parkTabView`), the held-state firewall (a parked page keeps executing, so it gets deny-all `setWindowOpenHandler`, main-frame navigation refusal, crash/destroy downgrade observers, and blanket permission denial via `heldWebContents` + `setHeldRequesterCheck` in permissions.js), restore (`reopenEntry`, the `adoptView` seam in `createTab`), and disposal. One entry per user action: `closeGroup` captures first and records a single group entry restored whole at its cluster index. Closed entries are the same class of secret as `sleepSnapshots` — snapshots and view refs never cross IPC/disk/sync; renderers see only `{id,title,favicon,tabCount}`. The ⌘L panel shows them in a Recently closed band styled like a group and placed among the groups; its place is a per-window `closedSlot` (the number of top-level items above it: groups and ungrouped tabs) that `src/main/closed-slot.js` keeps through every change and that persists in session.json and Spaces as `closedIndex`, with `closedSlot` kept as the rollback copy counting groups only. The band offers per-entry Forget and Clear all; either must immediately destroy a parked view. Entries also expire after one hour and remain capped at 25. Capture-anchored, prompt-pending, loading, quiet, and opener-family tabs are never held (Tier 1); private tabs are never recorded at all. Nothing is persisted, and on macOS dock-close the held view is destroyed while snapshot entries survive until their normal expiry.

reclaim, permission prompts) lives on a window-runtime record
(`src/main/window-runtime-registry.js`) — one per native browser window — resolved

**Local profiles.** `profiles.json` defines the permanent Personal identity plus bounded named profiles. Personal keeps every shipped root JSON file and Electron's default session, so upgrades move no existing data. Named profiles store Favorites, history, download metadata, and remembered permissions under `profiles/<opaque-id>/`; their normal tabs use `persist:blanc-profile-<id>` and private tabs use `private-browsing-<id>`. Settings, Supporter, telemetry, and network/presentation preferences remain device-level. Profile Sync and remote-tab presentation are Personal-only. Deletion is exact-name-confirmed and crash-resumable through the device-level `profile-deletions.json` marker; it closes the profile's windows, clears its Electron sessions, drops cached store/download state before removing its directory, and removes every saved workspace. Downloaded files remain on disk.

**The island's expanded states live in a separate always-on-top overlay `WebContentsView`** (`src/renderer/overlay.html`/`overlay.js`, transparent via `setBackgroundColor('#00000000')`), attached to the window's `contentView` only while something is showing, so panels float *over* the web content instead of growing the strip and shifting it down. Main owns the mode (`overlayMode`): `'panel'` — the command bar expanded in place at the pill's anchor; `'palette'` — the same panel summoned by ⌘L, on the same anchor as `'panel'` but over a scrim (it used to sit 120px lower, which read as a detached window rather than the pill opening); `'find'` — the find capsule, whose overlay bounds are kept *tight* around the capsule so the rest of the page stays clickable; `'shield'` — the site-protection popover opened from the pill's shield chip (fixed `calculateShieldBounds` region below the strip, right-aligned to the chip; site-scoped toggle reusing the /allow-ads//block-ads command paths; dismissed like panel/palette plus on tab switch and site-changing navigation — the toggle's own reload is same-site and keeps it open); `'spaces'` — the Spaces menu alone, opened from the Island's space mark (the pill's leading chip showing the current space's symbol and name; `calculateSpacesBounds` sizes the view around the 300px menu with room for its shadow and opening scale, hanging it just below the Island so it never covers it; dismissed like the shield popover, focus returning to the mark). From the ⌘L panel the same menu hangs below the Island from the footer's icon-only Spaces button. `showOverlay`/`hideOverlay` in main are the only mutators; the overlay renderer just applies `overlay:show`/`overlay:hide`. Guards that matter: a tab view attached while the overlay is open must be re-stacked below it (re-`addChildView(overlayView)` in `setActiveTab`), Escape dismisses via main's `before-input-event`, and overlay `blur` dismisses panel/palette (not find) — but is ignored while a blank-tab focus reclaim is pending, or the reclaim dance re-opens/closes in a loop. The panel's list area shows the tab switcher at rest, slash commands when the input starts with `/`, and the Quick Switcher (loose substring/in-order matching across open tabs, favorites, history) while typing anything else.

**Private tabs** (`/private`, ⌘⇧N, `private` on main's tab model): never recorded to history, excluded from session persistence, sync, and reopen-closed-tab, inherited by `window.open`/context-menu children, and opened to `blanc://newtab/?private=1`. Their views share the non-persistent `private-browsing` session, isolated from the normal profile; its cookies, storage, cache, service workers, HTTP auth, and permission decisions disappear when Blanc quits. Completed private-download metadata is kept only in memory, while the file the user saved remains on disk. The same permission, blocker, compatibility, and WebAuthn policies are installed on both sessions. While the active tab is private, the chrome uses its private theme and quick-exit chip.

**Tab groups** (per the Island Tab Groups exploration in the Bowser Design System): main owns `groups` (`{id, name, collapsed, color}`) alongside `tabs`; the window's `tabOrder` is the display order (spec `docs/superpowers/specs/2026-10-17-ungrouped-tab-placement-design.md`): each group's tabs are contiguous, ungrouped tabs may sit above, between or below groups as runs, and `groups` is kept in the same order. The shared pure `src/renderer/tab-sections.js` (main, strip and overlay) turns the order into sections, and `syncTabLayout` in main normalizes `tabOrder`, `groups` and the Recently closed slot before every payload and capture. A new group appears where its tab was; Remove from Group lands the tab directly below its group; saved windows and Spaces carry `sectionOrder: true`, and an entry without it is laid out as older builds drew it (groups, then ungrouped tabs); each tab carries `groupId` (or null). Groups have **names, not colors**, kept in the case typed and matched without regard to case (`/group research` finds "Research"; two groups can't differ only by case; `src/main/group-name-case.js`). Names saved lowercase before that change got a capital first letter once (settings `groupNamesRecasedVersion`, a `groupNamesRecased` stamp in workspaces.json). A group may carry an optional color, one of the eight Spaces presets (`SpaceIdentity.PRESETS`) or `null`, off by default (spec `docs/superpowers/specs/2026-10-17-tab-group-colors-design.md`, which reversed the earlier "groups have names, not colors" rule). `src/main/group-color.js` validates it and `groupRecord()` copies every group through restore, Spaces and Recently closed. Renderers paint it with `TabSections.paintGroup()`: the block takes a wash, a dot sits before the name, and the Island's dots take the color. Right-clicking a group header or pressing its ⋮ opens the **group menu**: a name field (a duplicate name is refused), the color row, **New Tab in Group**, **Move Group to New Window**, **Ungroup** and **Close Group**. It floats inside the overlay in the ⌘L panel; from the side list main opens the `'group-menu'` overlay mode beside the header. The website still says groups have no colors until a release ships them. A group exists only while it holds tabs (`pruneEmptyGroups`); creation happens through `/group <name>` (find-or-create) or the tab context menu's **Move to Group ▸ → New Group…**, which opens the ⌘L panel prefilled with `/group ` and binds that one run of the command to the right-clicked tab (`overlay:begin-group` → `pendingGroupTabId` in overlay.js — cleared on use, dismissal, or editing the input away from `/group`). Membership moves via the same submenu (existing groups as radio items, **Remove from Group**), `/ungroup`, or `/close-group`. There is deliberately no inline per-row group chip/picker any more — it crowded rows into truncation; grouping lives in the right-click menu (`tab-context-menu-model.js` / `tab-context-menu.js`, shared by the resting pill and the ⌘L tab rows). The pill now renders **only the active tab's group** (or, for an ungrouped tab, its run) as dots (capped at 8, with a quiet `+N` that opens the panel). It does **not** name the group — group identity lives in the ⌘L panel (group headers) and in which tabs the dots represent. Pinning is group-local: a grouped pin stays in that group and leads its rows/dots, while only ungrouped pins use the standalone pinned section in the ⌘L panel. Other groups also live in that panel behind per-group headers (click folds/unfolds; collapsed groups show an "N tabs tucked away" row). The Quick Switcher matches group names (ranked above tabs; picking one focuses the group), and ⌘1–9 change meaning when groups exist: nth *cluster* (group's first tab, unfolding it) instead of nth tab. A plain new tab (⌘T, panel row, `/new`) always launches ungrouped, regardless of the active tab's group — join a group afterward via the row's right-click menu. Link children (`window.open`/`target=_blank`, the context menu's Open Link in New Tab and Open Link in Glance) open ungrouped the same way, at the end of the tab order with the other ungrouped tabs; they inherit the opener's privacy and opener relationship but never its group (the owner reversed the earlier inherit-the-group rule in October 2026, so don't restore it). New private tabs are never grouped. `session.json` persists `groups` plus a `groupIds` array parallel to `urls`; groups referenced only by private tabs stay out of the file.

**The chrome documents only load their HTML/CSS once, at window creation** (`rt().window.loadURL(CHROME_INDEX_URL)` + `createOverlay()` in `createMainWindow()`). Editing `src/renderer/index.html`, `overlay.html`, `styles.css`, or either chrome renderer requires relaunching the app to see the change — `Cmd/Ctrl+R` reloads the *active tab's* `WebContentsView` (which re-fetches `blanc://.../pages.css` fresh on every navigation), not the chrome. Don't rely on a plain reload to verify a chrome-level change; restart `npm start`.

**`blanc://` internal pages** (`newtab`, `bookmarks`, `history`, `downloads`, `settings`) are served by `src/main/pages.js` over a privileged custom scheme instead of `file://`, so they get a real origin and ordinary web content can never link into local files. The handler resolves every request through `path.basename()` before joining it to `PAGES_DIR` (`src/renderer/pages/`) — **it can only serve flat files directly in that one directory, no subdirectories and no `../` traversal.** Any asset (`pages.css`, `icon.svg`, a font file) that `pages/*.html` needs must live flush inside `src/renderer/pages/`. The five utility pages (`bookmarks`, `history`, `downloads`, `settings`, `shortcuts`) **never open as tabs** — main routes them (via `src/main/utility-pages.js`'s `isUtilityUrl`, the single classifier checked at `openInternalPage`, tab `will-navigate`, `createTab`, the window-open handler, and typed navigation) into the **utility sheet**: a transparent always-below-the-island `WebContentsView` whose page draws its own scrim + card (`body.sheet` in pages.css + the shared `sheet.js`). Esc, scrim click, and the nav ✕ (strictly-guarded `pages:surface:close`) dismiss; tab switches/creation and summoning ⌘L dismiss; outbound clicks open real tabs; session restore filters stale utility tabs through `session-restore.js`'s zipped filter. `blanc://mahjong` (mahjong solitaire) is a KNOWN page served flat like the others but deliberately NOT a utility page — each of the four start-page footers opens it as an ordinary managed tab. Its engine/page split is `mahjong-engine.js` (pure, unit-tested) + `mahjong.js` (DOM, timer, localStorage best). The newtab page offers four layouts (Ledger, Billboard, Shelf, Tally — `newtabLayout`) inside one shared frame: an in-flow header (Sunrise mark + date), one centered content area, and a fixed footer (left: Ledger's weekly blocked count, version, the moving-in checklist as a "Finish setup" pill whose popover holds the list and whose × hides it for good, and an "Upgrade to Blanc Patron" pill whose × hides it for 90 days via device-local `patronCalloutDismissedAt`; centre: a **Customize** popover holding the layout picker and dynamic wallpaper; right: Mahjong, ⌘L hint). Ledger is a centered spread under one "Where to?" line: favorites left; tab groups ("Pick up where you left off" — clicking one focuses that group) and other devices right. Design: `docs/superpowers/specs/2026-10-05-start-page-layouts-polish-design.md`. There's deliberately no mascot on this page — an earlier version had an animated pixel-art dog sprite here, retired along with the "Bowser" name as part of the July 2026 rebrand; don't reintroduce one without being asked. Live group state and the blocked counter cross from main.js via the `startPage` hooks passed to `setupPages` (`pages:start:data` / `pages:start:focus-group`).

**Mahjong sound cues.** `mahjong-sound.js` synthesizes the game's quiet Web Audio cues locally and lazily after a user gesture; do not replace it with remote or bundled media without a CSP/privacy review. `mahjong.js` owns the accessible sound toggle and stores its device-local preference in the Mahjong origin's `localStorage`, which stays ephemeral in private tabs.

**Security posture:** the chrome window, the overlay view, and every tab's `WebContentsView` run `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`. Three separate preload scripts, deliberately asymmetric:
- `src/main/preload.js` — the rich `browserAPI` bridge (tab lifecycle, window controls, island data + command actions). Attached only to the chrome window and the overlay view.
- `src/main/tab-preload.js` — the minimal `bowserPages` bridge, exposed only when `window.location.protocol === 'blanc:'` (re-checked on every navigation, so a tab that leaves an internal page loses it). The main process still independently re-verifies `event.sender.getURL()` on every `pages:*` IPC call in `pages.js` — the client-side check is not trusted alone. `bowserPages` kept its internal-only name across the rebrand, same rule as the Favorites/`bookmarks` split below.
- `src/main/chrome-compat-preload.js` — an unprivileged session-wide `window.chrome.app`/`csi`/`loadTimes` compatibility shim. It is registered through `session.registerPreloadScript` so both ordinary tabs and Chromium-adopted OAuth children receive it without replacing the child's `webPreferences.preload` (which severs `window.opener`). It exposes no IPC or application data.

**IPC channel namespaces:** `tabs:*` (tab lifecycle, via `browserAPI`), `pages:*` (internal pages' guarded data API, via `bowserPages`), `window:*` (minimize/maximize/close), `chrome:*` (strip/overlay → main: layout height, open-island/open-find, and island data + command actions — history-list/favorites-list/history-clear/adblock-toggle/adblock-exempt-active/cycle-theme), `overlay:*` (main ↔ overlay show/hide/close), `fill:*` (main ↔ the 1Password fill-status capsule: fixed-kind show/hide plus request-id-echoed verb replies — never any credential, vault, or page-derived string).

**Address bar focus** is intentionally intricate (`tabsWantingAddressBarFocus`, `reclaimAddressBarFocus()` in `main.js`) because a blank new tab needs the island panel's address input focused rather than its empty page content, and `WebContentsView` focus can settle asynchronously after Electron's own focus/navigation callbacks — hence the reassert-on-next-tick pattern rather than a single focus call. `focusAddressBar()` now means "show the overlay panel and focus its input".

**Theming:** CSS custom properties in `:root` (+ a `prefers-color-scheme: dark` override, + an explicit `:root[data-theme="private"]` scope), with the same token names duplicated across `styles.css` (chrome strip *and* overlay — one shared stylesheet) and `src/renderer/pages/pages.css` (internal pages) — separate files by necessity given the flat-serving constraint above, kept in sync by hand, not shared/imported. `nativeTheme.themeSource` is driven by Settings → Appearance (also cycled by `/theme`), so system/light/dark propagates to chrome, internal pages, and web content together, no restart. Warm surfaces (utility sheets today; see `docs/brand-usage.md` → *Desktop Sunrise surfaces*) remap these semantic tokens to the themed `--sunrise-*` palette inside a scope class such as `body.sheet`, the same technique the Start Page's `.ledger-body` uses; the Island and its frame stay neutral.

**Interface language** (F44; `copy/messages/`, `src/main/i18n.js`, `src/renderer/pages/i18n.js`): every Blanc-authored string lives in `copy/messages/en.json` under a stable key; translations (`de`, `es`, `fr`, `pt-BR` and `it`, each selectable since it reached 100% coverage; a new language stays hidden until then) carry a per-entry source hash that only `npm run copy:ack -- <locale> <keys>` advances — `copy:build`/`copy:check` never do, so a stale translation cannot be cleared by building. A PR that changes English updates every language in the same PR. `copy:build` generates `src/renderer/pages/strings.<locale>.js` (never hand-edit), which every `blanc-chrome://` and `blanc://` document loads as `strings.js` (the handlers map that name to the active language and append the formatting locale) followed by `i18n.js`; main requires the same files. It also generates `src/main/ublock-strings.json` (only the `ublock.*` keys, every language): uBlock Origin's pages cannot load the catalog, so the uBO package adaptation ships that text beside a formatter-only `i18n.js` as hashed host inputs, and changing a `ublock.*` message needs `node scripts/build-ublock-adaptation.cjs --write`. Static HTML keeps its English inline with `data-i18n*` keys; JS calls `blancI18n.t(key, params)`; never `innerHTML` a message. `uiLanguage` (`system` or a code) is device-local, written only by `settings.setUiLanguage()` through `changeUiLanguage()` (never `pages:settings:set`), resolved once at `whenReady` and frozen, so a change applies after a relaunch; a stored unavailable language renders English. `Accept-Language`, search suggestions, Chromium's in-page widgets and spellcheck stay on the OS language; Blanc never passes `--lang`. `copy/i18n-scope.json` marks each string-bearing file `pending` or `guarded`; guarded files fail `copy:check` on hard-coded English, and `npm run test:i18n:desktop` (pseudo-locale `en-XA`) is the runtime check.

**CSP is declared per-file**, not centralized: `index.html`, `overlay.html`, and each `pages/*.html` file carries its own `<meta http-equiv="Content-Security-Policy">`. Chrome/internal-page fonts and assets are bundled locally; their CSPs do not allow remote images or fonts. Adding an external resource requires a narrow per-document policy change and a privacy/data-flow review.

**Ad blocking** (`src/main/adblock.js`): the `@ghostery/adblocker-electron` engine is installed in both regular and private sessions from the bundled verified snapshot. Request blocking, declarative cosmetic CSS, and bundled page-context scriptlets remain; `adblock-scriptlets.js` isolates each scriptlet's declarations to prevent cross-scriptlet helper corruption. Toggling in Settings updates both sessions; blocked-request counts are per-tab and coalesced before reaching chrome.

**Dark websites** (F42; `src/main/dark-websites*.js`, `dark-reader/`): off by default and device-local. While Blanc is dark, http(s) main frames are darkened from first paint by the pinned, unmodified Dark Reader API build (`dark-reader/upstream/`, hash-pinned in `dark-reader/pinned.json`, MIT). `dark-reader/build.mjs` generates `src/main/dark-websites-preload.js` from the two templates in `dark-reader/`; never hand-edit it, and run `npm run darkreader:build` after changing a template, the pin or the constants in `dark-websites.js` (`darkreader:check` runs in `substrate:check`). The session preload asks main synchronously whether to darken and runs the engine only when the answer is yes, in isolated world 1002 with its own CSP (the page's CSP would otherwise block its styles; world 999 is shared by every Blanc preload and must not get that exemption). That world's only capability is `dark-websites:fetch-css`, which main serves only after the tab's own blocker (Blanc Blocker or uBO) allows the stylesheet, from an in-memory session with no cookies, redirects or non-public addresses, `text/css` only, and size, time and rate limits (`dark-websites-fetch.js`). `/dark-site` and the shield popover's **Dark website** switch (`shieldPopover.darkSite`, from `siteState()` in the service) flip the current site; in private tabs that choice is memory-only and never written to settings. Iframes stay as drawn because session preloads reach only main frames. Updating Dark Reader is a reviewed release input, like the blocker lists.

**Capture indicator** (`src/main/capture-state.js`, `capture-preload.js`, `capture-mainworld.js`): a window-wide pill chip + popover showing live mic/camera use. The only off→on signal is the main-process permission grant (`setCaptureGrantObserver` in permissions.js); page-world instrumentation refines toward off via per-frame snapshots/settlements over `capture:report` — display state, not security truth (macOS's system indicator is the malicious-page backstop; a defeated patch fails stuck-on, never silently-off). Main-frame-only by spike-proven necessity (session preloads don't reach iframes without `nodeIntegrationInSubFrames`, which stays off — the main-world source therefore lives inline in `capture-preload.js`, and `capture-mainworld.js` re-exports the shipped bytes for the vm tests). Auxiliary `window.open` popups are capture surfaces in a process-wide registry that survives macOS window close/reopen. Capturing tabs are excluded from Quiet Tabs (`tab.capturing`, re-checked inside `sleepTab`'s final guard). Never persisted or synced; only the `tabs:updated` projection (`capture`, `captureChip`, `capturePopover`) leaves main. Capture IPC crosses unbound native boundaries, so its broadcasts rebind the window runtime (`scheduleCaptureBroadcast`) — same rule as downloads.js. Design: `docs/superpowers/specs/2026-08-13-capture-indicator-design.md`. The same preload also carries the **truthful `permissions.query` shim**: main-frame mic/camera queries answer `granted`/`denied`/`prompt` from Blanc's stored decisions over a sender-validated bridge (`capture:permission-query`), so preflighting sites ask instead of declaring the device blocked — display truth only; Electron's strict check/request handlers are untouched, and any bridge failure falls back to the strict query. Never map undecided to `true` in `setPermissionCheckHandler` (reviewed P0, reverted). Spec: `docs/superpowers/specs/2026-08-13-permissions-query-truthful-state.md`.

**Naming: "Favorites" vs. `bookmarks`.** The user-facing feature is called **Favorites** (heart icon) per the Bowser Design System — but every internal identifier deliberately stays `bookmarks` (`bookmarks.js`, `bookmarks.json`, `pages:bookmarks:*` IPC, the `blanc://bookmarks/` URL, `pages/bookmarks.html`). Change labels/copy only; don't rename the internals, and don't "fix" the mismatch in either direction.

**Persistence** is one `JsonStore` per feature (`src/main/store.js`): JSON in `userData`, loaded synchronously once and normally saved on a 250ms debounce. Routine debounced saves and space autosave write and flush off the main thread (`fs.promises`, a per-file sequence check before the atomic rename); explicit `flush()`/`updateAndFlush()` and quit-time saves stay synchronous. Both paths use an owner-only temporary file, flush to disk, and atomic replacement; legacy files are tightened to mode 0600 where supported. `settings.json`, `bookmarks.json`, `history.json` (capped at 5000), regular `downloads.json` (capped at 200), and `adblock-stats.json` remain local. Sync's retained derived key is stored only as an OS-credential-service-wrapped `protectedKey`; legacy plaintext keys migrate fail-closed. Because `userData` derives from `productName`, the permanent one-time Bowser→Blanc packaged-profile copy must remain so existing users keep their local data.

**Telemetry** (`src/main/telemetry.js`): bounded usage measurement, **on by default and opt-out** through the fresh-profile privacy choices or Settings. A fresh profile must save the presented choice before any event; existing profiles retain their saved setting and are not re-asked. Packaged builds only; fire-and-forget. Every event carries `{installId, sessionId, version, platform, arch, osVersion}` with OS version coarsened to a major. The launch uses `/ping`; `/event` accepts `mahjong_play` after the first real free-tile move and `newtab_layout` with one of the four fixed layout ids (the Worker also still accepts the historic `mahjong` layout from pre-1.20 builds), each at most once per app session. The Worker also accepts the first-day retention signals `day1_default`/`day1_browsed` (spec `docs/superpowers/specs/2026-10-09-first-day-retention-signals-design.md`): counted only for an install first seen that UTC day on version 1.31.0 or later, joined to next-day return through two-day keyed markers, never forwarded to GA. Desktop 1.31.0+ sends each at most once per installation within 24 hours of the `install.json` `createdAt`, two minutes after the launch report (`src/main/day-one-signals.js`). Main applies consent at the trusted IPC boundary, and private tabs never send product events. `installId` is a random per-install UUID in device-local `install.json`, never synced or joined to other Blanc data. The Worker HMACs it before storage/optional GA forwarding, applies strict validation, replay dedup, per-IP/minute and daily caps, and retains only expiring keyed seen-markers plus aggregate counts per metric. A route-level Cloudflare WAF/rate rule and billing alert remain deployment requirements. If the Worker URL changes, update both `PING_ENDPOINT` and `EVENT_ENDPOINT`.

**Blanc Patron and app icons:** Patron is optional support and unlocks nothing: Blanc Spaces became free for everyone in October 2026 (`docs/superpowers/specs/2026-10-13-blanc-spaces-redesign-design.md`), and Patron does not unlock icon variants either. A space's colour and symbol come from the pure `src/renderer/space-identity.js`, shared by main, the strip and the overlay; its readability guard derives the drawn ink, never the stored hex. The feature is called **Blanc Spaces**, and one saved set is a **space**, in every user-facing surface (renamed from "Named Workspaces" on October 11, 2026, recorded in `docs/website-blanc-spaces-rename-2026-10-11.json`). The command is `/space`; `/workspace` stays a working alias. Internal identifiers, the per-window session "workspace", URLs such as `/features/workspaces`, analytics ids such as `named-workspaces`, frozen release notes and earlier claim ledgers keep their original wording, and UI mock-ups and captures show the released UI until they are re-captured. macOS Settings offers only Sunrise, Sunrise Dark and Sunrise Gold. `settings.js` exports one `isAppIconAllowed()` predicate that both `setSettings()` (write) and `getSettings()` (read) apply, so retired ids fall back to Sunrise even for an active Patron. The one-time `presentationDefaultsResetVersion` migration intentionally resets existing profiles to Sunrise + Billboard for the next release, stamps the synced layout clock, and then preserves choices made after that reset on all later updates. Patron activation happens in the main process and renderers see only the derived `patronActive` boolean, never the key. Setup runbook: `docs/polar-setup.md`.

**Profile Sync** (`src/main/sync.js` + `src/main/sync-crypto.js`): opt-in, end-to-end-encrypted cross-device sync of **Favorites, settings, and optional per-device open-tab snapshots**. `scrypt`→`HKDF` derives the v1 opaque account locator and AES-256-GCM content key; the passphrase is discarded. The derived key persists only through `safeStorage` wrapping, with Linux `basic_text` rejected; legacy plaintext keys migrate fail-closed. The v1 Worker stores opaque ciphertext in KV and cannot read, index, or merge it. The separately approved authenticated v2 protocol and Durable Object migration belong in their own reviewed project and are not part of this tree. **Never synced:** `supporter`, `appIcon`, `searchSuggestions`, `usagePing`, cookies/storage, history/downloads/permissions, and private tabs. Open-tab icons ride in a separately budgeted encrypted store as bounded source-rasterized PNGs; receivers do not contact remote sites. Device names the user chooses (Rename Device… in the Other devices drawer, Settings → Sync for this device) ride in settings as `deviceNames`, merged entry by entry with a clock per device (`src/main/device-names.js`) and written only by `settings.setDeviceName()`; `sync.listRemoteDevices` applies them, and a device still publishes `deviceName()`, never its chosen name. The focus refresh pulls settings with session and icons for that reason. See `cloudflare/sync-worker/README.md` for the current v1 Worker.

**Address input normalization** (`normalizeAddressInput()` in `main.js`) is a deliberately simple regex heuristic — has-a-scheme, looks-like-localhost, looks-like-a-domain, else treat as a search query against the engine selected in Settings (DuckDuckGo/Google/Bing/Brave/Kagi, or a custom address with `%s` stored in `searchEngineTemplate`; every search path resolves it through `settings.currentSearchEngine()`). It will misclassify some edge cases (e.g. paths with dots in query strings); that's a known, accepted limitation, not a bug to silently "fix" with a heavier URL parser unless asked. `handOffToOs()` (also in `main.js`) is checked ahead of it wherever a URL becomes a navigation target — page-initiated navigation, `window.open` children, the context menu's "Open Link" actions, and the address bar's raw typed text before `normalizeAddressInput()` ever sees it — so a bare `mailto:`/`tel:`/`facetime:`/`sms:` URI (which has no `://` and would otherwise be misread as a search query or a bogus domain) is handed to the OS instead. The same guard refuses page-initiated `chrome-extension:` navigation, even in inner frames, with one exception: Chromium's built-in PDF viewer (`chrome-extension://mhjfbmdgcfjbbpaeojofohoefgiehjai`, `PDF_VIEWER_ORIGIN` in `blocking-resources.js`) loads each document into a child frame from its own origin, so `installExternalNavigationHandlers` lets through exactly that viewer-initiated load, and `isBrowserResource()` counts the viewer's files as browser resources for both blockers. Refusing either leaves every PDF an empty viewer (the guard's refusal shipped in v1.20.0; fixed October 2026); `npm run test:pdf-viewer:desktop` (the browser-shortcuts CI job) fails if either regresses.

**App icon:** macOS uses the Icon Composer artwork under `build/app-icons/`. Its selectable catalog is Sunrise, Sunrise Dark and Sunrise Gold; Sunrise is the default. Sunrise Gold is a cream glass mark over gold image layers, soft gold in Light and a polished metallic gold in Dark (a `hidden-specializations` swap, because Icon Composer darkens a plain fill by itself in Dark), all generated by `brand:build` into `build/app-icons/colorways/` and compiled by `after-pack-app-icons.js`; its flat fallbacks are `icon-sunrise-gold.png` and `icon-sunrise-gold-dark.png`, chosen by each definition's `darkFlatIcon`. In the live Dock a named stack follows Light and Dark, but only the bundle icon follows the Clear and Tinted icon styles, so in those styles (read from `AppleIconAppearanceTheme`, rechecked on activation and every 10 s) and for Sunrise itself `app-icon.js` clears the custom image with `dock.setIcon(null)` rather than loading a stack by name, which would freeze it. Gold is macOS-only (spec `docs/superpowers/specs/2026-10-19-sunrise-gold-icon-design.md`). Every Sunrise surface (the macOS icon layer, the Windows, Linux and iOS icons, in-app marks, website favicons, logo, press kit and share cards) derives from the vector `assets/sunrise-mark.svg`, the owner's redraw of October 15, 2026, through `assets/sunrise-mark-4096.png`; `brand:build` renders that master only when writing and `assets/sunrise-mark.lock.json` pins both files, because librsvg output differs between platforms. Ink versions close the artwork's hairline between the disc and the top horizon bar. Windows uses the freestanding Sunrise mark from `build/app-icons/Icon.icon/Assets/sunrise-mark.png`; `npm run icons:windows:build` omits its three shortest reflection lines and produces the committed nine-frame (16–256px) `build/windows-icons/icon-sunrise.ico`. `icons:windows:check` guards those bytes, and `win.icon` embeds it into the executable and installed shortcut. Windows has no selectable icon catalog, deliberately: an October 19, 2026 VM spike (`docs/research/windows-runtime-app-icon-spike-2026-10-19.md`) found that only rewriting the installer-owned shortcuts changes the taskbar icon, and the owner chose to keep Sunrise Gold Mac-only and leave Windows as it is. Linux packages `build/icon.png`, a byte-copy of `assets/sunrise-app-icon.png`, which `npm run brand:build` also generates. Mark scale is not portable between compositions: the flat Dock PNGs in `src/renderer/pages/` (the `dock.setIcon` fallback for unpackaged and pre-macOS-26 runs) draw an 824px tile inset 100px into a 1024 canvas, while macOS paints the Icon Composer tile full-bleed, so `sunrise-mark.png` matches the flat mark's share of the visible tile rather than its canvas size; `test/unit/app-icon.test.js` fails if the two drift apart. Legacy B-monogram choices are retired: stale saved ids sanitize to Sunrise, and retired page-icon assets are excluded from the package. The B motif inside Mahjong tile artwork is an intentional nod to Blanc's origins and must remain. Retired source art must not be exposed in Settings, accepted as a saved choice, or compiled into the adaptive catalog unless the product decision changes again.

## Cross-platform parity infrastructure (`spec/`, `tokens/`, `settings-schema/`, `copy/`, `test/desktop/`)

Scaffolding for a **future** native iOS/Android port (landed July 2026, PR #13). The mobile apps don't exist yet — this Electron app is the **reference implementation**, and everything here is additive to it except one test-only, env-gated hook.

**`spec/` is the platform-neutral source of truth for what Blanc *is*.** Features `F1–F24` define the user-facing contract each platform must implement; the divergence register `D1–D14` documents where platforms deliberately differ (e.g. the ad-blocking engine — desktop/Android programmatic vs. iOS's declarative `WKContentRuleList`, which reintroduces a Manifest-V3-style rule cap) plus the parity contract that still holds across the split; `blocking-backends.md` specs the two mobile blocking engines concretely; `parity-matrix.md` is the dashboard; `spec/acceptance/*.feature` are shared Gherkin scenarios. The governing rule: **parity means product/behaviour parity, not implementation parity** — a divergence is *documented* (add a `D#`), not avoided. `spec/README.md` is the entry point. It's a spec, not code; editing it doesn't change the app.

**Three "single source of truth" substrates generate the (future) mobile code *and* guard the desktop against drift.** `tokens/tokens.json` (design tokens), `settings-schema/schema.json` (settings enums + defaults), and `copy/slash-commands.json` (slash-command copy) each have a `build.mjs`: `npm run <name>:build` emits the mobile artifacts under `*/generated/` (Swift/Kotlin, plus iOS `.strings` / Android `.xml`), and `npm run <name>:check` verifies the **desktop** hasn't drifted from that source. `npm run substrate:check` runs all three, plus `adblock:check` — a same-shaped freshness guard that verifies the committed `WKContentRuleList` blocklist (`adblock/generated/`) still matches the pinned EasyList/EasyPrivacy sources (`adblock/` isn't a mobile-codegen substrate, just a generated artifact kept honest the same way); `.github/workflows/parity-guards.yml` runs it (+ the acceptance dry-run) on every push/PR, so drift fails CI.

**`browser-api/contract.json` is a desktop-only guard of the same shape** (Phase 0 of the platform evaluation in `docs/platform-migration-electron-to-chromium-2026-10-04.md`). It describes every `window.browserAPI` member, and `npm run browser-api:check` executes `src/main/preload.js` in a sandbox to verify members, IPC kind, channel, argument shaping, platform gating and trusted documents, plus channel presence in main and renderer usage. It also pins event payloads field by field and checks every `send('<channel>', …)` site in `src/main`, so a field added to `serializeTabs`, `currentTabsPayload` or any structured event payload needs the matching contract edit. Every `invoke` result is typed and checked against what its `chromeHandle` handler can return; history, Favorites, remote-tab, block-ads and search-suggestion records are proven by executing the modules that build them, so a new field there (or a new search engine in `settings-schema/schema.json`) needs the contract edit too. Object parameters are checked from both ends, so a field a renderer starts sending or main starts reading needs the contract edit as well. A new space `error`/`action`/protection `reason` literal must be added to the contract's unions. Change the preload and the contract together, then run `npm run browser-api:build`; it also regenerates `browser-api/generated/vectors.json`, the bridge's test vectors, which the check replays against the preload, so commit and review that diff too. The same check guards `window.bowserPages` (`tab-preload.js`) and the fill-status capsule bridge against `browser-api/bridges.json`. Each `pages:*` channel's hosts there must equal the host list its `pages.js` handler allows, so a new internal-page capability needs the preload, the handler and `bridges.json` changed together. See `browser-api/README.md`.

**The critical operational rule:** the desktop CSS/JS is *guarded, not generated* (a headless build can't visually re-verify chrome), so the source-of-truth JSON and the desktop file are kept in lockstep by the check, not by codegen. If you change a token value in `styles.css`/`pages.css` (the Theming section's `:root` custom properties), a default/enum in `settings.js` (search engines, themes, app icons — Blanc Supporter / App icon sections), or a slash-command hint in `overlay.js`/`pages/shortcuts.js`, you **must** also update the matching JSON and run `<name>:build`, or `substrate:check` fails — and vice versa. Never hand-edit `*/generated/` files. The checkers parse those desktop files with comment-stripping + line-anchored regexes to avoid false-negatives; if you substantially restructure them (single-line vs. one-per-line declarations), re-verify with `node <name>/build.mjs --check`.

**`test/desktop/` is a desktop acceptance harness** (Cucumber + Playwright-Electron) binding the `spec/acceptance/` scenarios to desktop step definitions (156 scenarios executing green in the `runnable` profile, out of 194 desktop-applicable; the rest a tagged backlog). It drives the app through **`src/main/test-hook.js`, a test-only main-process surface `main.js` installs only when `!app.isPackaged && process.env.BLANC_TEST === '1'`** — airtight (never a packaged build; `BLANC_TEST=0/false` stays off). That env-gate is the *only* parity change to shipping code; in test mode it skips the network ad-engine build so the app launches offline and exposes state on `globalThis.__blanc`. `npm run test:acceptance:dry` resolves step definitions without launching; `npm run test:acceptance:desktop` runs them (prefix `xvfb-run -a` on headless Linux; needs the Electron binary).

## Memory benchmark (`bench/memory/`)

A macOS-only harness that measures browser memory, added because an Instagram commenter asked how Blanc compares and nothing in the repo could answer. `npm run bench:memory -- --list` / `--probe` / `--browsers=blanc,chrome,zen --workloads=mixed --reps=3`. It sums **`phys_footprint` across a browser's whole process tree** — never summed RSS, which counts the engine framework once per renderer, so the error scales with process count and systematically penalises whichever engine isolates more per site; that measures the process model twice and calls it a result. Four backends (`footprint`/`vmmap`/`top`/`ps`) are probed in fidelity order and the winner is re-validated against the *first real browser* (`resolveReadableBackend`), because selection can only probe our own unhardened Node process. Results land in `bench/memory/results/`, which is gitignored — commit only a run you actually cite.

**The design rule is that checks fail rather than warn.** A cell must prove it loaded its pages, read back from the browser's own visit log after it quits (`history.json` for Blanc, `Default/History` for Chromium, `places.sqlite` for Gecko), matched **per page not per host**, joined against *visit* tables rather than URL catalogues (a `moz_places` row can be a bookmark), and bounded to the cell's own start time (profiles are copied from a warmed template). A cell with unreadable live processes, no idle baseline, or a browser that never initialised its profile is rejected — never published with a caveat. Three review rounds found 57 issues before it ran; running it found three more that no amount of reading had caught: `kill(pid, 0)` reports a **zombie** as alive, a flat byte total is not settled while the **process tree is still growing**, and macOS *transiently* refuses `footprint` on sandboxed renderers.

**Blanc-specific hazards it encodes, all still true of the app:** `installStartupNavigationGate` (`main.js:226`, installed at `:3751`) cancels every http(s) main-frame request until the blocker compiles, so a cold profile can look perfectly idle while loading nothing; a packaged Blanc copies a legacy `Bowser` userData directory into any path that doesn't exist yet (`main.js:153`), so profile dirs are created *before* launch; an unpackaged Blanc relocates userData to `<dir>-Dev` (`main.js:144`), so never benchmark a dev run; `main.js:3755` opens one `blanc://newtab` beyond the argv URLs (`extraBlankTabs`); and **`BLANC_TEST=1` disables ad blocking**, so the acceptance test-hook is unusable here. Third-party quirks found by running: Zen consumes the *first* startup entry with its own workspace surface (Gecko profiles lead with `about:blank`), Gecko rejects a copied profile carrying a stale `lock`, and a cross-domain redirect (`dailymail.co.uk` → `dailymail.com`) fails per-page matching for Blanc alone because Chromium and Gecko log redirect chains while Blanc records only the committed destination.

**The published figures are pinned.** `site/src/components/MemoryChart.astro` (the ad-blocking, Features and Media pages), `docs/press/fact-sheet.md`, and the committed run are held together by a `public-truth` test that recomputes the median from the run's own repetitions — change one alone and the build fails. Re-running means updating all three together. The two qualifications must travel with the numbers wherever they appear: Brave is the fair peer (it also blocks by default; in the October 19, 2026 run on v1.38.0 it used a little more than Blanc, 1.7 GB against 1.5, and in the October 15 run on v1.34.0 a little less, so the two are close), and the gap to Chrome is the blocking (blocker off, Blanc used 5.2 GB against Chrome's 4.9, with overlapping ranges).
