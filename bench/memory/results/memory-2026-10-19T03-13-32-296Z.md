## Per-browser caveats

- **Blanc:** main.js creates one blanc://newtab at startup in addition to the URLs passed on the command line — hence extraBlankTabs: 1. Blanc CANCELS every http(s) main-frame request until its blocker is compiled (installStartupNavigationGate, main.js:226/3751). On a cold profile that gate can stay shut for the whole sampling window, so the runner warms a template profile first and verifies every loaded cell against the browser's own idle baseline. Do NOT set BLANC_TEST=1 for a benchmark run: acceptanceTestMode in main.js disables ad blocking, which would measure a configuration the app never ships.
- **Blanc (blocking off):** Isolates what the built-in blocker contributes. The runner seeds settings.json in the throwaway profile with adblockEnabled: false. Shares a bundle path with the 'blanc' entry, so a process surviving one cell would be attributed to the other — which is why quit() reaps the whole measured process set rather than just the root pid.
- **Google Chrome:** The report's reference row: percentages are relative to Chrome rather than to whichever browser scored lowest.
- **Zen Browser:** Zen ships its own onboarding, separate from Mozilla's about:welcome, so browser.aboutwelcome.enabled=false does not touch it. Every cell mints a fresh profile, so every Zen cell is a first run; its welcome flow hides the browser content until a human clicks through, which would settle fast and clean and be recorded as an excellent result at the requested tab count. extraPrefs sets the pref that suppresses it — if a future build renames it, the welcome screen returns silently and only the load check against Zen's own idle baseline catches it. CONFIRMED 2026-08-09 on Zen 1.x / macOS 27: user.js startup-homepage tab seeding IS honoured — the upstream report of it failing on macOS aarch64 (zen-browser/desktop#12154) did not reproduce here. But Zen consumes the FIRST startup entry with its own workspace/new-tab surface, so the first workload URL was silently dropped (9/10 pages, twice, deterministically). geckoUserJs now leads with about:blank to absorb that.
- **Brave:** Brave's updater (Sparkle) lives inside the app bundle and keeps its check state in ~/Library/Preferences, which --user-data-dir does not reset — so a fresh profile does not prevent an update check firing mid measurement. --disable-brave-update suppresses it. This changes no process-model knob, so it does not violate the no-flags rule; the Gecko driver already sets app.update.auto=false for the same reason. UNVERIFIED: whether Brave opens a welcome tab on a fresh profile despite --no-first-run. If it does, extraBlankTabs must be raised.
- **Vivaldi:** Vivaldi ships its blocker set to block trackers, NOT ads, out of the box; the registry previously said 'built-in blocker (stock settings)', which read as an ad-blocking peer and would have grouped it with Blanc and Brave. UNVERIFIED against a real install — confirm in Settings > Privacy before publishing, since a wrong class silently moves the row into the wrong comparison group. Vivaldi's own UI is a web page rendered in a renderer process, so its process count and baseline include the browser chrome itself — the same property Blanc has, and unlike Chrome's native UI.

## How to read this

- **Median** of the repetitions, not the mean — one run sampled mid-GC should not set the headline.
- **vs ref** compares against the reference browser named above, not against the best row.
- **Range** is min–max across repetitions. A range that overlaps another browser's means the two are not distinguishable at this sample size.
- **Per page** is `(loaded median − idle median) / workload pages`: the marginal cost of a page, with fixed startup cost removed.
- **Procs** is the lowest process count observed across the samples the median was taken from. Chromium and Firefox both isolate content by site, but their process models differ in ways this benchmark does not measure — do not read a process-count difference as an explanation for a memory difference. See Mozilla's [process model docs](https://firefox-source-docs.mozilla.org/dom/ipc/process_model.html) for how Fission allocates content processes.
- **Reps** is how many repetitions actually produced a measurement. A row backed by 1 of 3 has a Range that looks precise and is not.
- **⚠️N** marks rows where N repetitions were still drifting when the sampling window expired.
- Browsers whose own UI is a web page (Blanc, Vivaldi) carry additional always-live renderers for the chrome itself, which are inside both their totals and their baselines.

## Limits of this benchmark

- Live sites change between runs. Results are only comparable **within a single session**, which is why the runner interleaves browsers rather than finishing one before starting the next.
- Every browser runs a **fresh profile**, with no extensions **except any the browser ships itself** — LibreWolf bundles uBlock Origin, and that memory is inside its total. That is the fair engine comparison, but it is not what most people run day to day.
- Memory is one axis. It says nothing about responsiveness, energy, or page-load time.
