# AGENTS.md

This file provides guidance to Codex (Codex.ai/code) when working with code in this repository.

## What this is

Blanc — a minimal Electron browser shell: custom-drawn "Island" chrome (a single floating command pill replacing the traditional tab strip + toolbar, per the Bowser Design System's Island Chrome handoff) with ad/tracker blocking wired in at the network layer, independent of Chrome's extension store and Manifest V3's `declarativeNetRequest` limits. Plus favorites, history, downloads, settings, slash commands, a Quick Switcher, private tabs, an explicit permission policy, and packaging config.

The app was renamed from "Bowser" to Blanc in July 2026 — its former name was inseparable from Nintendo's Mario villain, which didn't fit a serious indie browser's ambitions. `build.appId` in `package.json` deliberately stayed `me.bnfy.bowser` through the rename (only `name`/`productName` changed) to preserve macOS Gatekeeper/notarization identity and the auto-update chain for existing installs — don't "clean up" that mismatch, it's intentional. The design system's project name ("Bowser Design System", referenced throughout this file) is a separate Codex Design project the user maintains and wasn't renamed alongside the app; leave those references as-is.

**Current public baseline (Aug 22, 2026): v1.8.2.** Packaged v1.8.1 discovered, verified, installed, and relaunched v1.8.2 through the real macOS updater handoff, including **Restart Now**. The authenticated public v1.8.2 AppImage launched on Linux and rendered Blanc chrome, the start page, and `v1.8.2`. Windows also passed the real public v1.8.1 → v1.8.2 updater handoff: packaged v1.8.1 discovered and downloaded the update, **Restart Now** completed installation, Blanc relaunched, and the installed version was confirmed as v1.8.2. Details are in `docs/release-incidents/2026-08-22-v1.8.2.md`. A directly launched NSIS installer is not an updater-handoff test — the handoff must begin inside the old packaged Blanc, discover the staged `latest.yml`, download the matching installer, and invoke Restart Now.

## Commands

```
npm install
npm start                       # run in dev (electron .)
npm run dist                    # installable build: macOS dmg/zip, Windows NSIS, Linux AppImage
npm run dist:dir                # quick unpacked build in dist/, no installer
npm run release                 # scripts/release.sh: clean, build, sign, publish to GitHub Releases
```

After a release, `npm run site:deploy` is the production Cloudflare Pages
command. It deliberately includes `--branch=main` because the required clean
release checkout is detached at `origin/main`; without that flag Wrangler
creates a `HEAD` preview and leaves `blancbrowser.com` unchanged. A successful
post-release deployment is not complete until `wrangler pages deployment list
--project-name=blancbrowser` shows the expected source SHA as `Production` on
branch `main` and the canonical changelog shows the new version.

There is no linter configured. Unit coverage runs with `npm run test:unit`; desktop acceptance, packaged migration/first-run, OAuth, DNS, and substrate checks have their own scripts in `package.json`. There is no generic `npm test` script.

`npm run release` bumps nothing itself — bump `version` in `package.json` (and consider the `electron` devDependency, since Chromium can't be swapped out of a running app) *before* running it. It shells out to `scripts/release.sh`, which authenticates via the `gh` CLI's own cached session (no `GH_TOKEN` needed locally), builds unpublished, then uses `gh release create` directly instead of electron-builder's own GitHub publisher — that publisher races its per-artifact upload tasks against each other on first publish for a tag and can leave a release missing `latest-mac.yml` or a blockmap; creating the release once with the complete macOS asset set avoids that. **Released versions are immutable:** the script checks local/remote tags and GitHub releases before building and fails if the version already exists; always bump to a new version, never overwrite assets. It also refuses dirty desktop release sources and wipes `dist/` before building so artifacts correspond to committed code and stale files never linger.

**Notarization:** the build step is wrapped in `op run --env-file=.env.1password --no-masking -- ...`, pulling `APPLE_ID`/`APPLE_APP_SPECIFIC_PASSWORD` from the 1Password item **"Apple Notarization"** (vault Dev, `username`/`password` fields) plus a literal `APPLE_TEAM_ID` — electron-builder's `@electron/notarize` integration auto-detects those three env vars. The hardened runtime keeps Electron's required JIT/unsigned-executable-memory allowances. Library validation remains enabled for Blanc, Renderer, GPU, and ordinary helpers; only `Blanc Helper (Plugin).app` carries the narrowly required exception for the user-invoked 1Password SDK bridge, enforced by `scripts/sign-mac.js` and `scripts/after-sign-verify.js`. `release.sh` requires `op` and fails closed if notarization cannot run — a public release never falls back to an unnotarized build. A signed-but-unnotarized build gets quarantined and blocked by Gatekeeper the moment it is downloaded (e.g. by `electron-updater` during an auto-update), which is exactly what broke a stale pre-rebrand install after the v0.3.0 release.

**Release-operator protocol (mandatory after the v1.4.0 and v1.5.1 incidents):** `release.sh` supports exactly two interactive modes. Native Terminal.app is the default (`BLANC_RELEASE_OPERATOR=terminal`). A Codex/Claude release may explicitly request `BLANC_RELEASE_OPERATOR=agent`, allocate a real PTY, and run the whole command outside the sandbox with the user's execution approval; never spoof `TERM_PROGRAM`. However, the Codex execution safety layer rejected that route during v1.5.1 even after explicit approval. Do not waste time retrying it: after the first policy rejection, explain the constraint once, obtain approval to use native Terminal, and launch the complete terminal-mode command there automatically so the user does not have to copy or type it. This is still a foreground, visible, interactive Terminal release—not a background wrapper. The script itself performs the proven fail-fast authentication command `OP_BIOMETRIC_UNLOCK_ENABLED=true op signin` before any build work, then uses forced desktop integration again for `op run`; agents must not invent a separate sign-in flow. If `op` offers to add an account manually, cancel. Approve only the identity matching the actual operator. A sandboxed `gh auth status` can falsely report an invalid token because it cannot reach the macOS keyring: retry outside the sandbox and use the connected GitHub app or working Git credential before asking the user to reauthenticate; never send the user through `gh auth login` unless those existing paths have all genuinely failed. The canonical commands and stop conditions are in `docs/release-verification.md`; read that section immediately before every release. Complete the fresh Safari Sigstore page immediately. While notarization runs, inspect process names only (`ps ... comm`), never full arguments: `notarytool` includes the app-specific password in argv. If a tag/draft already exists, never rerun the full immutable release or overwrite native assets; follow the failed-draft recovery in `docs/release-verification.md`. Dated records live in `docs/release-incidents/`, including `2026-08-17-v1.5.1.md`.

**Windows & Linux:** `release.sh` only builds macOS locally (it's a macOS dev machine), then dispatches `.github/workflows/release-windows-linux.yml` (`gh workflow run ... -f tag=$TAG`) and watches it to completion. That workflow builds NSIS on `windows-latest` and AppImage on `ubuntu-latest` and uploads both onto the same draft release; duplicate uploads fail. Dispatch or native-build failure leaves the release as an unpublished draft. Windows code signing is fail-closed: **Azure Trusted Signing** is tried first from the Azure secrets/variables; a complete `CSC_LINK`/`CSC_KEY_PASSWORD` pair is the traditional Authenticode fallback; absent or partial signing configuration fails the job. Both the installer and unpacked app must have a valid timestamped signature whose exact subject equals `WINDOWS_EXPECTED_PUBLISHER`, and `windows-signature.json` binds that observation to the installer SHA-256. Linux AppImages have no OS-level equivalent, so release-manifest authentication is their publisher check.

Before a Windows hotfix is released, agents can build a private, signed installer from the candidate branch with `gh workflow run release-windows-linux.yml --ref <candidate-branch> -f mode=validation -f platform=windows`. Validation mode checks the same Authenticode identity, timestamp, fuses, and required files, but uploads the installer, blockmap, signature record, and `latest.yml` only as a three-day GitHub Actions artifact. It never creates or modifies a GitHub Release, never uploads updater metadata to the public feed, and never runs Linux. Installing the EXE proves install/launch and packaged behavior; launching it directly with `/S` while Blanc is open does **not** prove the `electron-updater` restart handoff. A handoff claim requires Blanc itself to discover the exact staged `latest.yml`, download the candidate, and invoke **Restart Now**. Obtain the user's explicit affected-machine confirmation before merging, tagging, or running `npm run release`. If an owner elects to waive a remaining gate, state the missing evidence and risk first, obtain an explicit written approval, and record the waiver in the dated release incident; never silently check off an unperformed test. Normal releases dispatch with `mode=release`; `scripts/release.sh` supplies it explicitly.

The Azure branch requires every tenant/client/account/endpoint/profile/publisher value before it is attempted; partial Azure configuration may use the complete CSC fallback but may never reach unsigned output. Two electron-builder artifact-naming quirks matter: an AppImage for the runner's default architecture gets no `-x86_64` suffix, and its block map is embedded rather than emitted separately. Re-check real `dist/` output before changing patterns. The release gate also verifies Electron fuses in every packaged executable, emits a CycloneDX SBOM and `SHA256SUMS`, signs the complete checksum manifest with Sigstore, and requires exact OIDC identity/issuer verification before publishing. GitHub Actions are commit-SHA pinned; native artifacts receive GitHub provenance attestations.

The desktop ad blocker compiles only the bundled, hash-verified EasyList + EasyPrivacy snapshots in `adblock/sources/`; it makes no live filter-list request at startup and strips remote scriptlet resources. The compiled engine is cached in userData as `adblock-engine.v<N>.bin`; delete it to force a rebuild from the same bundled snapshot. Updating the lists is a reviewed release input: update `pinned.json`, run `npm run adblock:build`, and commit the generated snapshot/hash changes together.

The pinned blocker files are byte-verified, so `.gitattributes` must keep `adblock/sources/*.txt`, `adblock/sources/pinned.json`, and `adblock/generated/*.json` at `eol=lf`. Without that, a Windows checkout converts them to CRLF and every packaged launch correctly fails closed with **Blocking could not start**. The native Windows workflow must run `npm run adblock:check` before electron-builder; never remove or bypass that gate. Every electron-builder package also runs `scripts/verify-packaged-adblock.js` from the cross-platform `afterPack` hook, comparing the actual `app.asar` payload byte-for-byte with the verified release inputs before signing. Release workflows repeat that packaged-payload check explicitly for macOS, Windows, and Linux.

Auto-update (`electron-updater` against GitHub Releases) only runs in packaged builds — `npm start` skips it entirely. Releasing means bumping the `electron` devDependency (it tracks Chromium stable) and `version` in `package.json`, since Chromium itself can't be swapped out of a running app.

## Architecture

**Many `BrowserWindow`s, each with many `WebContentsView`s.** The window's own `webContents` renders `src/renderer/index.html`/`styles.css` through the exact-allowlist `blanc-chrome://` scheme — the chrome **strip**: a slim (64px) band holding the resting island pill (back/forward, the active group's tab dots with a capped overflow, favicon, domain, the Blanc Blocker count, private chip, and a trailing reload/favorite/close-tab/downloads action cluster), window controls, and permission prompts. The whole resting pill is scaled up in one place with `zoom` on `#islandPill` (kept in lockstep with the `--strip-h` geometry token); each anonymous tab dot blooms into a disc showing that tab's favicon on hover/focus (`.dot-peek`, reusing the pill's favicon rendering) so you can tell which tab you're switching to before you click. Each tab is a separate `WebContentsView` added as a child of the window's `contentView` at `y = chromeHeight`; only the active tab's view is attached, so switching tabs is remove-one/add-another rather than destroying anything — but an *idle background* tab is a separate matter, and its renderer is deliberately discarded (see **Quiet Tabs** below). `src/main/main.js` owns all of this: the `tabs` Map + `tabOrder` array are the single source of truth, and both chrome renderers only ever reflect `tabs:updated` broadcasts.

**Quiet Tabs.** An idle background tab's renderer is deliberately discarded to reclaim its memory (~148 MB/tab measured on Electron 43), and rebuilt when the tab is activated again. Policy is pure and unit-tested in `src/main/tab-sleep.js` (`sleepCandidates`, `trimSnapshot`, `TAB_SLEEP_DELAY_MS`) — no `require('electron')` in that file. View construction and the whole per-tab listener set live in `src/main/tab-view.js` (`createTabView`, `wireTabView`, `initTabView`), which is also the single home of the private-session choice. `main.js` owns `sleepTab`/`wakeTab`, the 30 s sweep, and the wake generation (`tab.wakeGeneration`) that suppresses history and failure handling across every hop of a redirect chain. **`liveContents(tab)` is the only correct liveness check**: after `webContents.close()`, `view.webContents` can read back `undefined`. The main-process-only `sleepSnapshots` Map retains bounded navigation recovery data and must never move onto the tab record or cross IPC, disk persistence, sync, or crash reporting; snapshots may contain page state and POST bodies. During app shutdown, `closeTab` must never select and wake a surviving quiet tab while Electron tears down the native window. The dirty probe protects changed form controls across the frame tree and Chromium's unload objection. It deliberately does **not** treat non-empty `sessionStorage` as user work, because ordinary sites create site-owned keys on load and that blanket rule makes the feature inoperative. Instead, a storage-bearing tab keeps its WebContentsView in the snapshot Map, discards only its provably-exclusive renderer, and reloads that same WebContents so Chromium's browser-process sessionStorage namespace survives; any beforeunload listener or shared/uncertain renderer PID leaves it awake. `session.json` has an optional `meta: [{title, favicon}]` array parallel to `urls`, written into each v2 `windows[]` entry, never the five-key flat rollback mirror; `version` is `2`. Restored tabs are born quiet and only the selected tab loads. Internals say `asleep`/`tabSleep`/`sleepSnapshots`; every user-visible and assistive string says **quiet**, except the fixed `/sleep` command. The device-local delay is Settings → General → Quiet inactive tabs (`off|30m|1h|6h`, default `1h`, deliberately outside `SYNCED_KEYS`); Off stops future quieting and never wakes an existing quiet tab or drops its snapshot.

**Reopen Closed Tab.** Closing a tab records a per-window closed entry with three internal restore tiers: for ~30 s the closed tab's live `WebContentsView` is parked (same view re-attached on ⌘⇧T, no re-fetch, JS and POST state intact), then it degrades to a `trimSnapshot()` restore (back stack, scroll, group, pin, slot), with URL-only as the floor. Never expose tier jargon such as **held** in user-visible copy. Pure policy lives in `src/main/closed-tabs.js` (`holdEligibility`, `sanitizeSnapshot`, `buildTabEntry`/`buildGroupEntry`, `expireHolds`, `expireEntries`, `projectEntries` — no `require('electron')`); `main.js` owns parking (`parkTabView`), the held-state firewall (a parked page keeps executing, so it gets deny-all `setWindowOpenHandler`, main-frame navigation refusal, crash/destroy downgrade observers, and blanket permission denial via `heldWebContents` + `setHeldRequesterCheck` in permissions.js), restore (`reopenEntry`, the `adoptView` seam in `createTab`), and disposal. One entry per user action: `closeGroup` captures first and records a single group entry restored whole at its cluster index. Closed entries are the same class of secret as `sleepSnapshots` — snapshots and view refs never cross IPC/disk/sync; renderers see only `{id,title,favicon,tabCount}`. The panel offers per-entry Forget and Clear all; either must immediately destroy a parked view. Entries also expire after one hour and remain capped at 25. Capture-anchored, prompt-pending, loading, quiet, and opener-family tabs are never held (Tier 1); private tabs are never recorded at all. Nothing is persisted, and on macOS dock-close the held view is destroyed while snapshot entries survive until their normal expiry.

Per-window state (workspace, overlay, shield popover, utility sheet, focus
reclaim, permission prompts) lives on a window-runtime record
(`src/main/window-runtime-registry.js`) — one per native browser window — resolved
via AsyncLocalStorage bindings and sender-derived IPC; the `tabs` Map stays
process-wide with per-tab `runtimeId`. `session.json` is versioned (v2 +
a v0 mirror of the focused window so a rollback to 1.0.x keeps tabs).

**Local profiles.** `profiles.json` defines the permanent Personal identity plus bounded named profiles. Personal keeps every shipped root JSON file and Electron's default session, so upgrades move no existing data. Named profiles store Favorites, history, download metadata, and remembered permissions under `profiles/<opaque-id>/`; their normal tabs use `persist:blanc-profile-<id>` and private tabs use `private-browsing-<id>`. Settings, Supporter, telemetry, and network/presentation preferences remain device-level. Profile Sync and remote-tab presentation are Personal-only. Deletion is exact-name-confirmed and crash-resumable through the device-level `profile-deletions.json` marker; it closes the profile's windows, clears its Electron sessions, drops cached store/download state before removing its directory, and removes every saved workspace. Downloaded files remain on disk.

**The island's expanded states live in a separate always-on-top overlay `WebContentsView`** (`src/renderer/overlay.html`/`overlay.js`, transparent via `setBackgroundColor('#00000000')`), attached to the window's `contentView` only while something is showing, so panels float *over* the web content instead of growing the strip and shifting it down. Main owns the mode (`overlayMode`): `'panel'` — the command bar expanded in place at the pill's anchor; `'palette'` — the same panel summoned by ⌘L, on the same anchor as `'panel'` but over a scrim (it used to sit 120px lower, which read as a detached window rather than the pill opening); `'find'` — the find capsule, whose overlay bounds are kept *tight* around the capsule so the rest of the page stays clickable. `showOverlay`/`hideOverlay` in main are the only mutators; the overlay renderer just applies `overlay:show`/`overlay:hide`. Guards that matter: a tab view attached while the overlay is open must be re-stacked below it (re-`addChildView(overlayView)` in `setActiveTab`), Escape dismisses via main's `before-input-event`, and overlay `blur` dismisses panel/palette (not find) — but is ignored while a blank-tab focus reclaim is pending, or the reclaim dance re-opens/closes in a loop. The panel's list area shows the tab switcher at rest, slash commands when the input starts with `/`, and a six-row blend of the Quick Switcher (loose substring/in-order matching across open tabs, favorites, history) plus best-effort autocomplete from the selected search engine while typing anything else. Provider requests are debounced, main-process-only, cookie-free, bounded, and never made for URL-like/sensitive-looking/pasted text or private tabs; the device-local `searchSuggestions` toggle can disable them entirely, and stale/failing responses silently disappear.

**Private tabs** (`/private`, ⌘⇧N, `private` on main's tab model): never recorded to history (`history.addVisit`/`updateTitle` guarded per-tab), excluded from session persistence, sync, and reopen-closed-tab, inherited by `window.open`/context-menu children, and opened to `blanc://newtab/?private=1`. All private tabs in one app run share the non-persistent `private-browsing` Electron session, separate from regular tabs; it is discarded at quit. Completed private-download metadata is kept only in memory, while the file the user saved remains on disk. Favorites still behave normally. While the active tab is private, both chrome documents set `data-theme="private"` on `<html>`; the pill gets a dashed border, hollow dots, and a "private" chip that closes the tab.

**Tab groups** (per the Island Tab Groups exploration in the Bowser Design System): main owns `groups` (`{id, name, collapsed}`, display order = cluster order) alongside `tabs`; each tab carries `groupId` (or null). Groups have **names, not colors** — lowercase mono labels. A group exists only while it holds tabs (`pruneEmptyGroups`); creation happens through `/group <name>` (find-or-create) or the inline "new group…" field in the per-row "group" chip's picker, and membership moves via that picker (`→ name` / `→ none`), `/ungroup`, or `/close-group`. The picker's name field survives `tabs:updated` re-renders (value+focus restored across `replaceChildren`) — broadcasts arrive ~10/s while any tab loads. The pill now renders **only the active tab's group** as dots (capped at 8, with a quiet `+N` that opens the panel). It does **not** name the group — group identity lives in the ⌘L panel (group headers, the per-row chip) and in which tabs the dots represent. Pinning is group-local: a grouped pin stays in that group and leads its rows/dots, while only ungrouped pins use the standalone pinned section in the ⌘L panel. Other groups also live in that panel behind per-group headers (click folds/unfolds; collapsed groups show an "N tabs tucked away" row). The Quick Switcher matches group names (ranked above tabs; picking one focuses the group), and ⌘1–9 change meaning when groups exist: nth *cluster* (group's first tab, unfolding it) instead of nth tab. A plain new tab (⌘T, panel row, `/new`) always launches ungrouped, regardless of the active tab's group — join a group afterward via the row's "group" chip picker. `window.open`/context-menu children are the exception: they still inherit the opener tab's group, since a link opened from a grouped tab is presumed to belong with it. New private tabs are never grouped. `session.json` persists `groups` plus a `groupIds` array parallel to `urls`; groups referenced only by private tabs stay out of the file.

**The chrome documents only load their HTML/CSS once, at window creation** (`rt().window.loadURL(CHROME_INDEX_URL)` + `createOverlay()` in `createMainWindow()`). Editing `src/renderer/index.html`, `overlay.html`, `styles.css`, or either chrome renderer requires relaunching the app to see the change — `Cmd/Ctrl+R` reloads the *active tab's* `WebContentsView` (which re-fetches `blanc://.../pages.css` fresh on every navigation), not the chrome. Don't rely on a plain reload to verify a chrome-level change; restart `npm start`.

**`blanc://` internal pages** (`newtab`, `bookmarks`, `history`, `downloads`, `settings`) are served by `src/main/pages.js` over a privileged custom scheme instead of `file://`, so they get a real origin and ordinary web content can never link into local files. The handler resolves every request through `path.basename()` before joining it to `PAGES_DIR` (`src/renderer/pages/`) — **it can only serve flat files directly in that one directory, no subdirectories and no `../` traversal.** Any asset (`pages.css`, `icon.svg`, a font file) that `pages/*.html` needs must live flush inside `src/renderer/pages/`. The five utility pages (`bookmarks`, `history`, `downloads`, `settings`, `shortcuts`) **never open as tabs** — main routes them (via `src/main/utility-pages.js`'s `isUtilityUrl`, the single classifier checked at `openInternalPage`, tab `will-navigate`, `createTab`, the window-open handler, and typed navigation) into the **utility sheet**: a transparent always-below-the-island `WebContentsView` whose page draws its own scrim + card (`body.sheet` in pages.css + the shared `sheet.js`). Esc, scrim click, and the nav ✕ (strictly-guarded `pages:surface:close`) dismiss; tab switches/creation and summoning ⌘L dismiss; outbound clicks open real tabs; session restore filters stale utility tabs through `session-restore.js`'s zipped filter. The newtab page is the **"ledger" start page** (direction 1a of the Start Page exploration in the Bowser Design System): date line, "Where to?", favorites, tab groups ("pick up where you left off" — clicking one focuses that group), and a footer with the weekly blocked count + ⌘L hint. There's deliberately no mascot on this page — an earlier version had an animated pixel-art dog sprite here, retired along with the "Bowser" name as part of the July 2026 rebrand; don't reintroduce one without being asked. Live group state and the blocked counter cross from main.js via the `startPage` hooks passed to `setupPages` (`pages:start:data` / `pages:start:focus-group`).

**Security posture:** the chrome window, the overlay view, and every tab's `WebContentsView` run `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`. Three separate preload scripts, deliberately asymmetric:
- `src/main/preload.js` — the rich `browserAPI` bridge (tab lifecycle, window controls, island data + command actions). Attached only to the chrome window and the overlay view.
- `src/main/tab-preload.js` — a host-specific `bowserPages` bridge: each `blanc:` page receives only its own methods, and navigation re-evaluates the surface. Main independently maps every `pages:*` channel to the exact expected host, owned WebContents/session/surface, and main frame through `pages-ipc-trust.js`. `bowserPages`/`bowserAuth` kept their pre-rebrand internal names.
- `src/main/chrome-compat-preload.js` — an unprivileged session-wide `window.chrome.app`/`csi`/`loadTimes` compatibility shim. It is registered through `session.registerPreloadScript` so both ordinary tabs and Chromium-adopted OAuth children receive it without replacing the child's `webPreferences.preload` (which severs `window.opener`). It exposes no IPC or application data.

**IPC channel namespaces:** `tabs:*` (tab lifecycle, via `browserAPI`), `pages:*` (internal pages' guarded data API, via `bowserPages`), `window:*` (minimize/maximize/close), `chrome:*` (strip/overlay → main: layout height, open-island/open-find, and island data + command actions — history-list/favorites-list/history-clear/adblock-toggle/adblock-exempt-active/cycle-theme), `overlay:*` (main ↔ overlay show/hide/close).

**Address bar focus** is intentionally intricate (`tabsWantingAddressBarFocus`, `reclaimAddressBarFocus()` in `main.js`) because a blank new tab needs the island panel's address input focused rather than its empty page content, and `WebContentsView` focus can settle asynchronously after Electron's own focus/navigation callbacks — hence the reassert-on-next-tick pattern rather than a single focus call. `focusAddressBar()` now means "show the overlay panel and focus its input".

**Theming:** CSS custom properties in `:root` (+ a `prefers-color-scheme: dark` override, + an explicit `:root[data-theme="private"]` scope), with the same token names duplicated across `styles.css` (chrome strip *and* overlay — one shared stylesheet) and `src/renderer/pages/pages.css` (internal pages) — separate files by necessity given the flat-serving constraint above, kept in sync by hand, not shared/imported. `nativeTheme.themeSource` is driven by Settings → Appearance (also cycled by `/theme`), so system/light/dark propagates to chrome, internal pages, and web content together, no restart.

**CSP is declared per-file**, not centralized: `index.html`, `overlay.html`, and each `pages/*.html` file carries its own `<meta http-equiv="Content-Security-Policy">`. Chrome/internal-page fonts and assets are bundled locally; their CSPs do not allow remote images or fonts. Adding any external resource requires a narrow per-document policy change and a privacy/data-flow review.

**Ad blocking** (`src/main/adblock.js`): a single `@ghostery/adblocker-electron` engine is built from the bundled verified snapshot and attached to both regular and private sessions. Request blocking, declarative cosmetic CSS, and bundled page-context scriptlets remain; `adblock-scriptlets.js` isolates each scriptlet's declarations to prevent cross-scriptlet helper corruption. Toggling in Settings calls `enableBlockingInSession`/`disableBlockingInSession` at runtime; blocked-request counts are per-tab and coalesced (~10 broadcasts/s).

**No extension runtime or Blanc-owned password manager — deliberately.** The former extension runtime caused native crashes, required an unsandboxed chrome window, and imposed a GPL constraint, so it remains removed. The production 1Password integration is narrower: off by default, device-local, explicit Fill gesture only, and dependent on the user's installed 1Password app/account. `src/main/onepassword-broker.js` is the sole SDK owner inside Electron's Plugin utility process; only that helper may disable macOS library validation. Main sees one transient selected credential solely to inject it into the revalidated isolated-world target; credentials never cross renderer IPC, persist, sync, log, or enter crash reports. Website matching must honor 1Password's `AnywhereOnWebsite` / `ExactDomain` / `Never` rules without symmetric eTLD guessing. Do not add save/update, password generation, TOTP, passkey, payment-card, bulk export, background lookup, automatic fill, or service-account-token support without a new product/security review. Electron Touch ID WebAuthn still creates Blanc-owned, device-bound Secure Enclave passkeys through `src/main/webauthn.js`; it does not read existing third-party credential-manager passkeys. On startup, `main.js` still performs a one-time purge of extension profile state left by old versions, deliberately preserving ordinary websites' Service Worker data.

**Naming: "Favorites" vs. `bookmarks`.** The user-facing feature is called **Favorites** (heart icon) per the Bowser Design System — but every internal identifier deliberately stays `bookmarks` (`bookmarks.js`, `bookmarks.json`, `pages:bookmarks:*` IPC, the `blanc://bookmarks/` URL, `pages/bookmarks.html`). Change labels/copy only; don't rename the internals, and don't "fix" the mismatch in either direction.

**Persistence** is one `JsonStore` per feature (`src/main/store.js`): JSON in `userData`, loaded synchronously once and normally saved on a 250ms debounce. Writes use an owner-only temporary file, fsync, and atomic replacement; sensitive callers can flush synchronously. `settings.json`, `bookmarks.json`, `history.json` (capped at 5000), regular `downloads.json` (capped at 200), and `adblock-stats.json` remain local. Sync's retained derived key is stored only as an OS-credential-service-wrapped `protectedKey`; legacy plaintext keys migrate fail-closed. Because `userData` derives from `productName`, the permanent one-time Bowser→Blanc packaged-profile copy must remain so existing users keep their local data.

**Telemetry** (`src/main/telemetry.js`): a single launch ping, **on by default and opt-out** through the fresh-profile privacy choices or Settings. A fresh profile must save the presented choice before any ping; existing profiles retain their saved setting and are not re-asked. Packaged builds only; fire-and-forget. Payload is `{installId, sessionId, version, platform, arch, osVersion}` with OS version coarsened to a major. `installId` is a random per-install UUID in device-local `install.json`, never synced or joined to other Blanc data. The Worker HMACs it before storage/optional GA forwarding, applies strict validation, replay dedup, per-IP/minute and daily caps, and retains only expiring keyed seen-markers plus aggregate counts. A route-level Cloudflare WAF/rate rule and billing alert remain deployment requirements. If the Worker URL changes, update `PING_ENDPOINT`.

**Blanc Supporter** (`src/main/supporter.js`): a $19 one-time Polar.sh license that unlocks three supporter-only Dock colorways (`ember`, `plum`, `gold` — generated by `scripts/gen-supporter-icons.sh` from `icon-default.png`, same fixed geometry). Activation happens once in the main process against Polar's customer-portal API (dev builds hit the sandbox; `POLAR_ORGANIZATION_ID` in `supporter.js` is the production org's id, hardcoded) and writes `settings.supporter` via `setSupporter()` — the only writer; the generic `setSettings()` whitelist deliberately ignores it. Once set, the record is trusted forever: no revalidation, no phone-home, works offline — perks are cosmetics, DRM would betray the brand. Renderers only ever see a derived `supporterActive` boolean, never the key. `settings.js` exports one `isAppIconAllowed()` predicate that both `setSettings()` (write) and `getSettings()` (read) apply — a stale/unlicensed supporter icon id (hand-edited or copied settings.json) reads back as the default (`paper`) everywhere a renderer or `applyAppIcon()` sees it, not just at the Dock. Setup runbook: `docs/polar-setup.md`.

**Profile Sync** (`src/main/sync.js` + `src/main/sync-crypto.js`): opt-in, end-to-end-encrypted cross-device sync of **Favorites, settings, and optional per-device open-tab snapshots**. `scrypt`→`HKDF` derives the v1 opaque account locator and AES-256-GCM content key; the passphrase is discarded. The derived key persists only through `safeStorage` wrapping, with Linux `basic_text` rejected; legacy plaintext keys migrate fail-closed. The v1 Worker stores opaque ciphertext in KV and cannot read, index, or merge it. The separately approved authenticated v2 protocol and Durable Object migration belong in their own reviewed project and are not part of this tree. **Never synced:** `supporter`, `appIcon`, `searchSuggestions`, `usagePing`, cookies/storage, history/downloads/permissions, and private tabs. Open-tab icons ride in a separately budgeted encrypted store as bounded source-rasterized PNGs; receivers do not contact remote sites. See `cloudflare/sync-worker/README.md` for the current v1 Worker.

**Address input normalization** (`normalizeAddressInput()` in `main.js`) is a deliberately simple regex heuristic — has-a-scheme, looks-like-localhost, looks-like-a-domain, else treat as a search query against the engine selected in Settings (DuckDuckGo/Google/Bing/Brave). It will misclassify some edge cases (e.g. paths with dots in query strings); that's a known, accepted limitation, not a bug to silently "fix" with a heavier URL parser unless asked. `handOffToOs()` (also in `main.js`) is checked ahead of it wherever a URL becomes a navigation target — page-initiated navigation, `window.open` children, the context menu's "Open Link" actions, and the address bar's raw typed text before `normalizeAddressInput()` ever sees it — so a bare `mailto:`/`tel:`/`facetime:`/`sms:` URI (which has no `://` and would otherwise be misread as a search query or a bogus domain) is handed to the OS instead.

**App icon:** `build/icon.png` (1024×1024) remains the generic/macOS fallback source. It and the eleven colorway PNGs in `src/renderer/pages/` all share one fixed layout — an 824×824 rounded square inset 100px into the 1024 canvas, with the mark scaled to a 522px-tall bounding box dead-centered — so a future logo change only needs the mark re-rendered at that same geometry per colorway, not the layout re-derived from scratch. Windows deliberately has one fixed Paper icon: `npm run icons:windows:build` trims the shared margin from `build/icon.png`, fills the native taskbar canvas, enlarges only the central mark by 10% for optical parity with neighboring Windows glyphs, and writes the committed nine-frame (16–256px) `build/windows-icons/icon-paper.ico`; `icons:windows:check` is in the release gates and `win.icon` embeds it into the executable/installed shortcut. Windows does not package selectable icon resources, and Settings hides both the icon picker and its icon-only Supporter section there. The selectable colorways are macOS-only: eight are free (`icon-{paper,ink,graphite,default,midnight,cream,forest,sage}.png` — labels live in `settings.js`'s `APP_ICON_LABELS`, `paper` is the current default, `default` is the original green colorway whose id is frozen for saved settings); three are supporter-gated (`icon-{ember,plum,gold}.png`, see Blanc Supporter above).

## Cross-platform parity infrastructure (`spec/`, `tokens/`, `settings-schema/`, `copy/`, `test/desktop/`)

Scaffolding for a **future** native iOS/Android port (landed July 2026, PR #13). The mobile apps don't exist yet — this Electron app is the **reference implementation**, and everything here is additive to it except one test-only, env-gated hook.

**`spec/` is the platform-neutral source of truth for what Blanc *is*.** Features `F1–F24` define the user-facing contract each platform must implement; the divergence register `D1–D14` documents where platforms deliberately differ (e.g. the ad-blocking engine — desktop/Android programmatic vs. iOS's declarative `WKContentRuleList`, which reintroduces a Manifest-V3-style rule cap) plus the parity contract that still holds across the split; `blocking-backends.md` specs the two mobile blocking engines concretely; `parity-matrix.md` is the dashboard; `spec/acceptance/*.feature` are shared Gherkin scenarios. The governing rule: **parity means product/behaviour parity, not implementation parity** — a divergence is *documented* (add a `D#`), not avoided. `spec/README.md` is the entry point. It's a spec, not code; editing it doesn't change the app.

**Three "single source of truth" substrates generate the (future) mobile code *and* guard the desktop against drift.** `tokens/tokens.json` (design tokens), `settings-schema/schema.json` (settings enums + defaults), and `copy/slash-commands.json` (slash-command copy) each have a `build.mjs`: `npm run <name>:build` emits the mobile artifacts under `*/generated/` (Swift/Kotlin, plus iOS `.strings` / Android `.xml`), and `npm run <name>:check` verifies the **desktop** hasn't drifted from that source. `npm run substrate:check` runs all three, plus `adblock:check` — a same-shaped freshness guard that verifies the committed `WKContentRuleList` blocklist (`adblock/generated/`) still matches the pinned EasyList/EasyPrivacy sources (`adblock/` isn't a mobile-codegen substrate, just a generated artifact kept honest the same way); `.github/workflows/parity-guards.yml` runs it (+ the acceptance dry-run) on every push/PR, so drift fails CI.

**The critical operational rule:** the desktop CSS/JS is *guarded, not generated* (a headless build can't visually re-verify chrome), so the source-of-truth JSON and the desktop file are kept in lockstep by the check, not by codegen. If you change a token value in `styles.css`/`pages.css` (the Theming section's `:root` custom properties), a default/enum in `settings.js` (search engines, themes, app icons — Blanc Supporter / App icon sections), or a slash-command hint in `overlay.js`/`pages/shortcuts.js`, you **must** also update the matching JSON and run `<name>:build`, or `substrate:check` fails — and vice versa. Never hand-edit `*/generated/` files. The checkers parse those desktop files with comment-stripping + line-anchored regexes to avoid false-negatives; if you substantially restructure them (single-line vs. one-per-line declarations), re-verify with `node <name>/build.mjs --check`.

**`test/desktop/` is a desktop acceptance harness** (Cucumber + Playwright-Electron) binding the `spec/acceptance/` scenarios to desktop step definitions (116 scenarios executing green in the `runnable` profile, out of 132 total; the rest a tagged backlog). It drives the app through **`src/main/test-hook.js`, a test-only main-process surface `main.js` installs only when `!app.isPackaged && process.env.BLANC_TEST === '1'`** — airtight (never a packaged build; `BLANC_TEST=0/false` stays off). That env-gate is the *only* parity change to shipping code; in test mode it skips the network ad-engine build so the app launches offline and exposes state on `globalThis.__blanc`, including deterministic overlay/autocomplete readers that never contact a live provider. `npm run test:acceptance:dry` resolves step definitions without launching; `npm run test:acceptance:desktop` runs them (prefix `xvfb-run -a` on headless Linux; needs the Electron binary).

## Memory benchmark (`bench/memory/`)

A macOS-only harness that measures browser memory, added because an Instagram commenter asked how Blanc compares and nothing in the repo could answer. `npm run bench:memory -- --list` / `--probe` / `--browsers=blanc,chrome,zen --workloads=mixed --reps=3`. It sums **`phys_footprint` across a browser's whole process tree** — never summed RSS, which counts the engine framework once per renderer, so the error scales with process count and systematically penalises whichever engine isolates more per site; that measures the process model twice and calls it a result. Four backends (`footprint`/`vmmap`/`top`/`ps`) are probed in fidelity order and the winner is re-validated against the *first real browser* (`resolveReadableBackend`), because selection can only probe our own unhardened Node process. Results land in `bench/memory/results/`, which is gitignored — commit only a run you actually cite.

**The design rule is that checks fail rather than warn.** A cell must prove it loaded its pages, read back from the browser's own visit log after it quits (`history.json` for Blanc, `Default/History` for Chromium, `places.sqlite` for Gecko), matched **per page not per host**, joined against *visit* tables rather than URL catalogues (a `moz_places` row can be a bookmark), and bounded to the cell's own start time (profiles are copied from a warmed template). A cell with unreadable live processes, no idle baseline, or a browser that never initialised its profile is rejected — never published with a caveat. Three review rounds found 57 issues before it ran; running it found three more that no amount of reading had caught: `kill(pid, 0)` reports a **zombie** as alive, a flat byte total is not settled while the **process tree is still growing**, and macOS *transiently* refuses `footprint` on sandboxed renderers.

**Blanc-specific hazards it encodes, all still true of the app:** `installStartupNavigationGate` (`main.js:226`, installed at `:3751`) cancels every http(s) main-frame request until the blocker compiles, so a cold profile can look perfectly idle while loading nothing; a packaged Blanc copies a legacy `Bowser` userData directory into any path that doesn't exist yet (`main.js:153`), so profile dirs are created *before* launch; an unpackaged Blanc relocates userData to `<dir>-Dev` (`main.js:144`), so never benchmark a dev run; `main.js:3755` opens one `blanc://newtab` beyond the argv URLs (`extraBlankTabs`); and **`BLANC_TEST=1` disables ad blocking**, so the acceptance test-hook is unusable here. Third-party quirks found by running: Zen consumes the *first* startup entry with its own workspace surface (Gecko profiles lead with `about:blank`), Gecko rejects a copied profile carrying a stale `lock`, and a cross-domain redirect (`dailymail.co.uk` → `dailymail.com`) fails per-page matching for Blanc alone because Chromium and Gecko log redirect chains while Blanc records only the committed destination.

**The published figures are pinned.** `site/src/components/MemoryChart.astro` (press + ad-blocking pages), `docs/press/fact-sheet.md`, and the committed run are held together by a `public-truth` test that recomputes the median from the run's own repetitions — change one alone and the build fails. Re-running means updating all three together. The two qualifications must travel with the numbers wherever they appear: Brave is the fair peer (it also blocks by default), and the gap is not only blocking (blocker off, Blanc still beat Chrome).
